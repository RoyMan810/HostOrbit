# WebUI HostOrbit

[Документация](../docs/README.md) · [ТЗ v2.4](../docs/spec/HostOrbit_Technical_Spec_v2.4.md)

React-интерфейс Stage2 показывает зарегистрированные VPS в области доступа пользователя, результаты SSH-проверок и обнаруженное ПО. Для входа используйте учётную запись Controller. Список и карточка используют существующие серверные права доступа.

Статус SSH относится к текущему наблюдению. История успешной проверки отображается с собственной датой. Состояния Docker и Nginx описывают наличие файлов по проверенным путям на момент наблюдения.

Карточка VPS показывает, что изменения Firewall и SSH и управление Caddy не поддерживаются. Прямые запросы на изменение отклоняются API даже в сессии Owner. Статус Caddy относится к управлению и не сообщает, установлен ли сервис на VPS.

В карточке также отображаются состояния контейнеров, внесённых владельцем в [защищённую область обнаружения Docker](../docs/stage2-inventory.md). Карточка показывает опубликованные привязки в формате `адрес:порт хоста → порт контейнера/протокол`. Если Docker сообщил пустой список, карточка показывает отсутствие опубликованных портов. Для неполной выборки и старого SSH-helper выводится «Данные о привязках портов недоступны». Для устаревшей выборки карточка помечает эти сведения как исторические.

Для работающего контейнера со свежим наблюдением карточка позволяет открыть **Предпросмотр перезапуска**. Controller проверяет право `vps:restart` на эту VPS. Предпросмотр показывает полный ID и предупреждает о возможном кратковременном простое. При смене VPS или устаревании данных он закрывается. При свежем наблюдении v8 владелец может подтвердить тестовое назначение контейнера, создать Change Plan, запустить preflight и проверить Backup Gate. После повторной аутентификации владелец отдельно отправляет подтверждённую ревизию в очередь и проверяет результат в Timeline. Если ответ на отправку потерян, повторное нажатие использует то же подтверждение и возвращает тот же ID запроса. Timeline открывается по отдельному адресу и восстанавливается после обновления страницы. Пока операция в очереди или выполняется, Timeline обновляется автоматически. В журнале аудита события перезапуска ведут к Timeline той же операции, а Controller повторно проверяет права доступа. Для исполнения на VPS требуется настроенный профиль AC‑28.

В событии плана кнопка **Показать сохранённый план** открывает точную ревизию с целью, изменением, риском, решением о резервной копии и результатом операции. Для просмотра нужны одновременно доступ к аудиту и право чтения этой VPS.

Страница **Журнал аудита** показывает события существующего серверного API в порядке добавления, по 100 записей на страницу: тип, результат, время, ID инициатора, объекта и корреляции. Для чтения требуется `audit:read` с областью `*`; доступ проверяет Controller при каждом запросе. Если на последней странице ровно 100 событий, следующая страница может быть пустой. Обновление повторно загружает текущую страницу.

В событиях `job.accepted`, `job.transition` и `job.finished` кнопка **Показать историю задания** загружает переходы связанной SSH-проверки. Controller отдельно проверяет право `vps:read` на VPS задания. Переход на другую страницу журнала или обновление убирают ранее загруженную историю.

В событии `change_plan.draft_saved` журнал показывает ID плана и номер сохранённой ревизии. Ссылки переводят к ближайшим предыдущему и следующему событиям того же плана и ресурса на текущей странице.

В разделе **Проверить экспорт аудита** выберите категорию событий текущей страницы. Браузер показывает точный JSON перед скачиванием. В файл входят тип события, результат и время UTC. Для SSH-заданий добавляется номер задания внутри файла. Для сохранённых ревизий добавляются номер пары «план и ресурс» внутри файла и номер ревизии. Доступны также категории аутентификации и управления доступом. Исходные идентификаторы и детали событий исключены. При обновлении журнала или смене страницы категория сбрасывается.

**Проверить целостность журнала** вручную запускает проверку всей цепочки Audit и Outbox в одном снимке БД. Controller требует то же право `audit:read` с областью `*`. Интерфейс различает успешную проверку, нарушение целостности и недоступность проверки.

## Сборка и запуск

Для установки скачайте архив `hostorbit-webui-<commit>` из успешного прогона [HostOrbit WebUI](https://github.com/RoyMan810/HostOrbit/actions/workflows/web-ui.yml) на `main`. GitHub выдаёт ZIP после входа в аккаунт. Выбирайте прогон той же ревизии, что и установленный Controller. В распакованном ZIP сверьте `source-commit.txt` с `source_commit` подписанного манифеста Controller и выполните:

```sh
sha256sum -c SHA256SUMS && mkdir -p dist && tar -xzf webui.tar.gz -C dist
```

В архиве готовая статика. Node.js для её установки не нужен. Для ревизии, у которой архив отсутствует или истёк срок хранения, соберите frontend на Node.js 26 из зафиксированного исходного кода.

```sh
cd web
npm ci
npm run build
```

Опубликуйте содержимое `dist/` в корне того же HTTPS-домена, который указан как `--origin` при [установке Controller](../docs/stage1-installation.md). Сохраните существующее проксирование `/api/` к loopback endpoint Controller. Статический каталог содержит только файлы сборки и доступен веб-серверу на чтение.

Для существующего Nginx HTTPS server добавьте маршрут статических файлов рядом с маршрутом API.

```nginx
location / {
    root /srv/hostorbit-web/current;
    index index.html;
    try_files $uri $uri/ =404;
    add_header Content-Security-Policy "frame-ancestors 'none'" always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy no-referrer always;
}
```

В браузере откройте корень HTTPS-домена. Сессия использует HttpOnly cookie Controller, а CSRF-токен хранится в памяти страницы. Язык и тема сохраняются в настройках браузера.

## Ручная SSH-проверка

Выберите включённый VPS и нажмите **Запустить SSH-проверку**. Controller проверяет право `vps:probe` и ставит задание в очередь. Карточка показывает его цель, идентификатор и подтверждённый статус. После завершения инвентарь обновляется.

Кнопка **Повторить тот же запрос** при потере ответа использует исходный VPS и ключ запроса. Кнопка **Проверить статус задания** продолжает чтение уже принятого задания. При неизвестном исходе карточка сохраняет именно этот статус и показывает последнее успешное наблюдение отдельно.

Страница отслеживает одну ручную проверку. Controller хранит принятое задание после закрытия страницы или выхода из системы. Кнопка **Показать историю задания** запрашивает сохранённые переходы этого задания; повторное нажатие обновляет историю. Она не проверяет целостность аудита и не запускает новую операцию.

## Браузерные проверки

Playwright проходит сценарий владельца на русском и английском только с клавиатуры. Проверка охватывает вход, выбор VPS, план перезапуска, подтверждение ревизии, повтор после потери HTTP-ответа и переход из аудита в историю операции.

Установите зависимости из `requirements-dev.txt` в Python 3.15, доступный как `python`. Для тестов нужны OpenSSL и Chrome или Chromium. Тесты поднимают локальный HTTPS Controller с одноразовой SQLite и тестовыми учётными записями.

```sh
npm run build
HOSTORBIT_CHROMIUM="$(command -v google-chrome)" npm test
```

Для Chromium из Playwright выполните `npx playwright install chromium --only-shell`, затем `npm test`.
