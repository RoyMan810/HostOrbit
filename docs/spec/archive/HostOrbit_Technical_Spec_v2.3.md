## 1. Цель и границы продукта

HostOrbit — self-hosted платформа управления VPS, Linux-серверами, Docker/Compose, веб-сервисами, сетевыми конфигурациями, резервированием, мониторингом и контролируемыми операциями. Веб-панель предоставляет единую картину состояния инфраструктуры и последовательные мастера безопасных изменений. Для работы универсального ядра не нужны VPN, Remnawave или домены какого-либо конкретного проекта.

**Нейтральность платформы:** проект и бренд пользователя, адреса, домены, имена VPS и сервисные шаблоны задаются конфигурацией. Встроенные демонстрационные данные не используют боевую инфраструктуру автора. VPN и Remnawave — дополнительные сценарии через явно подключаемую интеграцию, а не обязательная предпосылка установки. **HostOrbit — внутреннее продуктовое имя baseline.** Публичный выпуск под этим именем запрещён до документально подтверждённой проверки товарных знаков и домена; при отрицательном результате изменяется только бренд, не техническая архитектура. Это релизный контроль, не открытый архитектурный вопрос.

Ключевые свойства: **agentless SSH** для работы с VPS; типизированные **сервисные адаптеры** для явно поддерживаемых технологий и API; прозрачная модель **Desired / Observed / Last Applied**; обязательные **Preflight → Diff → Risk-based Backup Gate → Approval → Apply → Verify** для изменяющих операций; достоверные статусы и проверяемая история действий.

Все главы являются согласованным текстом редакции 2.3; единственные нормативные Plan/Job/Incident transitions и release gates находятся в §40. Других правил приоритета или скрытых исключений нет. В первой версии не ставится задача реализовать все согласованные веб-модули. MVP должен завершать полезные сценарии безопасного ручного управления без компромиссов по защите доступа, секретам, очереди операций и восстановлению.

**Независимость от хостера:** HostOrbit не запрашивает, не хранит и не использует API-токены хостинг-провайдеров и не отправляет управляющие API-запросы в инфраструктуру хостера — ни для установки, ни для аварийного восстановления. Ручная изоляция прежнего Controller может выполняться владельцем через консоль, локальный гипервизор, панель хостинга или физическое отключение сервера; никакая автоматическая интеграция с таким интерфейсом не предусматривается.

**Не входит в исходную задачу:** собственная VPN-протокольная реализация, замена сторонних панелей управления или биллинга, неограниченная веб-консоль root, произвольное выполнение пользовательских shell-скриптов из шаблонов, автоматическое редактирование DNS у провайдера, безусловное автоисправление инцидентов, автоматический VPN failover или ручной просмотр приватных ключей в UI. Не заявляется универсальная поддержка произвольного сервиса без соответствующего проверенного адаптера.

## 2. Архитектурный каркас

### 2.1. Компоненты

- **Frontend:** React + TypeScript, адаптивный веб-интерфейс, RU/EN, светлая/тёмная/системная тема, доступность с клавиатуры. В браузере отсутствуют root/SSH/Docker-привилегии.
- **Backend API:** FastAPI; аутентификация, сессии, CSRF, RBAC, политика доступа, валидаторы, Change Plans, ресурсы, события и представление состояния.
- **Task Engine / Worker:** отдельный изолированный Python-процесс для разрешённых операций; durable queue, одноразовый план, подтверждённые execution permits от host-supervisor, typed Broker RPC и сверка прямых/делегированных эффектов (§32/34/36).
- **Service Adapter Contracts:** версионированные интерфейсы `discover`, `observe`, `capabilities`, `validate`, `prepare`, `apply`, `verify`, `reconcile`; адаптер не может обходить Policy Engine, Change Plan, Secrets Broker и ответственный Backend Manager. Контракты и сигнатуры закреплены в разделе 17.
- **SQLite:** постоянный реестр, конфигурационные метаданные, планы, задания, утверждения, события аудита и ссылки на секреты. Для резервирования — согласованные снимки БД через SQLite Online Backup API.
- **Secrets Broker / Vault:** зашифрованное хранилище, системная защита рабочего ключевого материала, строгие Secret References и разрешённое использование без передачи значений браузеру.
- **Independent Update Controller:** отдельный ограниченный host-сервис и **единственный durable admission/maintenance authority** для Worker и обновлений; не зависит от заменяемого Backend (§36.1).
- **Rescue CLI:** автономный локальный механизм восстановления/миграции, работающий без исправного Frontend, Backend или прежней VPS; не обращается к API хостинг-провайдеров и требует ручного протокола изоляции старого Controller перед включением записи.
- **Optional Observer (post-MVP):** только внешняя read-only диагностика; в MVP компонент не устанавливается и не требуется.

### 2.2. Принцип развёртывания

Docker Compose с раздельными Frontend, Backend и Worker, постоянными томами SQLite и Vault; Secrets Broker имеет собственный ограниченный локальный socket и отдельный UID (§31). Ни база, ни Worker не имеют публичных сетевых endpoint. Прямой доступ веб-процесса к Docker Socket и произвольному root-shell запрещён. В MVP привязку к имеющемуся system Nginx/Caddy владелец выполняет вручную: HostOrbit его не изменяет. Собственная управляемая Nginx-публикация возможна только через выделенный независимый instance и свободный listener (§35). Развёртывание не должно нарушать существующие сайты, контейнеры, сетевые службы и при наличии VPN-сервисы.

### 2.3. Технические интерфейсы

- SSH к зарегистрированным VPS через проверенные host fingerprints и индивидуальные ограниченные учётные данные.
- Типизированные адаптеры для заявленных и проверенных сервисов. Базовые сценарии не требуют внешнего API. Необязательная интеграция Remnawave использует поддерживаемый Panel API и не правит генерируемые Panel конфигурации в обход владельца.
- Системные менеджеры Docker, Nginx/Caddy, Firewall, Certbot и ОС — только для явно принятых под управление ресурсов. Внешние провайдерские API и токены хостинга не используются никаким из этих менеджеров.
- SSE или WebSocket для прогресса операций, с переподключением и восстановлением истории из устойчивого хранилища.
- REST API с версионированием, проверкой прав на сервере, идемпотентными идентификаторами запросов для запуска операций и условными обновлениями версий объектов (optimistic concurrency).

## 3. Данные и ответственность Backend Managers

### 3.1. Базовая модель

**VPS:** стабильный ID, хост, роли, теги, группы, SSH host identity, capabilities, версия ОС, Observed status, время проверки. **Service Instance:** ID, VPS, тип, источник управления, владелец конфигурации, порты, зависимости и здоровье. **Topology:** связи VPS, сервисов, доменов, сетевых интерфейсов, публикации и зависимостей; специализированные Entry/Exit/Panel — только при включённой VPN-интеграции. **Template/Policy:** идентификатор, неизменяемая версия, схема, provenance, overrides. **Change Plan:** замороженные цели, версии и хеш содержимого, исходные состояния, Diff, Preflight, риски и approvals. **Job:** ID, parent job, phase, checkpoint, locks, unknown outcome, timestamps, `direct_process_effects` и `delegated_effects`. Состояния и правила карантина едины (§40). **Secret Reference:** ID, scope, purpose, lifecycle, без сохранения значения в реестре. **Backup:** manifest, версия, проверка целостности, защищённый статус и зависимости. **Audit Event:** actor, action, resource, plan/job IDs, outcome, source-time/receive-time, integrity links.

Для каждой управляемой конфигурации раздельно сохраняются **Desired**, **Observed**, **Last Applied** и `last_checked_at`. Значение `Unknown` не заменяется устаревшим `Healthy`.

### 3.2. Единый источник истины

- **SSH/OS Manager** — универсальные операции с поддерживаемыми VPS, системными параметрами и определением возможностей без обязательного внешнего контроллера.
- **Service Adapter Registry** — поддерживаемые схемы и возможности сервисов; неизвестные сервисы остаются в режиме Discovered/Unmanaged.
- **Remnawave Adapter** — необязательная интеграция: Config Profiles, Hosts и другие объекты, которым Panel предоставляет поддерживаемый API.
- **Nginx/Caddy Managers** — только явно принадлежащие HostOrbit файлы/конфигурации; отдельный владелец сертификата и HTTPS-автоматизации.
- **Docker Manager** — контейнеры/Compose-проекты, подтверждённо управляемые HostOrbit; сторонние ресурсы сначала только обнаруживаются.
- **Network/Firewall Manager** — поддерживаемые локальные правила и конфигурации при распознанном backend; учитываются Docker NAT, IPv4/IPv6 и неизвестные внешние фильтры без попыток управлять ими через API хостера.
- **Template Manager** — генерирует Desired и Change Plan, но не применяет инфраструктурные изменения напрямую.
- **Policy Engine** — вычисляет Effective Policy, конфликты, security invariants и разрешённую область целей, но не изменяет сервисы в обход владельца.
- **Operations Manager** — единственный конвейер обычных infrastructure mutating jobs; независимый host Updater использует общую с Worker durable admission/maintenance authority (§36.1), а не самостоятельный обход.
- **Backup Manager** создаёт и защищает архивы; **Storage Registry** учитывает объекты и допустимость очистки; **Recovery Manager** управляет восстановлением.
- **Audit**, **Operation Logs** и **Monitoring** используют согласованные идентификаторы, но не подменяют один источник другим.

### 3.3. Описание режимов владения — только пояснение; transitions §40

`DISCOVERED` — только наблюдение; `PENDING_ADOPTION` — черновик перехода с проверками, без права записи; `PUBLICATION_ONLY` — управление лишь отдельным публикационным объектом, не исходным сервисом; `FULLY_MANAGED` — право менять только перечисленные в scope аспекты; `DETACHED` — снят с управления, файлы и данные сохранены; `DELETED` — удалён только собственный реестр после проверки зависимостей. Переход `DISCOVERED → PENDING_ADOPTION → PUBLICATION_ONLY/FULLY_MANAGED` требует импортированных наблюдений, точного owner/scope, Preflight, Diff, подтверждения и сохранённой исходной контрольной суммы. `PUBLICATION_ONLY → FULLY_MANAGED` — отдельный новый Change Plan. Обратный переход `FULLY_MANAGED → PUBLICATION_ONLY/DETACHED` прекращает операции, но не удаляет чужие файлы и данные. Удаление сервиса, снятие с управления и удаление данных — три отдельные действия.

Инвариант: **один авторитетный владелец на `(resource_id, aspect)`**; для одного ресурса разные аспекты (например, upstream и публикационный vhost) допускают разных владельцев при явной границе. При внешнем drift или неизвестном владельце аспект блокируется для записи; обнаруженная ручная конфигурация не переписывается. `Secret Reference` удаляется только после анализа ссылок; при живых потребителях `409 Conflict`, сначала переключение или отвязка, затем отзыв и удаление; orphan references фиксируются для расследования, а не каскадно стираются.

## 4. Обязательные требования P0 — блокируют выпуск

### P0-1. Единственный активный Controller; ручная изоляция старого экземпляра

**Принятое проектное решение ADR-001 (проверяется испытаниями Этапа 0):** HostOrbit использует single-active режим, без автоматического failover и **без API хостинг-провайдеров**. Восстановление нового Controller начинается исключительно в `READ_ONLY_RECOVERY`: Worker не имеет права запускать изменяющие операции, а расписания и прежние разрешения не возобновляются. Перевод в `ACTIVE` допускается только после **ручной подтверждённой изоляции** старого экземпляра, проверки, что он не может выполнять новые или уже начатые задания, внешней ручной ротации доступа на доступных VPS, quarantine остальных и отдельного подтверждения Owner через локальную Rescue CLI.

**Два допустимых доказательных маршрута:** (а) при доступном старом Controller — остановка и маскирование всех его Worker/Scheduler/system services, подтверждение отсутствия выполняющихся операций и отзыв старых полномочий; при необходимости дополнительно изоляция хоста; (б) при недоступном старом Controller — ручное выключение/сетевое отсоединение хоста через независимую консоль, гипервизор, веб-панель хостера или физический доступ, блокирование самопроизвольного запуска, проверка изоляции владельцем и затем отзыв старых SSH/API-учётных данных на управляемых VPS. **Сам HostOrbit не вызывает API хостера и не требует удаления старой VM.**

Недоступность SSH, DNS-переключение, `Generation ID`, одноразовый тайм-аут, снимок экрана и одна лишь декларация пользователя без проверяемого runbook не являются техническим fencing. HostOrbit не может независимо гарантировать изоляцию чужого хоста без агента или независимого control channel; **доверие к утверждённому владельцем ручному протоколу — явная граница модели безопасности**. Если подтверждение невозможно, остаётся `READ_ONLY_RECOVERY` и доступ к восстановленным данным; возможность изменять VPS блокируется. Ротация старых credentials до активации выполняется только внешним ручным runbook через консоль/SSH администратора управляемой VPS и не является Job HostOrbit. Формальный законный переход, карантин и выполнение сторонних незавершённых процессов — §§31–32. Устройства и сервисы с неотозванными старыми credential references остаются `QUARANTINED`. Подробный алгоритм и тесты — §16, AC-13/40/41/46.

### P0-2. Переносимое восстановление Secrets Vault

**Принятое проектное решение ADR-002 (проверяется независимым восстановлением):** данные Vault шифруются через libsodium XChaCha20-Poly1305 с отдельными случайными nonce на запись; ключ шифрования данных не хранится в SQLite и никогда не передаётся в браузер. Архивы Controller/Vault/VPS шифруются стандартным файловым форматом **age v1 с получателем X25519**, публичный ключ получателя находится на Controller, а приватный recovery identity — **только офлайн у владельца**. В состав архива под шифрованием входят манифест, согласованный снимок SQLite + неизменяемые версии Vault + ВСЕ необходимые версии рабочего DEK, помещённые Broker непосредственно в поток age-шифрования без plaintext DEK на диске. Копии одного лишь host-bound OS wrap недостаточно. Общий barrier, подпись происхождения и независимое восстановление описаны в §33. Rescue CLI в **offline-режиме на доверенной рабочей станции владельца** использует приватную age identity только для расшифровки архива, проверки манифеста и подготовки нового transport-encrypted recovery bundle под **одноразовый публичный ключ нового Controller**. На восстановляемую VPS передаётся только зашифрованный bundle; recovery identity не передаётся туда даже временно. Серверная Rescue CLI извлекает рабочий Vault DEK из защищённого bundle и перезапечатывает под новый OS credential, не получая приватную offline identity. После восстановления архив/ключи проверяются по манифесту и ручному test-restore. При утрате офлайн-ключа восстановление зашифрованного архива **не гарантируется** и не объявляется успешным.

### P0-3. Single Writer / Single Source of Truth

Каждый изменяемый компонент имеет авторитетный источник данных и ответственный Backend Manager. Нельзя одновременно изменять один объект через API внешней системы и прямую запись файлов, а один Nginx vhost — через два независимых менеджера. Шаблоны, визуальные редакторы и групповые действия создают согласованный план и передают применение владельцу ресурса. При неразрешённом конфликте владения доступен только read-only режим.

### P0-4. Надёжная семантика выполнения задач

Выполнение по SSH не гарантирует exactly-once. Нужны долговечные ID заданий, фиксация утверждённого плана, checkpoints, блокировки ресурсов, ограниченная идемпотентность и reconciliation. Если связь оборвалась после передачи команды, результат фиксируется как `Unknown Outcome`, а не `Failed` или `Completed` без доказательств. Повторное выполнение запрещено до сверки; необратимые действия требуют нового плана. При перезапуске Worker недопустимы параллельные исполнители одного задания.

## 5. Уточнения P1 — обязательны до реализации затронутого сценария

**P1-1. Safe Apply сети и SSH.** Опасная операция требует проверенного независимого watchdog/отката на самой VPS или другого доказуемого способа безопасного восстановления. Один обратный SSH-вызов недостаточен. Если условия не подтверждены — блокировка.

**P1-2. Сеть, DNS, TLS и порт 443.** Единый инвентарь слушателей (IP, family, TCP/UDP, bind address, контейнер/процесс, proxy), проверка конфликтов Nginx Stream, HTTP, Docker и, если установлен, Xray либо другого поддерживаемого сервиса. Ручное изменение DNS. Владельцы ACME/сертификатов однозначны; manual DNS-01 не обещает unattended renewal. При наличии VPN-интеграции локальный TLS decoy и публичный REALITY listener рассматриваются как разные компоненты.

**P1-3. RBAC и неизменяемые области разрешений.** Действительное право = роль ∩ закреплённые цели ∩ полномочие операции ∩ текущая политика ∩ действующее утверждение. Динамическая группа не расширяет старое разрешение на изменяющие операции. Любое изменение утверждённого плана делает прежнее подтверждение недействительным.

**P1-4. Retention / Backup / Audit.** Нельзя удалять последнюю проверенную копию, архив с зависимостями, критические checkpoints и нужную для расследования историю. У архива Audit должны сохраняться проверяемые контрольные точки цепочки целостности; удалённый архив опционален. Автоочистка — только собственные временные объекты и согласованные архивы. Прочая системная очистка VPS — вручную.

**P1-5. Совместимость версий и миграции.** Согласованная матрица Frontend, API, Worker, SQLite, Vault, схем шаблонов и подключённых адаптеров (в том числе Remnawave/Xray, когда они используются). Пиннинг проверяемых выпусков и образов по digest; `latest` не используется как воспроизводимый релиз. Автооткат после несовместимой/необратимой миграции БД запрещён. Site rollback — вручную.

**P1-6. Достоверные состояния.** Раздельные статусы для SSH-доступности, процесса, HTTP/TCP/TLS, прикладных API и специализированных проверок (например Bridge/end-to-end VPN при наличии адаптера); источник, время и тип проверки. `Unknown`, `Not Checked`, `Unreachable`, `Degraded` и `Healthy` не смешиваются. Нет автообъявления блокировки провайдера по одному timeout.

## 6. Единый жизненный цикл изменений

1. Пользователь формирует **Draft** с конкретной операцией и целями.
2. Backend проверяет RBAC, ограничения политик, владельца ресурса и совместимость.
3. Система собирает Observed, вычисляет **Preflight**, зависимости, риски и конфликты.
4. Пользователь видит семантический и при необходимости текстовый **Diff**, влияние на VPS, сервисы, веб-публикацию, сетевые зависимости и, если применимо, VPN-маршруты.
5. Выполняется **Backup Gate**: для любого необратимого, destructive, credential rotation, системного обновления или потенциально разрушающего изменения обязательна проверенная актуальная копия восстановимых данных. Для заведомо обратимого низкорискового действия отсутствие новой копии допускается лишь по формальной матрице риска и отражается в плане. Неподдерживаемые операции без допустимого Recovery Plan блокируются.
6. **Approval** закрепляется за хешем/версией плана, конкретными идентификаторами целей и ограничениями. Для критических действий — повторная проверка владельца.
7. Worker через профильный Manager выполняет разрешённые шаги с checkpoints и **глобальной сериализацией всех mutating jobs в MVP**; проверяет полный dependency lock set и актуальный remote baseline непосредственно перед первым изменяющим шагом (§34).
8. Выполняются **Verify / Health Check**. Результат фиксируется независимо для каждой цели: Completed, Failed, Partial, Unknown Outcome либо Recovery Required.
9. Audit хранит инициатора, одобрившего, исполнителя, версии, изменения и ссылки на доказательства; секреты исключены до записи.

**Недопустимо:** тихая подмена списка VPS, автоматический повтор SSH-команды при Unknown Outcome, скрытый downgrade транспорта, автоматическое переключение VPN Exit (если подключён VPN-адаптер) и безусловный откат уже работающих сервисов.

## 8. Граница MVP (первая приемлемая эксплуатационная версия)

### 8.1. В MVP обязательно

- Безопасный инсталлятор, защищённый initial Owner bootstrap, вход, базовые Owner/Admin/Operator/Auditor scopes и минимальные настройки RU/EN.
- Реестр VPS с добавлением по SSH, fingerprint pinning, диагностикой подключения, обнаружением ОС/сервисов и явным режимом владения.
- Универсальное обнаружение ОС, Docker/Compose, Nginx и Caddy (для Caddy в MVP только read-only) и поддерживаемых сервисов; безопасные ручные операции с явно управляемыми объектами без обязательного подключения Remnawave. Remnawave Panel/Node — дополнительная интеграция, когда она включена.
- Базовый Dashboard и страницы VPS/Services с достоверными `last checked`, Healthy/Degraded/Unknown и просмотром журналов.
- Единые Change Plans, Preflight/Diff/Confirm, SQLite Job Queue, Worker, resource locking, Unknown Outcome, Audit Log.
- Секреты через защищённые references, отдельные полномочия и запрет выдачи значений в UI/API.
- Шифрованные резервные копии Controller и поддерживаемых VPS, проверка целостности, защита последней копии; ручной Recovery Test и Rescue CLI как критерий готовности MVP.
- Документированное восстановление Controller на новой VPS через Rescue CLI; право изменять VPS появляется только после подтверждённой ручной изоляции старого Controller и отзыва старых доступов. Без этого — READ_ONLY_RECOVERY; расписания/задания не возобновляются автоматически.
- Минимальные проверки конфликтов портов/владения для поддерживаемых изменяющих действий; опасные сетевые операции, не имеющие Safe Apply, недоступны.
- Набор обязательных интеграционных и отказоустойчивых тестов из раздела 11.

### 8.2. Не входит в MVP (последующие версии)

Расширенные VPN-сценарии и Remnawave-специфичные мастера, полнофункциональный drag-and-drop конструктор топологий, массовые изменяющие операции, сложные динамические Policy Conflicts, автоматическое обновление инфраструктуры по расписанию, расширенная аналитика и прогнозирование, редактирование всех вариантов Firewall/ACME, произвольная миграция неподдерживаемых сервисов, расширенный поиск/command palette, локализованная обучающая библиотека, многоступенчатые интеграции уведомлений и внешние Observer.

**Обязательный универсальный сквозной сценарий MVP:** установить HostOrbit на чистой VPS; добавить другую Linux VPS по SSH; обнаружить Docker/Compose либо Nginx; принять поддерживаемый тестовый ресурс под управление; создать Change Plan с Preflight/Diff/Approval; выполнить безопасное действие; получить Job Timeline/Audit; создать и проверить зашифрованную резервную копию — без установки Remnawave и без настройки VPN.

**Условие:** отсутствие расширенной функции не освобождает MVP от обязательных P0/P1, если затронутый опасный сценарий уже включён. Например, неподдерживаемое изменение Firewall должно быть заблокировано, а не выполнено без Safe Apply.

## 9. Этапы реализации — один действующий Stage Gate

Этапы определяются **только** §40 и экспортом `HostOrbit_Requirements_Registry_v2.3.json`. Ниже — удобочитаемая последовательность, не альтернативный набор тестов.

- **Stage0 — доказательные прототипы:** B01/B02/B03/B04/B09 как приоритетные контракты; сохранение независимых прототипов A01–A05, тесты конфигурации SSH/IPC и валидатор реестра. Без отдельного разрешения владельца любые эти действия остаются документарным планом.
- **Stage1 — Foundation:** ограниченный Auth/RBAC, SQLite+Audit/Outbox, Broker, host admission gate, remote helper и негативные тесты компонентов.
- **Stage2 — вертикальный сценарий:** добавить Ubuntu VPS → обнаружить Docker/изолированный Nginx → сформировать Change Plan → Backup Gate → безопасный изменяющий шаг → verify/audit; AC-28 принимается здесь, не в Stage0/1.
- **Stage3 — выпуск MVP:** все обязательные MVP AC, негативные fault-injection, DR и Release/Recovery evidence.
- **Stage4–5 — post-MVP:** расширенные политики, топологии, групповые операции, автоматизация и необязательные адаптеры после отдельного разрешения; P0/P1 для включённых опасных сценариев обязательны.

`Stage0 PASS` не означает готовности MVP. Релиз запрещён при любом FAIL/NOT_RUN обязательного AC.


## 10. Нефункциональные требования

**NFR-01 — Security.** Least privilege, отсутствует публичный доступ к Worker/SQLite/Vault, нет произвольного shell, защита host key, TLS/CSRF/sessions, запрет секретов в логах, ограничение SSRF и инъекций через строго типизированные операции.  
**NFR-02 — Reliability.** После restart Controller не теряет принятые задания/аудит; неопределённость фиксируется явно; нет blind retry; изменения сериализуются по конфликтующим ресурсам.  
**NFR-03 — Recovery.** Переносимая зашифрованная backup chain, ручной test restore, автономная Rescue CLI, ручная изоляция старого Controller и отзыв его полномочий без API хостера. RPO ≤24 ч — только при реально успешно выполненном суточном резервировании; лабораторный RTO ≤4 ч измеряется при подготовленной recovery VPS, доступном архиве/офлайн-ключе и выполненной ручной изоляции. Эти числа являются условиями отдельного лабораторного теста, **не коммерческим SLA, не гарантией доступности и не обещанием RTO для реальной аварии**; фактический RTO зависит от владельца и доступности независимых средств управления сервером.  
**NFR-04 — Observability.** Структурированные журналы, корреляционные ID, доступные источники/времена наблюдений, безопасные diagnostic bundles с Privacy Review.  
**NFR-05 — UX/Accessibility.** RU/EN с одинаковой функциональностью, клавиатурная доступность, ошибки рядом с полями, подтверждения опасных действий, без неподтверждённых зелёных статусов.  
**NFR-06 — Compatibility.** Версионированные контракты API и схем; миграции с резервной копией; поддерживаемые версии ОС/Docker и подключённых сервисных адаптеров заданы матрицей, тестами и release notes.  
**NFR-07 — Maintainability.** Модульная кодовая база, независимые тесты менеджеров, типизированные контракты, документация API, ADR и единый каталог ошибок.  
**NFR-08 — Capacity.** MVP: Controller ≥2 vCPU, 4 GiB RAM, 40 GiB SSD; ≤25 управляемых VPS, ≤200 Service Instances; одновременные read-only проверки ≤8, изменяющая операция ≤1 на ресурс; p95 чтения API ≤500 мс на лабораторном стенде при отсутствии внешних SSH-вызовов. SQLite WAL только на локальном POSIX-томе, резервирование через Online Backup API; критерии будущей миграции БД в разделе 24.

## 11. Матрица критериев приёмки

Проверки проводятся на изолированной тестовой инфраструктуре (Controller, несколько VPS и тестовые сервисы Docker/Nginx; Remnawave используется в отдельных тестах необязательного адаптера). Для каждого теста сохраняются протокол, сборка, конфигурация, шаги, ожидаемый и фактический результат. Следующие AC являются обязательными, если соответствующая функция включена в релиз; AC-P0 выполняются для MVP.

### 11.1. Обязательные проверки MVP

**AC-01 (P0/Auth).** Чистая установка не предоставляет Owner первому веб-посетителю; локальный bootstrap создаёт Owner, случайный посетитель не может создать администратора.  
**AC-02 (RBAC).** Operator вне назначенного scope получает отказ API на изменение чужой VPS, даже если запрос сконструирован вручную.  
**AC-03 (SSH).** Подмена SSH host fingerprint приводит к блокировке подключения и событию безопасности.  
**AC-04 (Secrets).** Приватные SSH-ключи и API-токены отсутствуют в ответах обычного Web API и в структурированных журналах HostOrbit; разрешённая операция использует Secret Reference. Сырые сторонние stdout/stderr не выдаются в MVP; допускается только явно санкционированный age-зашифрованный Rescue export (§33, §35).  
**AC-05 (Ownership).** Попытка изменить ресурс, принадлежащий внешнему приложению/API (например, Panel-owned), через файл или чужой менеджер блокируется; система объясняет авторитетный источник.  
**AC-06 (Change Plan).** После утверждения изменение хотя бы одной цели, параметра или версии плана аннулирует approval; применение требует нового подтверждения.  
**AC-07 (Queue Recovery).** Перезапуск Worker во время задачи не создаёт параллельный исполнитель и сохраняет её ID/checkpoint.  
**AC-08 (Unknown Outcome).** Разрыв SSH после передачи команды переводит операцию в Unknown Outcome; автоматический повтор запрещён до reconciliation.  
**AC-09 (Locking).** Все mutating jobs MVP глобально сериализованы одним host admission authority с Update Controller. UNKNOWN сохраняет конфликтное dependency closure; карантин всей затронутой VPS и связанных cross-host ресурсов запрещает все пересекающиеся изменения до reconciliation/изоляции. Параллельные read-only проверки разрешены.  
**AC-10 (Audit).** Записываются инициатор, цель, одобрение, план, результат и время; запись не поддаётся обычному редактированию через UI.  
**AC-11 (Backup).** ControllerBackup выпускается только после согласованного barrier SQLite/Vault/key versions/audit-head, структурной проверки ссылок, проверки внешней подписи provenance-envelope и age ciphertext; незавершённые архивы не помечаются COMPLETED, последняя пригодная off-host копия защищена.  
**AC-12 (Vault Recovery).** Offline Rescue CLI на доверенной рабочей станции расшифровывает age-архив с приватной identity владельца и перешифровывает payload на временный публичный ключ нового Controller; Controller восстанавливает DB и Vault DEK без получения самой offline identity.  
**AC-13 (Manual Isolation).** Восстановленный Controller не допускает `ACTIVE` без локальной Owner attestation ручного протокола изоляции старого экземпляра, зафиксированных наблюдений и следующих условий: остановка/изоляция старого Worker, отсутствие опасных исполняющихся операций, отзыв старых credentials на доступных ресурсах, карантин остальных, целостность базы/Vault и локальное повторное подтверждение в Rescue CLI. API хостера не используется.  
**AC-14 (Interrupted Jobs).** После DR все незавершённые задания не запускаются самопроизвольно, расписания остаются на паузе до явного разрешения.  
**AC-15 (Status).** При недоступной проверке интерфейс показывает Unknown/Unreachable с источником и временем, не Healthy.  
**AC-16 (No Safe Apply).** При отсутствии подтверждённого независимого отката опасное изменение Firewall/SSH невозможно выполнить.  
**AC-17 (Port Conflict).** MVP не меняет общий system Nginx и не публикует на занятом чужом listener. HostOrbit-owned Nginx запускается на отдельном свободном address:port/config-prefix; проверяются конфликт IPv4/IPv6, effective config, routing/TLS и здоровье существующих сайтов.  
**AC-18 (Update).** Обновление HostOrbit с несовместимой миграцией SQLite не запускает автоматический откат старой версии поверх новой базы.

### 11.2. Проверки расширенного функционала

**AC-19 [post-MVP] (Groups).** Новая VPS, попавшая в динамическую группу, не добавляется в ранее подтверждённую изменяющую операцию и не наследует прежнее разрешение на изменение.  
**AC-20 [post-MVP] (Policies).** Конфликт групповых политик без согласованного правила разрешения блокирует применение, а источник каждого Effective Value отображается в UI.  
**AC-21 [post-MVP] (Retention).** Dry Run фиксирует точный набор удаляемых объектов; новые файлы после approval не попадают в удаление; связанные backup и журналы не удаляются.  
**AC-22 [post-MVP] (Automation).** Просроченное/отозванное разрешение блокирует изменение; пропущенный approved update не выполняется автоматически после восстановления Controller.  
**AC-23 [post-MVP] (Site Lifecycle).** Обновление статического сайта из одобренного источника не запускает автоматический rollback без отдельного ручного решения.  
**AC-24 [post-MVP] (TLS/DNS).** Выпуск сертификата не меняет DNS автоматически; manual DNS-01 не маркируется как полностью автоматическое продление.  
**AC-25 [post-MVP, optional adapter] (Optional VPN Topology).** При включённом VPN-адаптере неуспех Foreign Exit не приводит к неразрешённому переключению выхода, понижению защиты или direct-route. Без VPN-адаптера тест не требуется.  
**AC-26 [MVP minimum, extended post-MVP] (Localization/A11y).** В RU/EN проходят основные сценарии с клавиатуры; критические предупреждения доступны без опоры только на цвет.  
**AC-27 [post-MVP] (Audit Archive).** Нарушение локальной цепочки Integrity после появления независимой контрольной точки обнаруживается проверкой.  
**AC-28 [MVP] (Onboarding / Vendor independence).** На VPS без VPN и Remnawave доступны регистрация, обнаружение Docker/Compose или Nginx, безопасная ручная операция и аудит. Принятие существующей VPS не перезаписывает сторонний Nginx/Compose-проект без явного Change Plan.  
**AC-29 [MVP in-app; Telegram post-MVP] (Notifications).** Approvals нельзя подтвердить через Telegram; уведомление содержит безопасную ссылку на защищённую Web-сессию.  
**AC-30 [post-MVP] (Search).** Командная палитра не показывает недоступные оператору ресурсы и не позволяет сформировать произвольную shell-команду.  
**AC-31 [post-MVP] (Support Bundle).** Экспорт проходит Privacy Review; приватные ключи, токены и пароли отсутствуют, а пользователь сам разрешает передачу архива.  
**AC-32 [MVP minimal] (Offline Help).** Критическая справка доступна без подключения к внешним сайтам; обновление справки не исполняет код.

## 12. Условия готовности к эксплуатации — единый источник §40

**Единственным нормативным Release Gate** является экспорт проверяемого Requirements Registry §40: обязательные тесты всех MVP требований, состояний и защитных контролей должны иметь реальный наблюдаемый evidence `PASS`. Каталог AC-01…AC-52 и AC-A01…AC-A22/AC-B01…AC-B10 расположен в §§11/39; альтернативного списка «достаточно AC-01…18» нет.

Контроллер не запускает изменяющие операции при нарушении P0, несогласованном recovery, неустойчивой очереди, отсутствии права на execution permit или известной утечке секрета. Текст спецификации без протокола стенда ≠ evidence. Производственные сайты, контейнеры и службы не должны зависеть от доступности Web UI; полная безопасность при компрометации Backend/root или лживой Owner attestation не заявляется.


## 13. Риски и решения на стадии разработки

- **Agentless split-brain:** ADR-001 — только ручная изоляция старого Controller с ограниченными, проверяемыми шагами и отзывом credentials. Не используются API провайдера, автоматическое выключение или удаление VM. При невозможности изоляции остаётся READ_ONLY_RECOVERY. Нельзя обещать математически доказанный fencing при отсутствии внешнего доверенного канала; остаточный риск задокументирован.
- **Многообразие хостовых конфигураций:** на MVP ограничить перечень поддерживаемых ОС, режимов Docker/Nginx и операций; прочее только discover/read-only.
- **Несовместимость версий сервисных адаптеров:** использовать capabilities/version registry; для Remnawave/Xray (если установлены) применять поддерживаемый Panel API и не изменять неизвестные поля или генерируемые файлы.
- **Неполное знание внешней сети:** различать тест из Controller, тест со стороны VPS и внешний Observer; невозможность проверки показывать как Unknown.
- **Рост SQLite и журналов:** предсказуемая ретенция, индексирование и раздельные артефакты, без автоочистки критических данных.
- **Обновление самого HostOrbit:** заранее выделить update controller и совместимые схемы; проверять восстановление до production.

## 14. Статус проектирования

В редакции v2.3 устранены обнаруженные неоднозначности контрактов B01–B10; решения зафиксированы как `DESIGNED / TEST EVIDENCE PENDING`, а не как экспериментально VERIFIED. При контрпримере разрешено контролируемое изменение ADR с трассировкой FR/AC/миграций и повторным тестированием. Код, GitHub, VPS, DNS и внешние системы остаются неизменными.


## 15. Зафиксированная матрица совместимости MVP — ADR-003

Эта таблица является **нормативным диапазоном поддерживаемых окружений**, а не утверждением, что уже созданная реализация прошла тесты. Версии третьих сторон в готовых сборках закрепляются в release manifest и проверяются на указанной комбинации. Новые версии за пределами матрицы обнаруживаются только в режиме чтения до выпуска отдельного обновлённого compatibility manifest.

| Компонент | Поддержка MVP | Режим |
|---|---|---|
| Controller OS | Ubuntu Server 24.04 LTS, amd64, актуальные security updates | Установка и восстановление |
| Управляемая VPS | Ubuntu Server 24.04 LTS, amd64, OpenSSH 9.x из репозиториев Ubuntu | Discover, SSH и разрешённые операции |
| Python backend / Worker | Python 3.13.x внутри закреплённого OCI-образа | Runtime |
| Frontend build | Node.js 24.x LTS, React и TypeScript из lockfile | Только build-time, Node.js не обязателен на VPS |
| Docker Engine | Docker Engine Community 29.x из официального репозитория | Discover; управляемые контейнеры только по capability probe |
| Compose | Docker Compose plugin v2, закреплённый точной версией в манифесте релиза | Discover, явно импортированные проекты |
| Nginx | Ubuntu 24.04 `nginx` 1.24.0 с обновлениями безопасности дистрибутива | Discover и изменение только выделенных HostOrbit конфигураций |
| Caddy | Caddy 2.10.x | В MVP только discovery/read-only; управление post-MVP |
| SQLite | SQLite ≥3.45, локальный том на файловой системе с корректными POSIX locks; WAL | Постоянное хранилище |
| SSH-ключи | Ed25519, обязательная pinning-проверка host key | Доступ к VPS |
| Remnawave / VPN | Без установки в ядре | Post-MVP, опциональный адаптер |
| Recovery isolation | Независимая ручная консоль/гипервизор/панель хостинга либо проверенная локальная остановка старого Controller; никаких API-токенов хостера | Ручная миграция; иначе только READ_ONLY_RECOVERY |

**Совместимость не выводится только из номера версии.** Любой адаптер выполняет `capability probe`: поддерживаемый API, конфигурационное владение, доступные команды, особенности Docker/Firewall и отсутствие конфликтов. Если probe не завершён — `UNSUPPORTED/UNKNOWN`, запись заблокирована. Поддержка дистрибутивных backport-исправлений определяется метаданными пакета, а не сравнением только upstream-номеров. Для прочих ОС, ARM, Podman и альтернативных версий Nginx/Caddy допускаются только inventory/read-only при технической возможности. Наличие API провайдера не влияет на совместимость, HostOrbit не подключается к ним.

**UX-контракт capability detection:** на страницах VPS и сервисов каждое действие отображается с уровнем `MANAGE`, `READ_ONLY` или `UNSUPPORTED` (версия, источник и время проверки). Неподдерживаемые изменения недоступны, указана конкретная причина и поддерживаемая альтернатива, а не скрытая кнопка или автоматическая попытка выполнить действие. Для MVP: Caddy только наблюдение; Firewall/SSH изменение заблокировано; Docker/Compose запись только для явно принятых совместимых проектов; Nginx запись только для HostOrbit-owned объектов.

**Ресурсы Controller для поддерживаемой нагрузки:** 2 vCPU, 4 GiB RAM, 40 GiB SSD и внешний зашифрованный backup destination. Гарантируемая область тестирования MVP: до 25 VPS и 200 сервисных объектов. Вне этих пределов выполнение возможно только как неподтверждённая конфигурация без обещаний SLA.

## 16. Ручная миграция, изоляция и DR — ADR-001

### 16.1. Доверенная модель и состояния

Поддерживается **один активный Controller**, без automatic failover, активного кластера, API хостинг-провайдера или обязательного cloud-аккаунта. Возможна установка на выделенной или совместной VPS. Для совместной VPS аварийная изоляция всего хоста может нарушить другие сервисы, поэтому при невозможности безопасно остановить только HostOrbit предлагается `READ_ONLY_RECOVERY` до решения владельца; HostOrbit никогда самостоятельно не выключает и не удаляет сервер.

Состояния: `UNINITIALIZED`, `ACTIVE`, `QUIESCING`, `READ_ONLY_RECOVERY`, `FENCED_RETIRED`, `RECOVERY_BLOCKED`. Значение `FENCED_RETIRED` фиксируется только по завершении ручного проверяемого протокола, а не по сетевому тайм-ауту. `Generation ID` пригоден для корреляции и аудита, но не способен предотвратить исполнение SSH-команд старым процессом. При восстановлении из бэкапа новый экземпляр всегда запускается `READ_ONLY_RECOVERY` с заблокированными Scheduler и mutating Worker независимо от сохранённого в архиве старого статуса.

**Доверенная граница:** без агента на VPS и без доверенного независимого канала изоляции никакая локальная запись нового Controller не доказывает, что старый экземпляр выключен. Поэтому `ACTIVE` основан на конкретных ручных действиях компетентного Owner и документированном наборе свидетельств. При компрометации Owner, скрытом клоне старой VM или недостоверных свидетельствах безопасность не гарантируется; такой сценарий требует изоляции и полной ротации доступа. Продукт запрещает представлять ручную аттестацию как аппаратно доказанный fencing.

### 16.2. Нормативный протокол ручной изоляции

1. **Подготовка:** новый Controller/Rescue CLI проверяет наличие и целостность локального или SFTP age-архива и подпись выпуска; полноценная расшифровка и проверка SQLite/Vault выполняются через offline-режим Rescue CLI на доверенной рабочей станции и отдельный зашифрованный recovery bundle. Включены только read-only команды. Все расписания и ранее утверждённые mutating permissions остаются отключёнными. Архив не может сам подтвердить свой прежний `ACTIVE`.
2. **Определение исходного экземпляра:** Owner сверяет зафиксированные при установке `controller_id`, исходный SSH host key, известную машину и источник резервной копии. Совпадение одного IP, DNS или имени VPS не является достаточной идентификацией.
3. **Если старый Controller доступен:** на старой машине Owner переводит управление в `QUIESCING`, прекращает выдачу новых задач, дожидается безопасных checkpoint, останавливает и маскирует Worker/Scheduler, проверяет отсутствие активных дочерних процессов/SSH-операций и отключает автозапуск HostOrbit. При неизвестном побочном эффекте сначала выполняется read-only reconciliation либо ручное завершение/изоляция. Если подтверждение остановки невозможно, выбранный маршрут не допускает `ACTIVE`.
4. **Если старый Controller недоступен:** Owner **вручную** изолирует прежнюю машину (выключение питания и блокировка перезапуска, отсоединение виртуального NIC через гипервизор, физическое отсоединение либо эквивалентный проверенный способ через независимую консоль/панель хостера). HostOrbit никогда не отправляет провайдеру управляющие API-запросы. Нужно подтвердить, что канал управления старого экземпляра отсутствует и не возобновится самопроизвольно. Только SSH timeout, отключение DNS, HTTP-ошибка или один скриншот не подходят.
5. **Credentials (внешняя ручная процедура до ACTIVE):** на всех доступных управляемых VPS Owner через независимую административную консоль/доверенный SSH-доступ **вне HostOrbit Jobs и Change Plans** удаляет выделенные старому Controller `authorized_keys`, отзывает его интеграционные API credentials и проверяет новые ограниченные ключи нового Controller; на недоступных VPS флаг `QUARANTINED`, запись там запрещена. Не допускается повторное использование общего root-пароля или ключа старого экземпляра. Ранее открытые удалённые сессии/запущенные задачи должны быть остановлены либо их эффект разрешён read-only сверкой. Изоляция хоста необходима до выдачи новому Controller возможности записи; ротация — дополнительно.
6. **Свидетельства:** Rescue CLI сохраняет `old_controller_id`, способ изоляции, место/консоль или локальные команды, время UTC, исполнителя, минимум два независимых наблюдения состояния с интервалом ≥10 секунд там, где это технически доступно, результаты отключения автозапуска, остановки задач и отзыва старых credentials, `backup_manifest_hash`, `recovery_controller_id`, `QUARANTINED` ресурсы и повторную Owner re-auth. Достоверность стороннего ручного действия подтверждается владельцем; данные протокола не превращаются в автоматическое доказательство отсутствия всех клонов.
7. **Активация:** только после проверки обязательных свидетельств, Vault, базы, разрешений, статуса задач и отдельного подтверждения владельца Rescue CLI разрешает `ACTIVE` для нового экземпляра. Для ресурсов `QUARANTINED` изменяющие действия заблокированы. Все Scheduler-задачи, автоматические разрешения, неизвестные результаты и ранее прерванные операции требуют отдельных решений.
8. **Повторный запуск старого экземпляра:** новый инсталлятор/recovery обязан запускаться read-only, но старый полный snapshot способен восстановить прежний локальный activation record. HostOrbit **не обещает распознать такой скрытый клон**; безопасность уже переведённых ресурсов основана на ручной изоляции и отзыве прежних SSH-доступов. Старые credentials отзываются, а обнаруженная попытка старого экземпляра управлять ресурсами рассматривается как инцидент: останавливаются новые задания, затронутые ресурсы карантинируются, подтверждается повторная изоляция и проводится ротация секретов. Для украденного клона без возможности отключения ограничение обеспечивает отзыв его доступов, а не Generation ID.

**Недопустимое состояние:** Owner не смог проверить изоляцию старой машины или остановку её опасных заданий. В этом случае `READ_ONLY_RECOVERY` сохраняется без временных bypass, `force-active`, эвристики SSH-timeout или автоматических recovery-переходов. Восстановление данных и экспорт разрешены, управление VPS — нет.

### 16.3. Испытания и доказательства

Приёмочный стенд включает доступную старую машину и аварийно недоступную машину, отдельный ручной канал управления старым хостом, новую recovery VPS и управляемые тестовые VPS. Тестируются: успешный ручной перенос, недоступная старая машина без возможности её изолировать, фальшивое подтверждение Owner без обязательных проверок, попытка повторного старта старого Worker, незакрытое `UNKNOWN_OUTCOME`, потеря/смена SSH-ключей и ресурс `QUARANTINED`. Требуется зафиксированное доказательство: без изоляции новый Controller не получает возможность отправлять mutating SSH команды; при подтверждённом ручном протоколе выполняется новый безопасный сквозной сценарий. **Удаление старого сервера не требуется и не выполняется программой.**

**Связь с B01/B04/B09:** старые SSH-ключи не завершают уже принятый запрос Docker daemon. Recovery runbook обязательно проверяет remote ledger и delegated effects на доступных VPS. Если прекращение невозможно доказать, затронутая VPS и dependency closure остаются в карантине; новый Controller не начинает конфликтующую работу и не обновляется, пока есть OPEN UNKNOWN (§§32/34/36). Ручное Owner attestation — обязательное evidence, но не криптографическая гарантия отсутствия скрытого клона.


## 17. Контракты сервисных адаптеров и ownership — ADR-004

Все адаптеры реализуют версионированный контракт `AdapterV1`. Минимальные методы и семантика:

- `discover(target) -> [DiscoveredResource]`: read-only и без побочных эффектов; каждый объект имеет deterministic external identity, provenance и confidence.
- `observe(id) -> ObservedState`: раздельные `status`, `source`, `observed_at`, `received_at`, `capabilities`, `etag`; отсутствие проверки — `UNKNOWN`.
- `capabilities(id) -> Capabilities`: список допустимых операций с версиями и ограничениями. Невозможность проверить — запрет на запись.
- `validate(change, observed, policy) -> ValidationReport`: синтаксис, ownership, конфликты, совместимость, точные эффекты и степень риска.
- `prepare(change) -> PreparedChange`: `plan_hash`, resources, diff, backup requirement, dry-run evidence; никаких изменений в этом шаге.
- `apply(prepared, operation_id) -> OperationReceipt`: только отдельный Worker после approval и locks; `operation_id` используется для deduplication в доступных адаптеру пределах.
- `verify(receipt) -> VerificationReport`: фактическая сверка; HTTP/process up не равнозначен полной health-проверке.
- `reconcile(operation_id, target) -> ReconciliationReport`: только проверки без повторного применения исходной команды.

**В MVP реализуются ровно три вида адаптеров:** Ubuntu OS/SSH с типизированным ограниченным helper для mutating операций, Docker/Compose v2 только для импортированных test projects и выделенный HostOrbit-owned Nginx instance на незанятом listener (§31.2/35.1). Чужой shared Nginx — read-only. Caddy discovery-only. Ни один адаптер не передаёт arbitrary shell из Web UI и не изменяет внешние файлы при отсутствии scope. Для Docker учитываются root-equivalent привилегии: Docker daemon на managed host доступен лишь root-owned typed helper для импортированных проектов; ни FastAPI, ни непривилегированный SSH account не получают docker.sock/group access. Root-компрометация managed host входит в TCB.

Разрешённые действия MVP для `FULLY_MANAGED`: чтение состояния/логов, валидируемый `restart` отдельного контейнера, публикация тестового HostOrbit-owned Nginx instance на отдельном выделенном незанятом listener, запуск согласованной backup операции. Изменение SSH/firewall и системные package upgrades в MVP **read-only/blocked**, если специально не введены после Safe Apply test gate в post-MVP. Необязательная технология (Remnawave, VPN, Certbot, Caddy manage) не входит в эту тройку.

`RESOURCE_OWNER` уникален для ключа `(resource_id, aspect)` и хранит manager, external origin, scope, baseline checksum, version, last applied. `PUBLICATION_ONLY` включает только публикационный аспект. Процедура перехода имеет `DISCOVERED → PENDING_ADOPTION → PUBLICATION_ONLY|FULLY_MANAGED`, затем `FULLY_MANAGED → DETACHED` или `PUBLICATION_ONLY`; destructive purge не является обычным переходом. Каждый переход выполняется отдельным Change Plan и audit. При drift `write=false` до согласованного Diff. Удаление owner-resource не удаляет секреты; ссылки блокируются или явно перепривязываются.

## 18. Очередь задач и reconciliation — ADR-005

### 18.1. Машины состояний — ссылка на единый контракт §40

Управление Plan, Job и Incident использует **только** нормативную state machine §40. `UNKNOWN_OUTCOME` завершает одну remote attempt, а открытый incident хранит неустранённую неопределённость. Старый Job не переписывается успешным статусом при reconciliation; фиксируется новый result-incident, полный audit trail и решение по lock. Отмена возможна лишь в `CANCELLED_SAFE` до эффекта или на явно безопасной checkpoint.

### 18.2. Устойчивость и блокировки — ссылка на §34

В MVP все изменяющие задания глобально сериализованы. Истёкший Worker lease не является доказательством отсутствия remote effect; применяется §32.2 и §34 (durable intent → remote unit → reconciliation). SQLite WAL `synchronous=FULL`, `foreign_keys=ON`, критичные Job/Audit/Outbox transitions в одной транзакции. Remote evidence хранится в durable checkpoint, `UNKNOWN_OUTCOME` блокирует конфликтующие изменения. Terminal job retention 90 дней в БД с последующим архивом, но `plan_execution_ledger` не очищается обычной GC, а неразрешённые инциденты защищены от удаления.

### 18.3. Источник времени и временные блокировки — ссылка на §36.2

Для Controller применяется проверенный host-side TimeHealth (chrony/timesyncd), sample freshness, max error, bounded holdover и monotonic timeout. Нормативные пороги и отказ при clock step определяет §36.2; устаревшие приблизительные значения 5s/30s не являются дополнительными допустимыми разрешениями mutating Apply. Отсутствие достоверного времени блокирует новые mutating операции, но не read-only диагностику.

### 18.4. Протокол сверки после Unknown Outcome

1. Зафиксировать `UNKNOWN_OUTCOME`, отменить зависимые новые действия, запретить слепой retry, заблокировать конфликтующий scope.
2. Сохранить доказательства отправки/получения SSH, command/operation ID (без секретов), время, expected side-effects и последний checkpoint.
3. Выполнить **только read-only** запросы `observe` и `reconcile` с bounded timeout: на одну попытку 30 секунд, максимум три попытки с задержкой; если хост недоступен — оставить Unknown.
4. Сравнить текущий `Observed` с ожидаемым постусловием, `Last Applied`, remote unit receipt и исходным snapshot. Исходная remote attempt остаётся `UNKNOWN_OUTCOME` в истории; отдельный Incident получает `RECONCILED_SUCCEEDED` при подтверждённом постусловии, `RECONCILED_FAILED` при доказанном отсутствии эффекта либо `QUARANTINED` при сохраняющейся неопределённости. Частичное действие явно сохраняется в evidence без выдуманного итогового `SUCCEEDED`.
5. Любое повторное выполнение изменяющей/необратимой операции требует **нового Change Plan**, новой проверки и подтверждения. Для заранее доказанной идемпотентной операции допускается повтор только по отдельной явно зафиксированной политике и при доказанном отсутствии частичного эффекта; для MVP автоматический retry **выключен для всех изменяющих операций**.
6. Завершить incident, снять lock и разрешить новые задачи только после явного подтверждения сверки/Recovery Plan.

**UX-контракт Unknown Outcome:** система сама выполняет до трёх разрешённых read-only попыток и показывает оператору `последний достоверный checkpoint → уже проверенные доказательства → оставшаяся неопределённость → допустимое следующее действие`. Предусмотрена одна безопасная команда повторить **только диагностику**, не исходное изменение. По каждому incident есть ссылка на diff, timeline и протокол сверки. Невозможность подтвердить результат — основание для ручного нового Change Plan, а не навсегда зависший индикатор прогресса.

Идемпотентность HTTP-запроса означает лишь отсутствие второго создания Job при повторе клиентского запроса; она **не обещает** exactly-once исполнения команды на удалённой Linux VPS.

## 19. API, optimistic concurrency и права — ADR-006

### 19.1. Общие контракты

REST API `/api/v1`. JSON Schema/OpenAPI versioned и генерируемые типы React. Идентификаторы ресурсов — UUIDv7/ULID без семантического значения; объект содержит `id`, `revision` (монотонное целое), `observed_at`, `updated_at`. API `GET` возвращает сильный `ETag: "r:<revision>:<hash>"` для управляемых сущностей. Для `PUT/PATCH/DELETE` и критических POST-изменений обязателен `If-Match` с текущим strong ETag; без него `428 Precondition Required`, при несоответствии `412 Precondition Failed` с безопасным описанием diff/reload. Не допускается молчаливая перезапись. Два параллельных подтверждения/изменения одного плана — только один победитель через DB transaction / version CAS.

`POST /change-plans` создаёт черновик; `POST /change-plans/{id}/preflight` вычисляет evidence; `GET /change-plans/{id}/diff`; `POST /change-plans/{id}/approve`; `POST /change-plans/{id}/apply` возвращает `202 Accepted` и Job URL; `GET /jobs/{id}` возвращает authoritative persisted status; SSE `/events` сообщает только уже сохранённые переходы и поддерживает reconnect/replay. `POST /jobs/{id}/reconcile` создаёт разрешённое read-only задание сверки. Схематичные пути здесь являются частью API contract; формат полей документируется OpenAPI без исходного кода в рамках Этапа 0.

При создании Job обязательна `Idempotency-Key` (уникальная непрозрачная строка 16–128 символов), дедупликация по уникальному ключу `(actor_id, action_namespace, idempotency_key)` на 24 часа; `payload_hash` — сравниваемое поле, не часть UNIQUE. Дополнительно одна APPROVED ревизия Change Plan может породить только одно исполнение во всём жизненном цикле, даже после истечения HTTP TTL (§34). Повтор с тем же ключом и другим payload даёт `409 Conflict`; повтор с тем же payload возвращает исходный job/plan. Для API ошибок единая структура `{code,message,correlation_id,details}` без secrets. Авторизация выполняется **до** раскрытия существования ресурса или его метаданных.

Статусы: `400` некорректное тело, `401` нет сессии, `403` нет права, `404` несуществующий/скрытый ресурс, `409` конфликт владения/состояния, `412` stale revision, `423` ресурс заблокирован, `428` нет If-Match, `429` rate limit, `422` схема/валидация, `503` upstream недоступен. Все mutating endpoints требуют HTTPS, защищённой cookie-сессии и CSRF-токена. OpenAPI endpoint на внешнем интерфейсе доступен только авторизованному Owner/Admin.

### 19.2. Аутентификация и rate limiting

Пароли — Argon2id с версионированным параметром сложности, заданным release manifest и допускающим миграцию при входе; серверные сессии, HttpOnly/Secure/SameSite cookies, rotation session ID, блокировка fixation и CSRF. Первоначальный Owner — исключительно через локальную CLI, которая выдаёт одноразовый bootstrap token с TTL 10 минут; публичного `/register-admin` нет. На критических одобрениях требуется re-auth паролем, подтверждение действует 5 минут и относится к `plan_hash`.

Обязательные лимиты, заданные как минимальная защитная конфигурация: не более 5 неудачных login на пару account+IP за 15 минут; не более 20 login-requests на IP за 15 минут; critical approvals не более 3 попыток на пользователя за 15 минут; обычное API — 120 запросов/мин на пользователя и 600/мин на доверенный IP, с отдельным ограничением тяжёлых диагностик до 10/min/user. При превышении `429` и `Retry-After`, с аудитом для критичных событий. Реальные IP принимаются через `Forwarded/X-Forwarded-For` только от явно указанных доверенных reverse proxies; иначе берётся адрес peer.

RBAC: `Owner` все операции; `Admin` только делегированные admin-scopes; `Operator` ограниченный whitelist задач по frozen VPS scope; `Auditor` read-only. Права на секрет определяются только словарём `View Metadata`, `Use`, `Manage`; права `View Secret` нет. `Use` не раскрывает значение через Web API, а `Manage` не даёт произвольный decrypt. Отдельный офлайн-зашифрованный Rescue export не является Web API раскрытием (§31/33). Предусмотрены серверные проверки на уровне endpoint, manager, worker до apply и внутри bounded execution.

## 20. Формат Vault, резервные копии и восстановление — ADR-002

### 20.1. Vault runtime

Секрет — `{secret_id, kind, purpose, owner, allowed_consumers, created_at, version, state, encrypted_blob, nonce, key_version}`; криптографическое значение не попадает в SQLite registry; зашифрованные blobs физически лежат в отдельном защищённом Vault storage. AEAD — libsodium XChaCha20-Poly1305, ключ 256 бит, nonce 192 бита из CSPRNG, AAD включает `secret_id`, `version`, `kind`, `purpose`, `owner_id`, `allowed_consumers_digest`, `state` и `policy_revision` канонического broker-authoritative metadata. Изменения ACL/state не допускаются прямой правкой SQLite; Broker независимо сверяет protected policy (§33). Изменение AAD или повреждение ciphertext приводит к отказу дешифрования. Ключ Vault (DEK) хранится вне базы и доступен только Secrets Broker. Локальный wrapping key размещается в защищённом OS credential store/файле с mode 0600, root-owned, без публичного bind mount; на host с root compromise секретность не гарантируется (явная граница Threat Model). Нельзя давать браузеру endpoint для произвольного decrypt/export.

### 20.2. Encrypted backup v1

Контейнер архива: `hostorbit-backup-v1.age` по стандарту age v1/X25519; внутри аутентифицированного ciphertext лежат `manifest.json`, `controller.sqlite` (снимок Online Backup API), `vault/`, `vault/dek-versions.cbor`, `configs/`, `audit-head.json`, `versions.json` и checksums. Manifest содержит `schema_version`, `backup_id`, `created_at_utc`, `source_controller_id`, `generation`, `release_digest`, `sqlite_schema`, `vault_format`, перечень объектов с SHA-256, правила retention, признак завершённости и список критичных ссылок. Перед шифрованием всё собирается в безопасный архив без абсолютных путей, symlinks, hardlinks и path traversal. После создания age-файл и внешний подписанный provenance-envelope проверяются по доверенному офлайн-публичному ключу Controller signing identity и опубликованной контрольной точке; размер/хеш оболочки сами по себе не удостоверяют источник; заявлять `RESTORE_VERIFIED` можно только после ручного test restore, проверка контрольной суммы сама по себе означает только `INTEGRITY_VERIFIED`.

**Recovery key**: одна выделенная offline age X25519 identity владельца, публичная часть на Controller. Приватная identity создаётся локально и копируется в минимум две независимые физические офлайн-копии, каждая проверяется владельцем; не попадает на сервер, в Git, веб-формы, email, Telegram, Task Queue, логи или support bundle. Приватная identity вводится исключительно в offline-режиме Rescue CLI на доверенной рабочей станции владельца: локальная расшифровка, проверка манифеста, повторное шифрование содержимого для нового Controller по одноразовому публичному получателю. На новую VPS доставляется только ciphertext; серверная Rescue CLI расшифровывает новым транспортным ключом и перезапечатывает runtime DEK под новый OS credential. Identity никогда не передаётся на управляемые VPS или в Controller, даже в оперативную память.

### 20.3. Операционный регламент офлайн-ключа восстановления

При первичной установке recovery identity генерируется на принадлежащем владельцу доверенном офлайн-устройстве; Controller получает **только age public recipient**. Две независимые физические копии приватной identity сохраняются в раздельных защищённых местах (например, два офлайн-носителя), с доступом только Owner и без облачной синхронизации. Владелец обязан проверить читаемость каждой копии и соответствие публичному recipient через тестовый зашифрованный объект, а затем выполнить **ручной test-restore** резервной копии в изолированную среду. До выполнения теста статус DR — `NOT_READY`, даже если архив создан успешно. Инструкция включает защиту от утери/повреждения носителя и передачу в доверенном административном контуре.

Повторная проверка обеих копий и изолированное восстановление — не реже одного раза в 90 дней, а также после обновления формата Vault, смены ключа или контроллера. **Ротация identity** выполняется только вручную: создать новую офлайн-пару и две проверенные копии, добавить новый публичный recipient для новых архивов, перешифровать или повторно сформировать все архивы, которые нужно сохранить, проверить их ручным восстановлением, только после этого снять старый recipient. Нельзя удалять последнюю доступную старую копию до проверки всех защищённых бэкапов. Потеря всех приватных копий делает прежние age-архивы невосстановимыми, если не существует другого заранее проверенного получателя; HostOrbit показывает `RECOVERY_KEY_LOST / DR_NOT_READY` и не обещает обхода криптографии.

Offline-режим Rescue CLI на доверенной локальной рабочей станции принимает identity только из офлайн-носителя или прямого ввода, не помещает её в аргументы процесса, shell history, рабочие файлы, журналы или swap. Публичный recovery recipient допускается на Controller. Для переноса создаётся одноразовая пара X25519/age-получателя непосредственно на восстановляемой VPS; её публичная часть сверяется владельцем по независимому каналу, а приватная остаётся у новой серверной Rescue CLI. Передаваемый bundle шифруется на рабочей станции для этой публичной части и сохраняет контрольные суммы, ID и срок использования. Приватная identity владельца **не попадает на Controller ни постоянно, ни временно**. Очистка временных данных, ограничение прав и отключение офлайн-носителя обязательны. Весь процесс отражается в runbook и проверяется негативными тестами.

### 20.4. Backup и retention defaults

Controller: шифрованный backup каждые 24 часа в 02:00 UTC и обязательный pre-change для критичного обновления/миграции; хранение `7 daily + 4 weekly + 3 monthly`. Минимум одна проверенная копия хранится вне исходной Controller VPS на SFTP, независимом от её потери. При отсутствии внешнего archive destination система маркирует DR `NOT_READY` и запрещает выдавать статус полноценной готовности восстановления. Копии VPS — по отдельно утверждённой политике ресурса. **Последняя проверенная копия** не удаляется никогда, пока не появится другая проверенная независимая копия; archive dependencies имеют приоритет над retention.

Ручной test restore в изолированной среде — до объявления DR Ready при первом вводе ключа, перед MVP release, после смены формата/ключей, после восстановления и по расписанию напоминания не реже одного раза в 90 дней. Автоматически выполняются только проверки целостности и полноты манифеста, не фактическая расшифровка/restore.

## 21. Threat Model — ADR-007

| Угроза | Актив / возможное воздействие | Обязательная защита | Проверка |
|---|---|---|---|
| Компрометация Frontend / XSS | Кража пользовательской сессии, запуск API действий | CSP, HttpOnly, CSRF, short-lived reauth, RBAC, no secrets API | Попытки XSS/CSRF, direct API и approval replay |
| Компрометация FastAPI | Эскалация в Worker/Docker | отдельные процессы и UID, не монтировать Docker socket, ограниченный broker, deny-by-default | Backend container не может достичь Docker/socket/root |
| Компрометация Worker | SSH и container privilege, распространение на VPS | отдельные учётные данные и scopes, штатные structured actions, logs redaction, privileged broker isolation | Попытка неразрешённой команды/ресурса |
| Кража backup/SFTP | Доступ к реестру/Vault/данным | age X25519 encryption, offline private key, per-archive manifest | Копия не расшифровывается без offline identity |
| Split-brain Controller | Два набора команд к VPS | ручная изоляция прежнего Controller, отзыв его credentials, fail-closed и карантин | AC-13/14/40/41/46, стенд с повторным запуском старого экземпляра |
| Supply-chain подмена | Малварь в контейнере или update manifest | pinned OCI digest, Ed25519 signature trusted root, SBOM, проверка до apply | Подмена digest/signature блокируется |
| SSH MITM | Подмена управляемой VPS | pinning host key с отдельным подтверждением замены | AC-03 |
| SSRF/инъекции | Скан internal network, shell execution | только зарегистрированные targets, strict URL/arg schemas, без arbitrary shell | Негативные API-тесты |
| Удаление/подмена Audit | Скрытие действий | append-only на уровне API, hash chain, опциональные внешние checkpoints | AC-10/27 |
| Компрометация root на Controller | Чтение runtime secrets и credentials | hardening ОС, аудит, ограниченные права, backup/offline key | Явно указан остаточный риск; не обещать невозможного |

Ни одна мера не предполагает защиту от владельца root+provider с полным контролем над инфраструктурой. В `Support Bundle` данные подвергаются нормализации и запрету plaintext secrets ещё до формирования архива.

**Нормативная граница Backend-in-TCB:** FastAPI с правом писать authoritative approval/plan в SQLite остаётся доверенным. При RCE в Backend система НЕ гарантирует независимую криптографическую достоверность approval; отдельные Broker-ACL, peer credentials и host admission gate ограничивают доступ и классы эффектов, но не заменяют внешний независимый authorizer. Root/managed Docker daemon и сознательно ложная Owner attestation не входят в полную защитную гарантию. В negative tests заявлять защищёнными можно только те границы, которые реально проверены.


## 22. Независимые обновления — ADR-008

### 22.1. Выпуски и trust chain

Сервер выпуска создаёт `release.json` с `release_id`, `build_time`, `frontend/backend/worker/update-controller OCI digests`, `sqlite_schema_from/to`, `vault_format`, `migration_reversible` и `min_compatible_controller`; manifest подписывается Ed25519-ключом издателя. Публичный trust root закреплён в офлайн устанавливаемом bootstrap/Rescue CLI и не может заменяться скачанным manifest. SBOM и checksums поставляются вместе с выпуском. Если подпись, checksum, совместимость или pre-update backup не подтверждены — обновление блокируется. Удалённая документация не исполняет код.

### 22.2. Обновление самого Updater

Upgrader использует A/B host executable и подписанный manifest, но **исключительное право допуска выдаёт стабильный bootstrap supervisor** согласно §36.1. Журнал A/B и state recovery обновляются независимо от заменяемой SQLite; self-update и application update имеют разные планы и один shared maintenance gate. Этот раздел не определяет альтернативной state machine.

### 22.3. Минимальные привилегии Update Controller

Отдельный локальный сервис не публикует TCP/HTTP endpoint и принимает запросы только через аутентифицированный локальный IPC с доступом у выделенных административных UID; основной FastAPI-контейнер не получает root, Docker Socket или прямой write-доступ к исполняемым слотам. Изменяющие команды ограничены подписанными release manifests, допустимыми целевыми путями, whitelist операциям со слотами и проверенной последовательностью. Права на файлы и журналы, systemd sandboxing, запрет произвольных аргументов/скриптов, аудит каждого обновления и отдельные тесты компрометации Backend являются обязательными. Для обновления собственного исполняемого файла используются только атомарные A/B слоты; небезопасная самостоятельная выдача новых привилегий не разрешена.

### 22.4. Controller update workflow

Единственный порядок и аварийные переходы описаны в §36.1: signed compatible release → off-host Backup Gate → durable QUIESCING and drain → MAINTENANCE permit → stage/migrate/smoke → RESUMING/NORMAL или RECOVERY_HOLD. Нет автоматического несовместимого downgrade/rollback SQLite, нет пересечения с обычным Worker mutation или неизвестным remote effect. Выпуск без отрицательного теста B09 запрещён.



## 23. Протокол публикации, сети и Safe Apply — ADR-009

Для любого `listener` инвентаризуются `{protocol, address_family, bind_addr, port, owner_process, docker_network, proxy_target, exposure}`. Проверяются как wildcard адреса `0.0.0.0` и `[::]`, так и локальные привязки, TCP и UDP отдельно; Docker `host` network наследует портовые конфликты ОС. Локальная доступность порта и реальная внешняя доступность — разные факты; cloud firewall может быть неизвестен. Existing third-party sites, Nginx Stream и сертификаты не перезаписываются при публикации HostOrbit. DNS только руками владельца. В MVP Nginx publication доступна лишь для отдельного свободного socket/vhost без существующего wildcard-conflict; публичный порт 443 не захватывается установщиком.

Для любых меняющих SSH/firewall операций после MVP требуется `SafeApplyProof`: snapshot правил, локальный независимый rollback watchdog, заранее проверенная длительность rollback 120 секунд, новая проверочная SSH-сессия с другого соединения и Owner confirmation после восстановления доступа. При потере доступа watchdog возвращает **только управляемый фрагмент** правил. Непроверенный backend, Docker NAT/ufw конфликт, отсутствие второго канала или отсутствие доказанного rollback → `UNSUPPORTED/blocked`. В MVP таких изменяющих операций вообще нет: Network Center показывает только чтение.

## 24. Хранение, производительность и триггеры будущего масштабирования — ADR-010

### 24.1. Установленные политики по умолчанию

| Тип данных | Удержание | Неизменяемые исключения |
|---|---|---|
| Controller Backup | 7 daily + 4 weekly + 3 monthly | Последняя проверенная независимая и pinned recovery backups |
| VPS Backup | Отдельная политика VPS; default 7 daily + 4 weekly | Последняя проверенная; активные зависимости |
| Audit events | 365 дней локально; 30-дневные сегменты hash chain | Legal/incident hold; anchors и evidence archive |
| Job metadata | 90 дней после verified terminal | UNKNOWN/RECOVERY_REQUIRED не удалять до ручного решения |
| Operation logs | 30 дней | Неудаляемые при активном расследовании |
| Monitoring raw | 7 дней | Не включать в критические журналы |
| Monitoring aggregates | 90 дней | Анонимизация при экспорте |
| Support Bundles | 7 дней | Только свои зарегистрированные файлы |
| Temp downloads | 24 часа после подтверждённого завершения | Активные job/release artifacts защищены |

Retention выполняется по Dry Run с exact object set, повторной проверкой перед delete и журналом; Audit hash chain разбивается на блоки с пронумерованными signed checkpoints и сохранением `previous_segment_hash` при архивации. Внешние зашифрованные Audit checkpoints — опциональны; без них гарантируется только обнаружение локальных непреднамеренных изменений в пределах модели доступа, не защита от root-злоумышленника. Автоочистка касается только собственных, зарегистрированных объектов. `docker system prune` и произвольный `rm -rf` запрещены.

### 24.2. SQLite и критерии перехода

SQLite WAL используется только на локальном томе; WAL/SHM не копируются напрямую для backup. Индексы: `resource_id`, `job status+updated_at`, `audit resource+timestamp`, `events correlation_id`, `plan hash` и `retention timestamp`. Периодический WAL checkpoint и VACUUM проводятся только при проверенной возможности остановки writer и достаточном диске. Это требования к реализации, а не обещание безопасности без тестов.

**Post-MVP PostgreSQL capacity review:** p95 read API >500мс, SQLite ≥8 GiB или рост выше 25 VPS / 200 services / 100000 events/month инициируют только review с метриками (§37), **не автоматическое решение** о PostgreSQL. Переход возможен после доказанного SQLite bottleneck и отдельного ADR; автоматической миграции нет. Формат будущего переноса — экспорт строго типизированных таблиц и immutable evidence с проверкой контрольных сумм и отдельным Change Plan. Само решение о переходе на PostgreSQL уже принято как условное post-MVP, открытого вопроса для MVP нет. **Путь переноса**: завершить или перевести в Unknown активные jobs, остановить запись, сделать проверенный encrypted backup SQLite и Audit anchors, экспортировать версионированную каноническую схему с UUID/ULID, проверкой строк и ссылок, загрузить PostgreSQL в изоляции, сравнить количество записей, контрольные суммы и referential integrity, затем выполнить отдельное подтверждённое переключение единственного writer. Никакого dual-write; откат на SQLite допустим только до первой успешной новой записи PostgreSQL, затем требуется отдельный Recovery Plan. Эта операция и PostgreSQL adapter не входят в MVP.

## 25. Разметка функционального объёма

Для каждой функции из §7 и теста из §§11/39 нормативные `release_inclusion` (MVP / POST / OPTIONAL / MVP_BLOCKED), `stage` (Stage0–Stage5), `owner`, `assertions` и `evidence_path` находятся **в одном** Requirements Registry (§40 и сопровождающий JSON). Названия вкладок в UI не означают поддержку изменяющей операции. Текущие ограничения MVP: Docker — только импортированные поддерживаемые проекты; Nginx — выделенный instance/listener; Caddy и общий Nginx — discovery/read-only; Firewall/SSH changes — BLOCKED; Remnawave/VPN — optional post-MVP.


## 26. Приёмочный стенд и дополнительные тесты

### 26.1. Минимальный стенд

Требуется минимум **2 экземпляра Controller** (original + recovery) и **3 управляемые Ubuntu 24.04 VPS** (Docker/Compose, Nginx, mixed/unsupported), отдельное SFTP backup-хранилище, **ручной независимый канал изоляции старого Controller** (локальный гипервизор/консоль VM/управление питанием через человеческий интерфейс, без автоматизированного API) и fault-injection тестовый стенд. Контроллеры получают независимые credentials. Тесты включают старую доступную машину, полностью недоступный сервер, повторное включение старого Worker, ложное подтверждение изоляции, запоздавший SSH side-effect, недоступную VPS и восстановление из snapshot. При возможности наблюдения old host off и запрета автозапуска журналируются независимо; отсутствие достаточного подтверждения оставляет READ_ONLY. Подмены SSH fingerprints, потери сети, переполнения диска, одновременные requests и аварийные отключения вводятся управляемо.

На Controller используется chrony или systemd-timesyncd, проверки рассинхронизации времени и блокировки изменяющих задач включены в тесты; все события в UTC. Ни на тестовом стенде, ни в production **не требуется аккаунт, API-токен или управляющий API хостинга**.

Сценарии нагрузки: 25 зарегистрированных VPS, 200 Service Instances, **4 параллельных read-only SSH-соединения**, 2 конкурирующих mutating requests (выполняется только один), 30-дневный реалистичный Audit/Job dataset, 100 конкурентных API read запросов, 10 циклов Worker kill/restart; 30 минут warmup + 8 часов soak, p95 API чтения ≤500 мс при зафиксированных endpoint/hardware и штатной нагрузке. Error rate считает только неожиданные 5xx/timeout; ожидаемые 4xx исключены. Полная методика §37. RPO ≤24 ч при удачном суточном backup и **только лабораторный** RTO ≤4 ч при заранее подготовленной recovery VPS, наличии офлайн-ключа и завершённой ручной изоляции; числовое значение не является SLA в реальной аварии.

### 26.2. Дополнительные обязательные AC MVP

**AC-33 [MVP].** На неподдерживаемом хосте Adapter возвращает `UNSUPPORTED` для изменяющего действия; read-only описание не выдаётся за Fully Managed.

**AC-34 [MVP].** HostOrbit-owned Nginx instance использует отдельный listener и config namespace; существующий сторонний Nginx master не перезагружается, его vhost сохраняют маршрутизацию/TLS/health. Сравнение байтов файлов дополняется функциональными проверками routing и портов (§35).

**AC-35 [MVP].** Попытка удалить Secret Reference при живой ссылке от resource/job/backup блокируется `409`; удаление resource не очищает секрет каскадно.

**AC-36 [MVP].** Два одновременных изменения по stale strong ETag приводят к одному success и другому `412`; без `If-Match` — `428`.

**AC-37 [MVP].** Повтор `Idempotency-Key` создаёт один Job, а тот же key с другим payload — `409`. Remote SSH effect при `UNKNOWN_OUTCOME` автоматически не повторяется.

**AC-38 [MVP].** Повреждённый архив и неверная age identity отвергаются; private recovery key используется исключительно offline Rescue CLI на доверенной рабочей станции и не передаётся на VPS ни временно, ни постоянно. При восстановлении новая VPS получает лишь ciphertext, зашифрованный на одноразовый публичный ключ получателя; test-restore DB+Vault успешен, логи/аргументы/env не содержат ключей.

**AC-39 [MVP].** Подмена подписи/digest update manifest блокирует обновление; сбой обновления самого Update Controller откатывает только его A/B слот, а не SQLite.

**AC-40 [MVP].** При недоступном старом Controller и отсутствии ручного доказательного протокола изоляции новый экземпляр остаётся `READ_ONLY_RECOVERY`; отсутствие обязательных независимых наблюдений/записей не позволяет включить `ACTIVE`; умышленно ложное Owner attestation или скрытый полный snapshot не обнаруживаются гарантированно. Тест без API провайдера.

**AC-41 [MVP].** Штатный перенос с доступного старого Controller допускает ручную остановку/mask Worker и Scheduler и отзыв старых credentials без выключения VPS с посторонними сервисами. Если невозможно подтвердить прекращение опасных операций или изолировать недоступный старый экземпляр, только `READ_ONLY_RECOVERY`, без `force active` и удаления VPS.

**AC-42 [MVP].** Rate limits срабатывают независимо для login, approval и API; spoofed X-Forwarded-For из недоверенного peer не меняет identity источника.

**AC-43 [MVP].** Установщик при занятом публичном порту 443 не заменяет чужой listener/Nginx Stream и предлагает непубличный localhost endpoint, не портит сайты.

**AC-44 [MVP].** Read-only restore после потери Controller сохраняет прежние jobs/schedules выключенными; каждый ресурс с неотозванными old-controller credentials помечен QUARANTINED до проверки и ротации.

**AC-45 [MVP].** На стенде 25 VPS/200 services соблюдаются оговорённые ограничения concurrency и p95 API; журнал не содержит паролей и приватных SSH-ключей даже при ошибках.

**AC-46 [MVP].** Подтверждённая ручная изоляция старого Controller + отзыв старых credentials допускают отдельную активацию новой VPS. При повторном запуске старого Worker с отозванными SSH credentials он не может выполнять mutating операции на доступных тестовых VPS; недоступные при ротации VPS остаются `QUARANTINED`.

**AC-47 [MVP].** Оба независимых офлайн-носителя recovery identity проходят ручную проверку и test-restore с локальной offline-дешифровкой; потеря/неверный ключ приводит к `DR_NOT_READY`, процедура ротации не удаляет прежний доступ до проверки новых зашифрованных архивов. На новую VPS передаётся только зашифрованный recovery bundle.

**AC-48 [MVP].** При рассинхронизации локальных часов более 5 секунд или отсутствии надёжной синхронизации Scheduler и новые mutating jobs блокируются; восстановление синхронизации не запускает старый SSH side-effect автоматически.

**AC-49 [MVP].** UI и API честно маркируют неподдерживаемые действия как `READ_ONLY/UNSUPPORTED`, включая Caddy manage и Firewall/SSH changes в MVP; отсутствует скрытый обход запрета через прямой API.

**AC-50 [MVP].** Компрометированный Backend не может отправить произвольный shell в Independent Update Controller, подменить подписанный выпуск, записать A/B slots напрямую или получить доступ к Docker Socket вне разрешённого брокера.

**AC-51 [MVP].** Установка, штатное управление, тест миграции и восстановление не требуют API хостера, его credentials или вызова облачного control API. На тестовом стенде с заблокированными внешними API эти сценарии сохраняют заявленную функциональность при подтверждённой ручной изоляции.

**AC-52 [MVP].** UX для `UNKNOWN_OUTCOME` показывает последний checkpoint, результаты максимум трёх read-only сверок и следующий допустимый шаг, не предлагая автоматический повтор mutating команды; тест с обрывом SSH не создаёт второй побочный эффект.

**Релизный gate:** AC-01…AC-18, AC-28, минимальные AC-26/29/32 и AC-33…AC-52 обязательны для MVP. AC-19…AC-25, AC-27, AC-30/31 расширяются при включении соответствующего post-MVP функционала. Это исключает двусмысленность при приёмке.

## 29. Неизменяемые решения владельца

HostOrbit остаётся универсальным; Remnawave/VPN — optional post-MVP. **Ни один Backend Manager не подключается к API хостинг-провайдера.** Fencing старого Controller выполняется вручную владельцем; при недостаточном подтверждении новый экземпляр остаётся в READ_ONLY_RECOVERY, проблемные VPS — QUARANTINED. Офлайн-приватная recovery identity остаётся вне VPS. Изменения кода/репозитория/серверов не выполняются без отдельного разрешения.

## 31. Архитектурная граница доверия, доступ и привилегии — A04/A07/A14/A18

### 31.1. Trusted Computing Base и реально работающий Broker IPC — A04/B10

**Выбранная модель доверия:** Backend, SQLite/approval authority, Worker, Secrets/Execution Broker, host updater/supervisor, host root и remote root helper входят в TCB. Вредоносный Backend с разрешением писать Plan/Approval в БД может фабриковать внешне допустимые approvals; система не обещает независимой защиты от Backend RCE. Worker и Backend не получают plaintext DEK через API, и не имеют прямого доступа к root/docker.sock. Брокер разрешает только типизированные вызовы и сверяет собственный protected ACL/nonce/TTL; отрицательные тесты различают arbitrary shell и злоупотребление допустимыми операциями.

**Единственный доверенный путь:** браузер → FastAPI → committed Plan/Job/Audit/Outbox в SQLite → Worker → host `AdmissionGate` (§36) и scoped execution permit → Broker RPC → проверенный SSH host fingerprint → remote restricted helper → process/delegated-effect envelope (§32). Никакие сырые credentials не передаются браузеру или произвольному Worker subprocess.

**Локальные UID и монтирование:**

| Процесс | UID/группа и доступ | Запрет |
|---|---|---|
| Frontend | `ho-web`, только статические assets | DB, Vault, Broker socket, host updater, docker.sock |
| FastAPI | `ho-api`, scoped SQLite/HTTPS session | Broker socket mount, DEK, Docker socket, root |
| Worker | `ho-worker` + supplementary group `ho-broker-rpc`, Broker IPC | plaintext vault, root host, docker.sock |
| Broker | `ho-broker`, socket group `ho-broker-rpc`; Vault/ACL/SSH key handling | публичный endpoint, generic decrypt/exec |
| Updater / host gate | root-owned host service, защищённый admission journal | web endpoint, неавторизованные проекты/пути |
| Remote helper | root-owned ELF/типизированная программа, запускается только через точный sudoers | unrestricted shell, docker-group access у remote account |

**Нормативная IPC конфигурация:** только AF_UNIX socket по `/run/hostorbit/broker/broker.sock`, каталог `0710 root:ho-broker-rpc` либо аналогичная проверенная ACL конфигурация, сокет `0660 ho-broker:ho-broker-rpc`, отдельно выделенная GID. Socket bind-mount только в namespace Worker и Broker; фиксированный сопоставленный host/container UID/GID, никаких неявных user-namespace maps. Backend не состоит в группе и не монтирует путь. Брокер читает `SO_PEERCRED` (PID/UID/GID), проверяет разрешённую роль именно host-authoritative peer, а не JSON `consumer_kind`. Параметры RPC (`operation_id`, `plan_digest`, `resource`, `secret_ref`, `scope_digest`, `permit`, `nonce`, `expiry <=60s`) проверяются независимо с protected Broker ACL. Нельзя изменить identity подстановкой JSON. Socket permissions без проверки peer credentials недостаточны. Во время установки проверяется реальный RPC из Worker и `EACCES` из API/неразрешённого UID.

**Возможности Broker:** `use_for_scoped_ssh`, `use_for_registered_adapter`, `rotate_scoped`, `backup_stream_to_age`. Нет `decrypt(any)` или generic command. Использование секрета требует актуального Broker-policy + конкретного execution permit от Host Gate; при REVOKED/QUARANTINED выдача блокируется. Даже при честном Backend отдельный Broker уменьшает blast radius, но полный root compromise остаётся вне гарантии.

### 31.2. Воспроизводимый restricted SSH service account — A07/B08

На поддерживаемой Ubuntu 24.04 администратор **вручную** устанавливает подписанный `hostorbit-typed-helper` и `hostorbit-ssh-gateway`, привязанные к root-owned неизменяемому пути `/usr/local/libexec/hostorbit/`. Удалённый аккаунт `hostorbit-svc` с действительным системным login shell **`/bin/sh`**, необходимым для OpenSSH forced command; пароль заблокирован, самостоятельный вход по паролю, интерактивная shell-сессия, PTY и forwarding запрещены. **Не использовать `/usr/sbin/nologin` или `/bin/false` как универсальный shell для этого профиля**: это может нарушить forced-command в зависимости от конфигурации sshd.

Серверная `Match User hostorbit-svc` политика `sshd` включает `ForceCommand /usr/local/libexec/hostorbit/ssh-gateway`, `DisableForwarding yes`, `PermitTTY no`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitUserRC no`, `X11Forwarding no`, `AllowAgentForwarding no`, `AllowTcpForwarding no`, `PermitTunnel no`, `PubkeyAuthentication yes` и `AuthorizedKeysFile /etc/ssh/authorized_keys/hostorbit-svc`. В `authorized_keys` каждый ключ дополнительно ограничен `restrict,command="/usr/local/libexec/hostorbit/ssh-gateway"`; серверная Match-политика обязательна даже при неверной/отсутствующей опции ключа. Path `authorized_keys`, все родительские каталоги, wrapper/helper и sudoers — root-owned, не доступны для записи `hostorbit-svc`. Запрет произвольных environment-переменных, user rc и SSH_ORIGINAL_COMMAND как интерпретируемой команды обязателен.

Account **не состоит** в группах `sudo` и `docker`; это не исключает **одной точной** sudoers-capability: `hostorbit-svc ALL=(root) NOPASSWD: /usr/local/libexec/hostorbit/typed-helper ""`, где `""` запрещает аргументы командной строки. Передача строго канонизированного ограниченного JSON происходит только через stdin; gateway не вызывает shell `-c`, eval, пользовательские binary paths или argv-forwarding. `sudo` использует `env_reset`, фиксированный `secure_path`; helper перепроверяет whitelist operation/target/version, захваченные baseline и path safety. Docker daemon остаётся root-equivalent; доступ только у typed helper, `hostorbit-svc` не получает docker.sock. Первичный SSH fingerprint владелец независимо проверяет перед pinning.

**Negative tests на реальной чистой Ubuntu:** разрешённый typed request работает; интерактивный shell, PTY, forwarding, env override, command-substitution, path traversal, замена `authorized_keys`, wrapper и parent dir запрещены. Учётная запись, имеющая shell `/bin/sh`, не означает, что пользователь получает интерактивный доступ из-за forced-command restrictions.

### 31.3. Сессии, утверждения и SSRF

Owner получает password-only auth в MVP **с явным остаточным риском отсутствия MFA**: Argon2id, защищённая server-side cookie session с idle TTL 30 минут и absolute TTL 12 часов; критическое подтверждение — повторный ввод пароля в последние 5 минут, привязанный к plan hash, это **не** независимый four-eyes approval. Смена пароля или роли отзывает все затронутые сессии и tokens; Owner recovery — только локальная root CLI с отдельным событием аудита, сменой session signing keys при компрометации, принудительным завершением сессий. Пароли: минимум 14 символов либо passphrase от 4 случайных слов; проверка известных утечек только при безопасном доступе к локальному списку, без передачи пароля сторонним сайтам. WebAuthn/TOTP — будущая возможность, не требование MVP.

**Сетевые адреса** для Worker probe и adapter-connect: явные owner-approved CIDR/ports/hostname + capability, роль на регистрацию. Запрещены loopback/link-local/metadata адреса Controller и произвольные локальные UNIX endpoints по умолчанию; RFC1918 разрешён в явных scoped сетях VPS. Все A/AAAA должны удовлетворять policy, DNS ответы перепроверяются непосредственно перед connect, используется pinned resolved IP + проверяемый TLS host identity, redirects отключены для чувствительных probe. IPv6 zone/link-local, decimal/octal/dword IP spellings, DNS rebinding и redirect-to-local — отрицательные тесты. Controller-local service endpoints доступны только явным фиксированным adapter capabilities, не через общую регистрацию внешнего VPS. Неавторизованный Operator не может расширить CIDR scope или зарегистрировать привилегированный внутренний endpoint.

## 32. Recovery privilege path, remote execution и snapshot reactivation — A01/A05/A06

### 32.1. Законный путь из READ_ONLY_RECOVERY

**Выбранный вариант A01: внешний ручной recovery-runbook**; нового privileged recovery endpoint/Job или `RECOVERY_CREDENTIAL_ROTATION` состояния в Backend не вводим. Рабочие шаги: (1) новый Controller загружается в `READ_ONLY_RECOVERY`, все mutating/API writes/jobs/schedules недоступны; (2) Owner независимо изолирует старый Controller через доступный console/hypervisor/physical access и фиксирует доказательства в локальном runbook; (3) Owner вручную на **каждой доступной managed VPS**, вне HostOrbit Job Queue, отзывает старые `authorized_keys`/API credentials и устанавливает новый ограниченный HostOrbit SSH public key; проверяет новое соединение и old-key denial; (4) недоступные VPS помечаются `QUARANTINED`, исключаются из всех mutating scopes; (5) сверяются удалённые незавершённые процессы по §32.2; (6) в Rescue CLI владелец подписывает локальное attestation и запрашивает активацию только для подтверждённо безопасных VPS. Если старый контроллер не изолирован либо доверенные свидетельства недоступны — весь экземпляр остаётся `READ_ONLY_RECOVERY`. Нет `force-active` и API провайдера.

**Разделение статусов:** `READ_ONLY_RECOVERY` — Controller не пишет управляемые системы; `ACTIVE` — разрешённые mutating capabilities могут исполняться *только* на VPS без `QUARANTINED`; `QUARANTINED` — статус конкретного ресурса, не отдельный контроллер. При активном Controller карантинные VPS доступны только для безопасного read-only observation. Невозможно сделать quarantined VPS доступной к изменению без новой проверенной credential rotation и завершения remote uncertainty. `RECOVERY_READY` — отчёт readiness, не самостоятельное право записи.

### 32.2. Два вида эффектов: process envelope и delegated-effect envelope — A05/B01

Каждая mutating операция обязана декларировать `direct_process_effects` и `delegated_effects` (пустые списки допустимы, если доказуемо). На VPS restricted SSH gateway принимает canonical `operation_id` и подписанный typed plan digest, записывает `remote_operation_ledger` в защищённом root-owned каталоге до dispatch и запускает команду в именованной transient systemd unit/cgroup `hostorbit-<operation-id>`, с `RuntimeMaxSec`, pipe-safe stdout и ограничением ресурсов. `systemctl inactive`, завершение helper/SSH или превышение RuntimeMaxSec **доказывает только состояние процесса**, не завершение delegated-effects у `dockerd`, nginx master или иного daemon.

**MVP Docker restart только импортированного immutable container:** до запуска фиксируются `container_id` (не mutable name), project/daemon identity, `StartedAt`, `RestartCount`, ожидаемые и запрещённые эффекты, Docker event checkpoint/daemon boot identity и операция в remote ledger. Перед dispatch — durable Controller intent и receipt местного helper. После dispatch опрос Docker API и event sequence применяется для подтверждения *конкретной* postcondition, подтверждения отсутствия/завершения pending daemon request в пределах доступного адаптеру протокола и проверки, что identity контейнера не сменилась. `dockerd` не даёт общего transactional operation ID для всех REST действий; только `docker events` или отсутствие нового `RestartCount` НЕ доказывает, что отложенная команда уже не выполнится. При разрыве/пропуске events, перезапуске daemon, изменении container identity, тайм-ауте, незавершённом daemon side effect — `UNKNOWN_OUTCOME` и карантин dependency closure; новые пересекающиеся операции не допускаются до read-only reconciliation плюс доказанной quiescence либо утверждённой ручной изоляции/завершения сервиса.

**Протокол daemon quiescence:** неравноправен «timeout завершился». Требуется scoped evidence, что асинхронный запрос больше не выполняется и не имеет отложенного эффекта: подтверждённый daemon receipt + terminal результат или вручную документированное администратором прекращение соответствующих daemon/remote process effects и последующая сверка ресурсов. Если такой evidence отсутствует — incident остаётся OPEN, затронутая VPS и все общие зависимости QUARANTINED. Закрытие SSH connection, отзыв ключа или kill helper сами по себе не обнуляют эффект. Нельзя ограничивать карантин лишь `container A`, если shared network/volume/project затрагивает B.

**Другие remote effects:** изолированный Nginx reload имеет отдельный типизированный receipt (проверка нового master generation, effective config, контролируемых URL и ответов); процесс перезагрузки и доказанная postcondition различаются. Никаких необозримых `nohup`, фоновых shell, произвольных systemd units или методов Docker без проверенного adapter reconciliation. Отмена возможна только до побочного эффекта либо в безопасной checkpoint. Тест B01 убивает helper при искусственно задержанном daemon effect и проверяет отсутствие ложного unlock и позднего конкурирующего рестарта.

### 32.3. Boot, snapshot и граница ручного fencing

Разделяем `NORMAL_REBOOT` уже активного известного экземпляра и `RESTORE_OR_IMPORT` нового Controller. Новый комплект данных, восстановление archive, изменение host identity/instance ID или Rescue install **всегда** стартует read-only. Обычный reboot допускает запуск только с устойчивым локальным activation record и проверкой invariants, но полная копия диска старого ACTIVE содержит такую же запись — программно отличить скрытый клонированный snapshot невозможно без внешнего anchor. Поэтому **HostOrbit не гарантирует обнаружение произвольного скрытого клона**; защита реально опирается на ручную изоляцию и смену SSH-credentials на managed VPS. На неохваченных ротацией VPS никакие гарантии отсутствия split-brain не заявляются — они quarantined. Generation ID полезен для аудита, но не является fencing. AC проверяет контрольируемые recovery/import и отказ old-keys после ротации, а не магическое распознавание неизвестного snapshot.

## 33. Согласованный Backup, криптографическое происхождение и Vault lifecycle — A02/A03/A11/A12/A13/A14

### 33.1. Согласованный snapshot и аутентифицированный recovery bundle — A02/A03/A13/B02/B03

**Рабочий Vault:** XChaCha20-Poly1305, `DEK_vN`, broker-authoritative ACL. Локальный OS wrap нужен только runtime. В portable archive передаются plaintext bytes всех необходимых DEK поколений **только внутри защищённого однонаправленного age/X25519 encryption stream**, без файла plaintext; host-bound OS wrap сам по себе не является backup. Offline Owner identity существует исключительно на доверенной изолированной Ubuntu workstation. Она расшифровывает подписанный исходный архив, проверяет согласованность data manifest, затем шифрует self-contained payload на одноразовый recipient нового Controller; private identity не попадает на VPS.

**Единый Backup Coordinator с ограниченной задержкой записи:**

1. `REQUESTED`: durable control-journal `backup_id`, baseline epoch, max wait. Обычные read-only проверки остаются доступны.
2. `CLOSING_ADMISSION`: gate запрещает новые **business mutations** Controller/Vault и новых mutating jobs, но позволяет ACK/checkpoint/Audit/Outbox/ошибки/backup-coordinator control metadata. Существующие операции и Vault rotations **drain** с допустимыми контрольными транзакциями; timeout 60 секунд → `ABORTED` с устойчивой причиной, все admission locks освобождаются. Нет ожидания завершения Job с одновременным запретом его checkpoint commits.
3. `SHORT_BARRIER`: максимум 30 секунд фиксируются `snapshot_id`, версия БД, `audit_head/sequence`, immutable index всех Vault blob IDs/digests, DEK generations, config version и идентификаторы всех pinned dependencies. Запрещены новые business-state writes; разрешены только независимые административные записи о ходе барьера, не меняющие pinned snapshot state. Копируется SQLite point-in-time snapshot (Online Backup API и закреплённая транзакционная точка) и полный pinned immutable blob/config set, проверяется `integrity_check`, `foreign_key_check` и referential completeness. Если не удалось сформировать самодостаточный локальный snapshot за предел → ABORT, не COMMITTED.
4. `BARRIER_RELEASED`: как только self-contained локальный snapshot и key set закреплены, writer admission **открывается**; pins защищают snapshot blobs/keys от GC до завершения работы. Ни `age` encryption, ни подпись, ни SFTP upload **не удерживают глобальный writer gate**. Snapshot фиксирует `audit_head` *до* записи финального `backup completed` audit event, которое относится к следующей последовательности событий.
5. `SEALED → SIGNED → UPLOADING → PUBLISHED/FAILED`: возраст/полнота сверяются, portable DEK экспортируются прямо в age stream; отдельный подписанный Controller provenance envelope покрывает исходный ciphertext digest + canonical manifest. Удалённая публикация — temporary object, verified checksum и atomic rename/final marker последним; только после этого COMPLETED. SFTP timeout, ENOSPC, crash/kill оставляют `FAILED/INCOMPLETE`, а не пригодный архив. По завершении release pins с контролируемым восстановлением после restart; контрольный журнал никогда не требует повторного lock business-state на время внешней загрузки.

**Журнал Coordinator:** отдельные durable control transitions с собственным коротким SQLite commit/outbox (или root-owned fsync journal для фаз при отказе БД); service metadata/Audit commits разрешены во время `CLOSING_ADMISSION`, а во время `SHORT_BARRIER` только вне snapshot-critical записи. Если невозможно записать статус, **никакая новая mutating операция не допускается**, а barrier восстанавливается из жёстко записанного phase/manifest. Граница lock измеряется и тестируется: 60 секунд на drain и максимум 30 секунд на pin/local snapshot; внешняя сеть не продлевает barrier.

**Происхождение исходного архива:** `age` гарантирует шифрование для владельца, но не аутентичность отправителя. Независимо сохранённый Controller public signing anchor проверяет подписанный наружный digest/manifest; владелец проверяет исходную подпись *на offline workstation* до расшифровки. Root compromise Controller signing identity не исключён и прямо указан как остаточный риск.

**Проверяемая привязка новой recovery bundle:** одни `source_envelope_sha256`, `recipient`, `target_id` и `challenge` в plaintext header недостаточны. **Выбранный MVP: независимое подтверждение точного SHA-256 финального ciphertext bundle владельцем** на новой VPS через физическую/удостоверенную локальную Rescue CLI-консоль. Offline workstation показывает `bundle_sha256`, проверенный `source_backup_hash`, `recipient_fingerprint`, `target_id`, `challenge`, `expiry` и краткую attest-сводку состава; владелец переносит полный digest в доверенную локальную Rescue CLI **не через сам загружаемый bundle и не через недоверенный Web UI**. Rescue сравнивает digest с байтами принятого зашифрованного bundle, проверяет challenge/recipient/expiry и одноразовый consumption ledger, после чего требует отдельную Owner auth и импорт. Подмена DB/DEK при сохранённых корректных внешних полях создаст другой digest и будет отклонена без нового независимого Owner approval. Это модель доверенного Owner/offline workstation, не математическое доказательство происхождения plaintext для недоверенного Owner.

**Негативные тесты:** непрерывные rotations, долгий Job, kill/ENOSPC в каждом состоянии, SFTP outage → deadlock не возникает, опубликованный архив всегда восстановим на независимой машине; правильный recipient/challenge/source hash с подменённым DB/DEK → отказ при неверном независимом digest; повторный/чужой bundle → отказ по consumption target binding.

### 33.2. ResourceBackup не равен снимку диска VPS

`ControllerBackup` охватывает согласованное внутреннее состояние HostOrbit. `ResourceBackup` — отдельный адаптер на поддерживаемой VPS. В MVP **только**: (а) HostOrbit-owned Nginx config-only bundle с сохранением разрешённых владельцев, modes, digest и списка included files; (б) остановленный импортированный тестовый Docker *named volume*, без bind mounts и без живой базы данных. Каждый ресурсный архив содержит тип данных, source host/UID/GID/mode, допустимые ACL/xattrs для поддержанного FS, excludes, приложения/схему/версию, размеры, целевой restore layout, проверку свободного места, overwrite policy `new_empty_target_only`, теги quiescence и зависимости; шифруется age и подписывается provenance аналогично ControllerBackup. Для неизвестного приложения, работающей БД, live bind mount и полного диска VPS — `UNSUPPORTED`, без обещания универсального snapshot. Нативные DB dumps и quiesce для дополнительных сервисов — отдельные проверенные возможности post-MVP.

**Resource restore** выполняется только вручную через профильный Manager и утверждённый Change Plan; в MVP тестовый restore на чистой Ubuntu и новом target без перезаписи чужих данных, затем проверка контента, владельцев файлов, запуска/health. Наличие age файла само по себе не доказывает, что приложение восстановлено.

### 33.3. Формальный Backup Gate, off-host RPO и Vault ACL

Три независимых свойства: `FRESH_BACKUP` — завершённый, с нужным `data_scope` и сохранённый за требуемый интервал; `INTEGRITY_VERIFIED` — проверены completeness/origin/checksums и файлы доступны; `RESTORE_ATTESTED` — **отдельная** ручная проверка процедуры восстановления той же схемы/типа ресурса, срок до следующей аттестации 90 дней. Ни одна ежедневная копия автоматически не получает статус `RESTORE_ATTESTED` из-за успешного sha256. `RESTORE_VERIFIED` разрешён только конкретному экземпляру, который реально восстановлен и проверен.

| Риск операции MVP | Backup Gate |
|---|---|
| Read-only / низкорисковый idempotent probe | копия не требуется |
| HostOrbit-owned Nginx config replacement | pre-change `FRESH_BACKUP` именно затронутого config scope не старше 30 минут, `INTEGRITY_VERIFIED`, актуальная `RESTORE_ATTESTED` процедура; если нет → block |
| `RESTORE_NEW_EMPTY_TARGET` для ресурса | Это **не pre-change backup gate**. Требуется `SOURCE_ARCHIVE_ELIGIBLE`: подписанное происхождение, целостность/полнота, совпадение типа/schema, актуальная `RESTORE_ATTESTED` процедура, реальная пустота новой цели, свободный объём и ручное подтверждение. Время создания source archive — выбранная точка восстановления, **без ограничения 15 минут**. |
| Controller update/schema migration | согласованный off-host ControllerBackup ≤30 минут до операции, complete/origin, проверенная restore-процедура и schema compatibility; иначе block |
| Замена непустого volume/restore с перезаписью | `BLOCKED` в MVP — без исключений, даже при наличии свежего архива |
| Необратимые / неподдерживаемые операции | BLOCKED в MVP, никакой «просто подтвердить риск» |

RPO измеряется **от времени последнего успешно завершённого off-host защищённого снимка**, а не от Cron-настроек. Failed SFTP, неподходящий data_scope или просроченный restore test — `BACKUP_GATE_DENIED`; UI показывает причину и следующий допустимый шаг. Продолжение без gate возможно только для класса, в котором backup явно не требуется.

**Vault ACL:** отдельная authoritative metadata в Broker с `secret_id`, immutable `secret_version`, `owner_id`, `allowed_consumers`, `purpose`, `state`, `policy_revision`; брокер валидирует protected ACL и связывает её хеш с AAD каждой blob/version. Стадии `ACTIVE → ROTATING → REVOKED`, terminal `DELETED` после снятия потребителей/retention. Отозванный secret не выдаётся для *новых* операций; перед каждым этапом фактического Use повторная проверка, выданные на старые этапы handles ограничены TTL и отзываются при safe checkpoint. Уже раскрытый сторонней системе token нельзя отозвать криптографически без ротации/смены его у поставщика; in-flight удалённые эффекты контролируются §32. Смена DEK создаёт новое поколение, старые поколения остаются для действующих blobs/backups до надёжного истечения зависимостей; экспорт содержит все необходимые поколения. Любая попытка прямого изменения ACL/metadata в SQLite не расширяет права Broker.

**Единая терминология B05:** `SOURCE_ARCHIVE_ELIGIBLE` для восстановления на пустую цель независим от `PRECHANGE_BACKUP_FRESH` для операции, которая разрушает существующие данные. В MVP нет destructive replacement; восстановление вчерашнего архивного снимка на новую пустую цель допускается с явным recovery point и проверкой формата.


## 34. Apply-time verification, очередь, блокировки и одноразовый запуск — A08/A09/A10/A19

### 34.1. Preconditions непосредственно перед первым побочным эффектом — G-02

`Preflight Evidence` содержит `evidence_revision`, `created_at_utc`, `source_host_key`, canonical remote config SHA-256, сведения об inode/symlink (если применимо), immutable Docker project/container image identity, dependency graph, service owner/aspect, policy revision, fixed target list, lock set и разрешённый scope. Период доказательности перед apply не более **5 минут**; истечение срока требует нового Preflight (само по себе не повторного approval, если базис не изменился). После получения lock Worker повторно запрашивает observed fingerprint через доверенный helper, сверяет актуальную RBAC/approval/secret state и полную версию baseline. При несоответствии — `STALE_BASELINE` до первого эффекта, новый plan+diff+approval, без перезаписи чужой правки. Перед **каждым** последующим изменяющим шагом проверяются отзыв полномочий и существенные baseline changes. Запись config — temp рядом с файлом, root-owned helper отклоняет symlinks/path escape, проверяет expected inode/hash, делает fsync файла+директории, atomic rename и verify/reload по собственному Nginx instance. Внешний actor, меняющий чужой файл между проверкой и rename, вне полной контролируемости; managed namespace исключает несанкционированную запись, а обнаруженная гонка должна fail-close.

### 34.2. Полное dependency closure, global mutator и UNKNOWN — A09/B04

MVP допускает **один** обычный mutating infrastructure Job за раз; право допуска выдаёт durable host supervisor (§36.1). Plan хранит `lock_set` с host, package database, isolated nginx instance, Docker daemon/project/container/volume/network/listener, credential scope, shared controller state и cross-host зависимости. Построение множества учитывает **транзитивное замыкание пересечений**: дочерние Compose ресурсы, общие сети, volume, proxy, cluster identities и связанные Remote effects. Поля `direct_process_effects` и `delegated_effects` фиксируются до Apply.

При `UNKNOWN_OUTCOME` исходная попытка терминальна, но incident остаётся OPEN, а его **полное conflict/dependency closure** заблокировано. **Упрощение MVP:** всегда карантин **всей VPS** и её пересекающихся cross-host dependents; `QUARANTINED` — только read-only observation. Нельзя ограничиться контейнером A и изменить контейнер B с общим volume/network. Глобальный mutator permit может быть освобождён для операций на заведомо независимых VPS **только** после durable Owner quarantine decision, вычисления полного closure и атомарного сохранения запрета на пересечения в host supervisor и Controller registry. Если невозможно доказать независимость (включая неизвестную cross-host связь), global permit остаётся удержанным и любые изменения блокируются.

Отсутствие heartbeat, истечение SSH/systemd timeout или простая остановка Worker не снимают locks. В read-only reconciliation подтверждаются remote ledger, прямые и делегированные эффекты, daemon status/event continuity и разрешённые postconditions; только проверенный результат либо утверждённая изоляция удалённого ресурса закрывает incident. В MVP **Controller application update и updater self-update запрещены при любом открытом `UNKNOWN_OUTCOME` / незавершённом delegated-effect incident**; независимо от затронутой VPS. Это упрощает конфликтную политику B09 и не допускает миграции Controller во время неизвестного удалённого эффекта.

Тест B04: неопределённый restart A с общим network/volume B блокирует новый план B; независимая VPS после полноценного quarantine closure допускается при едином permit; обновление Controller остаётся BLOCKED при любом открытом incident. Более узкий карантин — только post-MVP адаптер с доказанной моделью независимости.

### 34.3. Durable queue и audit-outbox

SQLite — **только локальный POSIX filesystem**, WAL и `PRAGMA synchronous=FULL`, `foreign_keys=ON`, контролируемый `busy_timeout=5000 ms`, короткие транзакции, проверка PRAGMA на startup, отказ в готовности при несоответствии. Все mutating Job transitions, Audit Event и Outbox Event записываются **в одной SQLite-транзакции**; после `COMMIT` события доступны SSE, до коммита нельзя сообщать success. HTTP 202 возвращается только после устойчивого `job+plan+audit+outbox` commit.

**Порядок:** перед каждым mutating send Worker получает у host supervisor однократный permit (§36); журналирует identity permit и **затем** `APPROVED` → durable `INTENT_PREPARED` с expected remote effects, operation_id и lockset, commit → durable `DISPATCHING/EXECUTING` before remote send → remote helper enqueue и durable remote receipt → read-only verification → committed `SUCCEEDED` либо `FAILED/UNKNOWN_OUTCOME` в зависимости от доказательств. Если commit не удался до отправки, команда не передаётся. Если исход после send неоднозначен — `UNKNOWN_OUTCOME`; успешная отправка без durable receipt не разрешает повтор. При `SQLITE_BUSY`, `ENOSPC`, повреждении DB или невозможности Audit commit — новые мутации fail-closed с `CONTROL_PLANE_STORAGE_UNAVAILABLE`; запущенные удалённые эффекты фиксируются как неопределённые после восстановления. SSE использует transactional outbox с monotonic event IDs, возможен replay после reconnect; несуществующий persisted event не может «мигнуть» успешным. При повторах worker lease не является гарантией завершения удалённой unit (§32).

### 34.4. Независимые запреты двойного исполнения

HTTP `Idempotency-Key` уникален по `(actor_id, action_namespace, idempotency_key)` в 24-часовом окне. `payload_hash` хранится отдельно для сравнения. Повтор с тем же payload возвращает тот же ответ; повтор с другим payload → 409, в том числе при гонке двух запросов. **Отдельный неизменяемый `plan_execution_ledger` запрещает второе создание mutating execution для `(plan_id, approved_revision)` независимо от истечения сетевого dedup TTL**; запись execution ledger и Job транзакционно атомарны. Повтор approved плана через 25 часов не создаёт нового Job — нужен новый Change Plan/Revision с новым Approval. Reconciliation читает состояние существующей попытки, не создаёт новую mutating execution. Нельзя терять tombstone uniqueness при обычной очистке Job History.

**Состояния** Plan/Job/Incident и Authority Gate определяются **только §40**, не этим разделом. Снятие глобального permit при UNKNOWN подчиняется полному quarantine closure §34.2; terminal attempt остаётся исторической, отмена не объявляется успешной, пока возможен удалённый побочный эффект.

## 35. Публикация Nginx, журналы и безопасность сетевых проверок — A16/A17/A18

### 35.1. Выбранная модель Nginx MVP

MVP **не редактирует конфиги system Nginx, shared nginx master, конфигурации чужих vhost или чужой `default_server`**. Управляемая публикация доступна только через отдельный HostOrbit-owned Nginx instance с собственными `-p/-c`, PID, include namespace, root-owned конфигурационным деревом и **выделенным свободным address:port** (например, отдельный localhost high-port). Публичные IP:80/443, занятые другим процессом, не захватываются; привязка к существующему публичному proxy выполняется владельцем **вручную вне HostOrbit**, её состояние обнаруживается как Publication Only/Discovered. Вариант управлять общим master с семантическим анализом виртуальных хостов — post-MVP и без автоматического переноса. Это ограничение применяется ко всем MVP FR/AC, в том числе если UI ранее именует «Nginx Manager».

Helper валидирует абсолютные paths/uid/mode и include allowlist, `listen`, `default_server`, `server_name` и proxy protocol; делает `nginx -t` на **полном effective configuration своего instance**, atomic config write, reload только своего PID и verification HTTP/TLS в собственном listener. Изменение во внешнем system nginx недопустимо. Negative tests: duplicate names, IPv4/IPv6 dual-stack, занятие чужого socket, symlinks/includes outside tree, failure during reload, проверка доступности контрольных сторонних сайтов до/после; байтовая неизменность их файлов — необходимая, но недостаточная проверка. На системах с общим единственным Nginx такой сценарий управляемой публикации не поддерживается MVP, доступен read-only и документированный manual vhost setup.

### 35.2. Достоверная политика журналов

MVP показывает **только структурированные журналы, произведённые HostOrbit**, и ограниченные типизированные результаты поддерживаемого helper (`operation_id`, timestamps, status, allowlisted errors). Перед попаданием в SQLite/audit/SSE/export выполняются allowlist + redaction; ограничение одного события ≤16 KiB, окна результатов ≤1 MiB/job и частоты. Дамп environment, приватных файлов, arbitrary third-party stdout/stderr и «сырые» логи произвольного приложения **не выдаются в MVP**. Сторонний stdout может содержать неизвестные пароль, base64, multiline, URL encoded: универсального детектора секретов нет. Post-MVP сырой лог может появиться только как отдельный явно помеченный высокорисковый capability с ограничением доступа и best-effort redaction, не под обещанием абсолютного отсутствия секретов.

Canary test включает строку/URL/base64/multiline/traceback/SSH stderr; все заявленные защищённые каналы DB/SSE/Audit/Support Bundle/браузер не содержат контрольные секреты. Журналы не доказывают, что произвольное внешнее приложение само не пишет секреты на своей VPS — это вне гарантии HostOrbit.

### 35.3. SSRF-aware registered targets

Любая инициируемая Worker сеть привязана к явной `NetworkTargetPolicy(target_id, allowed_cidrs, allowed_ports, hostname_set, host_identity, purpose, registered_by, policy_revision)`. Приватные RFC1918 сети допустимы по белому списку владельца, а локальные Controller loopback/link-local/metadata IP блокируются по умолчанию, включая нестандартные текстовые формы адресов, redirects и IPv6 zones. DNS разрешение/проверка **всех** A/AAAA выполняются при Preflight и непосредственно при connect; при изменении адреса на запрещённый или после approval — `STALE_TARGET`, без connect. HTTP redirects для чувствительных probes выключены. TLS host identity, SSH host fingerprint и endpoint binding проверяются раздельно. Операторы без владельческого права `RegisterTarget` не могут использовать регистрацию/подмену DNS для доступа к привилегированным внутренним endpoint; local loopback сервисы допускаются только через отдельные fixed capability adapters.

## 36. Independent Update Controller, время и offline Rescue environment — A15/A21

### 36.1. Host Updater, единый durable admission authority и исключение Worker — A15/B09

**Подписанный артефакт:** host-installed `hostorbit-updater-<platform>-<version>.tar.zst` (НЕ OCI binary). `release.json` подписан Ed25519 и содержит `sha256,size,version,platform,min_bootstrap_version,min_allowed_release,schema_compatibility,signing_key_id` + отдельные OCI digests Web/API/Worker. Root-owned стабильный **bootstrap supervisor** остаётся вне A/B updater slots и не заменяется во время app update; он является **единственным host-local authority для выдачи mutating execution permits и maintenance permits**. Отдельного нового Web-модуля или постоянного агента на VPS нет.

**Host state:** root-owned каталог `/var/lib/hostorbit/control-gate/` с fsync-устойчивым журналом и monotonic `epoch`; состояния только `NORMAL → QUIESCING → MAINTENANCE → RESUMING → NORMAL`, либо `RECOVERY_HOLD`. Ключевой инвариант: в `MAINTENANCE` нет активных remote mutating permits, а в `NORMAL` нет updater maintenance permit; одновременно их выдать невозможно даже после kill/restart. `GatePermit` привязан к `plan_id/revision`, `job_id`, `target`, `lock_closure_digest`, `epoch`, TTL и одноразовому nonce; подписан/аутентифицирован локальной host authority и проверяется Broker/Worker. Истечение TTL **не доказывает** завершение удалённого эффекта и не позволяет переиспользовать ресурсы до reconciliation. Gate-журнал хранится отдельно от мигрируемой SQLite, поэтому новый Backend/Worker не может сбросить maintenance состояние при смене схемы БД.

**Application update:** (1) Owner утверждает отдельный неподменённый update plan, (2) supervisor записывает `QUIESCING` и прекращает выдавать новые mutating permits **до ACK**, (3) Worker безопасно drain-ит задания и checkpoint commits; supervisor проверяет broker/remote admission ledger и **отсутствие любых OPEN UNKNOWN / delegated effects** (§34.2), (4) root-owned supervisor долговечно фиксирует `MAINTENANCE`, отзывает обычные permits, выдаёт **один** maintenance permit updater, (5) подписанный download/stage/backup/schema migration/apply/smoke-test, (6) supervisor только после результата записывает `RESUMING`, проверяет Worker и invariant gates, затем `NORMAL`. Ошибка, смерть Worker/updater или отсутствующее ACK → `RECOVERY_HOLD`, не автоматическая активация mutator.

**Self-update:** updater A/B и application update — разные планы/журналы с **одним** gate. Self-update не запускается, если иной update уже в прогрессе или OPEN incident. Host bootstrap выполняет atomic `fsync + symlink switch`, проверяет новую версию updater и при ошибке возвращается к **совместимому бинарному** слоту без rollback SQLite. Crash recovery читает durable journal, не превращает подписанный старый release в разрешённый downgrade. DB schema migration имеет отдельную до-/после- точку; несовместимый rollback запрещён.

**IPC:** root-owned AF_UNIX socket host supervisor, ограниченные UID и peer credentials, `plan_hash+owner approval id+epoch+nonce+requested capability`. Backend не получает root/docker.sock и не может создать maintenance permit прямым JSON. Worker с недействительным gate permit не получает Broker SSH-use. Условия допуска не зависят от готовности самого обновляемого Backend. Минимальное разрешение Owner для update — не независимый second approver; Backend-in-TCB (§31) сохраняется.

**Негативный тест B09:** одновременно отправить typed Docker restart, app update и updater self-update; выполнить kill Worker/updater на `QUIESCING`, перед/после ACK, во время migration и при reboot host; проверять что не возникли два mutating permits, UPDATE при OPEN incident отклонён, после crash есть однозначный `RECOVERY_HOLD` либо корректно восстановленный `NORMAL`, а не гонка admission.

### 36.2. Time health и Rescue profile

Host-side `TimeHealth` через установленный локальный helper сообщает `source=chrony|timesyncd`, `last_sync_utc`, `offset_ms`, `max_error_ms`, `clock_step_detected`, `sample_age_s` и `boot_id`; Worker получает **проверяемые сведения с хоста**, не пытается читать host chrony из контейнера по догадке. Для mutating approval/leases: sample age ≤5 минут, последняя доверенная синхронизация ≤24 часа, оценка absolute offset+error ≤2 секунды и отсутствие clock step >1 секунды после выдачи плана. Offline holdover допускается до **1 часа** после последней годной выборки, если monotonic clock не менялся и projected uncertainty ≤2 секунд; иначе `TIME_UNTRUSTED`, блокируются новые mutating apply, но read-only остаётся. Тайм-ауты внутри процесса — monotonic, абсолютные интервалы — UTC с указанной неопределённостью. В тестах проверяются step clock, отключение сети, отсутствие time health и старый sample.

**Offline Rescue workstation MVP:** Ubuntu 24.04 amd64, изолированная доверенная локальная среда, не публичный Web UI. Перед чтением offline identity проверяются запрет core dumps (`ulimit -c 0`/OS policy), отсутствие hibernation, swap **выключен либо полностью зашифрован и надёжно управляем**, недопущение plaintext temp и записи приватной identity в args/env/history. Sensitive buffers очищаются best-effort средствами используемой криптобиблиотеки; абсолютной гарантии очистки Python memory, DRAM или произвольной рабочей станции нет. Если строгий профиль не выполнен, Rescue CLI **отказывает в offline decrypt**; допускается только отдельный документированный ручной сценарий с осознанно меньшей гарантией вне MVP. В тесте проверяются swap/core/suspend/preflight и отсутствие приватных ключей на новой Controller VPS.

## 37. Capacity, нагрузка, retention и пользовательские границы — A22 + дополнительные рекомендации

SQLite остаётся единственной DB MVP, локальный диск 40 GiB — **ресурсная конфигурация стенда**, не доказательство, что 100 тыс. событий в месяц хранятся год без очистки. По всем данным определяются отдельно: журнал ≥30 дней с ограничением byte budget/категорий, audit retention согласно §24 и защищённым ссылкам, job checkpoints до закрытия инцидента, максимальный payload/SSE replay и GC через registered objects; при превышении quota новые тяжёлые diagnostics блокируются вместо удаления критичных свидетельств. Максимальный SSH pool MVP — **4 read-only concurrent connections**, **1 mutating**, 10 diagnostics/min/user как в §19; API streaming response size ≤1 MiB/window, task output ≤1 MiB, SSE replay window 24 часа или 10 тыс. events (что раньше), затем reconnect по authoritative Job endpoint. ResourceBackup для MVP ≤10 GiB на один остановленный volume при наличии свободного пространства и SFTP quota, больше — UNSUPPORTED до отдельного теста.

**Нагрузочный протокол:** фиксированный образ Ubuntu 24.04/2 vCPU/4 GiB RAM/40 GiB SSD, набор 25 VPS, 200 сервисов, минимум 30-дневный синтетический dataset (включая связанные audit/jobs/metric records), 30 мин warmup, 8 часов mixed soak с doc-defined API read/write/SSH workloads и переменной конкуренцией. Метрики: writer lock wait, SQLITE_BUSY count, duration транзакций, fsync/storage latency, WAL growth/checkpoint duration, query plan/regressions, p95/p99 каждого названного endpoint, error count по типу. Намеренные 401/403/409/412/423/428 не считаются серверной ошибкой; 5xx/timeout считаются. Пороговые числа могут вызвать **capacity review**, но не автоматический переход на PostgreSQL. Такое решение принимается только при подтверждённом именно SQLite-bottleneck, после индексации/retention/profile и отдельного подписанного ADR; SQLite→PostgreSQL post-MVP — только offline single-writer cutover, без dual-write.

**Функциональная граница MVP:** Caddy, Firewall, SSH changes — read-only/blocked; Docker manage — только импортированный, подтверждённый и защищённый отдельным helper project; Nginx manage — только отдельный HostOrbit instance на незанятом listener; Remnawave/VPN/Topology advanced — optional post-MVP. Объяснение ограничения обязательно в onboarding и карточке capability. Релиз не должен позиционироваться как полнофункциональный универсальный Firewall или серверный root-console.

## 39. Дополнительные критерии приёмки редакции 2.3 (AC-A01–AC-A22)

Каждый AC имеет обязательный evidence artifact: тестовый сценарий, setup/versions, сохранённый результат, журнал без секретов и заключение reviewer. Отсутствие фактического протокола = `NOT_TESTED`. AC-A01…AC-A05 должны быть доказаны узкими прототипами **до утверждения соответствующих контрактов и до разработки привилегированного MVP**; все AC-A06…AC-A22 обязательны до релиза соответствующего функционала, A19–A22 для общего MVP.

**AC-A01 — Recovery privilege path [P0/Stage0].** На полностью выключенном старом ACTIVE новый Controller не выполняет обычный restart. Внешний ручной runbook отзывает old keys и устанавливает new restricted keys на доступных VPS, недоступный хост остаётся QUARANTINED; Owner активирует только проверенные цели. Ни один обычный Job не получает исключение в READ_ONLY_RECOVERY.

**AC-A02 — Portable Vault DEK [P0/Stage0].** Удалить old host credential store и системный диск; извлечь archive на иной машине с offline Owner age identity; reencrypt под одноразовый recipient; восстановить все активные и необходимые старые версии секретов. Подмена одним OS-wrapped DEK проваливает тест.

**AC-A03 — Cross-store snapshot [P0/Stage0].** Во время непрерывной Vault rotation/revoke и изменения ресурсов создавать backup; kill/powerfail каждой фазы REQUESTED/CLOSING_ADMISSION/SHORT_BARRIER/BARRIER_RELEASED/SEALED/SIGNED/UPLOADING/PUBLISHED. Все COMPLETED архивы восстанавливают все reference/key_versions/audit head; INCOMPLETE не предлагаются к восстановлению.

**AC-A04 — TCB/Broker boundary [P0/Stage0].** В тестовом Backend RCE попытаться подделать plan/approval, перезаписать DB, вызвать Broker IPC, запросить secret и Docker operation; ожидать отказ для shell/несоответствующего scope/невалидного IPC. Если тест демонстрирует злоупотребление разрешённым выглядит approval в пределах TCB, это **показывается как остаточный риск, не маскируется фразой «RCE защищён»**; разработчик подтверждает заявленную границу доверия.

**AC-A05 — Remote delayed side effect [P0/Stage0].** Запустить transient unit с задержанным побочным эффектом, оборвать SSH, выключить прежний Controller, отозвать key. Новый не снимает conflict lock и не запускает вторую мутацию пока direct process и delegated daemon effects не подтверждены завершёнными или ресурс не изолирован или VPS не изолирована. Запущенный process tree проверяется через cgroup/systemd.

**AC-A06 — Snapshot/reboot [MVP].** Сравнить normal reboot, restore/import и full snapshot clone. Новая восстановленная установка стартует READ_ONLY; old key отвергается VPS после ротации. Не заявляется универсальная детекция скрытого клона; возможный злоумышленный full clone описан в Threat Model как недоказуемый без внешнего anchor.

**AC-A07 — Remote SSH privilege [MVP].** Украденным dedicated hostorbit key попытаться открыть shell, PTY/port forwarding, изменить helper, получить docker.sock, выполнить чужой project, подставить shell metacharacters. Все выходы за типизированные allowlist отказываются на самой VPS. Проверен root-owned helper package/version и new SSH fingerprint.

**AC-A08 — Stale baseline [MVP].** После Approval изменить remote file, inode/symlink, Docker project/container identity, ownership и policy. Apply прекращается ДО первого эффекта со `STALE_BASELINE`, не перетирая ручную правку. Проверить повторные guards перед последующими шагами.

**AC-A09 — Dependencies & locking [MVP].** Одновременно запросить два vhost своего Nginx instance и изменение общего Docker project/network. Один host-issued глобальный mutator permit и полный dependency closure предотвращают пересечения. После UNKNOWN lock удерживается; read-only observation идёт; deadlock и промежуточное «Healthy» не возникают.

**AC-A10 — Durable intent and outbox [MVP].** Inject kill/powerfail/ENOSPC/SQLITE_BUSY на границах `job accepted → intent committed → remote send → receipt → verify → audit+outbox`. Принятый Job не исчезает; возможно выполненный эффект отражается UNKNOWN; SSE не показывает неподтверждённый SUCCEEDED. Стартовые PRAGMA проверены.

**AC-A11 — Resource restore [MVP].** Полностью удалить тестовый HostOrbit-owned Nginx instance config и остановленный Docker named volume с исходной VPS. Восстановить заявленный supported data scope на чистую Ubuntu, проверить права/содержимое/health приложения. Live DB/unknown bind mount должны вернуть UNSUPPORTED.

**AC-A12 — Backup Gate [MVP].** Новый pre-change backup без ручного restore каждого экземпляра допускается лишь с актуальной restore procedure attestation и нужным scope; просроченная аттестация, SFTP failure и неверный scope блокируют Apply. RPO считается от завершённой off-host копии.

**AC-A13 — Backup provenance/replay [MVP].** Полностью заменить age ciphertext/SFTP manifest на корректно пересчитанную, но не подписанную доверенным ключом пару — отказ. Старый bundle, чужой target recipient и повторный challenge — отказ. Идентифицированы границы при скомпрометированном signing key/full snapshot.

**AC-A14 — Secret metadata/rotation [MVP].** Изменить owner/ACL/state в DB, переставить ciphertext, отозвать секрет после Approval до Apply, сделать DEK rotation во время backup и выполнить in-flight job. Неавторизованный Use невозможен, запрещённые новые потребители блокируются; старые поколения ключей сохраняют расшифровку архива.

**AC-A15 — Updater failure matrix [MVP].** Kill/self-update после каждой фазы A/B switch и до/после DB migration; повтор IPC, валидная старая подпись, ошибочный Vault smoke test. Существует один durable host admission/maintenance journal и один trusted authority; downgrade несовместимого DB запрещён, Rescue доступна.

**AC-A16 — Safe Nginx publication [MVP].** На VPS с чужими vhost/shared nginx создать отдельный owned instance; проверить старые routing/TLS/health до и после. Duplicate server_name, IPv6 dual-stack, default_server, опасный include, занятый socket и partial reload не воздействуют на system master.

**AC-A17 — Secret leakage/logging [MVP].** Canary token в stderr/stdout, URL, multiline, traceback и SSH output. В SQLite, structured logs, audit, SSE, браузере и экспорте нет canary; сырой third-party stdout отвергается отдельным unsupported capability, а не «волшебным redaction».

**AC-A18 — SSRF [MVP].** DNS rebinding, ipv6 link-local zone, нестандартная IPv4 нотация, redirect-to-metadata, изменение A/AAAA после preflight и Operator-register-privileged-target — deny; разрешённая по policy RFC1918 VPS при этом работает.

**AC-A19 — Idempotency ledger [MVP].** Два конкурентных запроса с одним key и различным payload создают один Job и один 409. Повтор APPROVED plan через 25 часов и после cleanup job history не создаёт новой mutating execution.

**AC-A20 — Registry/state integrity [Stage0, затем каждый release].** Автоматически проверить, что каждый активный FR/subrequirement имеет stage, owner, хотя бы один AC и evidence path; каждый AC ссылается на доступный этап и capability. Проверить невозможные state transition и отсутствие Stage0 dependency на Stage2 Web, отдельное handling UNKNOWN incident.

**AC-A21 — Time/Rescue environment [MVP].** Проверить host NTP time-health при offline network holdover, clock step, sample age и large skew; неподтверждённое время блокирует mutation. Offline Rescue с необработанным swap/core dump/hibernation отказывает в decrypt и не копирует owner identity на новую VPS.

**AC-A22 — SQLite capacity/soak [MVP].** На фиксированном аппаратном стенде провести 8h mixed soak после 30m warmup на 30d dataset. Приложить нагрузку, p95/p99 отдельных endpoint, WAL/transaction/writer metrics, full quota test, error accounting с исключением ожидаемых 4xx. Решение PostgreSQL не выводится автоматически из числа VPS/событий.
### 39.2. Испытания контуров B01–B10 (дополнительно к AC-A01…AC-A22)

Эти испытания обязательны для затронутого MVP capability; B01/B02/B03/B04/B09 — узкие `Stage0` доказательные прототипы. Один и тот же `NOT_RUN` никогда не принимается как PASS. В частности `quarantine` не подтверждает окончание Docker daemon-side эффектов.

**AC-B01 [Stage0; Execution/Adapter].** **Docker delegated-effect termination:** Artificially delay daemon restart after typed helper receipt; kill SSH/helper/systemd; verify late daemon effect cannot produce false quiescence, and closure stays blocked until proven completion/manual isolation.

**AC-B02 [Stage0; Backup Coordinator].** **Backup coordinator admission and barrier:** Long Job and Vault rotation during backup; SFTP unreachable, ENOSPC and coordinator kill in every phase; verify bounded business admission block, checkpoint/audit progress, self-contained immutable snapshot and safe pin GC.

**AC-B03 [Stage0; Rescue/Recovery].** **Recovery bundle owner provenance:** Build wrong age payload with correct source-hash/recipient/challenge but altered DB/DEK; Rescue must require independent exact Owner digest and reject substitution/replay/other target.

**AC-B04 [Stage0; Operations/Policy].** **Quarantine dependency closure:** Unknown Docker A shares Compose network/volume with B; B blocked, truly independent VPS may proceed after durable closure; updater blocked while any OPEN unknown.

**AC-B05 [Stage2; Backup/Resource Restore].** **Restore source eligibility:** Restore valid previous-day source archive into new empty volume; success after compatibility/origin/attestation; refuse restore on occupied target regardless of age.

**AC-B06 [Stage0; Requirements/Auth].** **Requirements trace and security sessions:** Validator rejects missing descriptions, stage, release, assertion, AC owner, dependency; test session idle/absolute expiry, logout/revocation, role change, CSRF denial and Stage0/MVP gates derived from registry.

**AC-B07 [Stage0; Architecture/QA].** **No competing normative state machines:** Static checker finds single normative Plan/Job/Incident/Gate definitions and Stage0 gate, no promise to detect knowingly false Owner attestation; ADR amendment allows design changes.

**AC-B08 [Stage0; SSH/OS].** **SSH account reproducibility:** Fresh Ubuntu forced-command with /bin/sh and root-owned authorized_keys; valid typed request succeeds; shell/PTY/forwarding/sudo wildcard/writable key and helper paths fail.

**AC-B09 [Stage0; Updater/Operations].** **Update admission mutual exclusion:** Race Docker restart, app update and self-update with kill/crash before/after quiesce, schema migration and supervisor restart; no two permits, open unknown blocks update, host gate recovers fail closed.

**AC-B10 [Stage0; Secrets Broker].** **Broker UID/GID socket ACL:** Real container UID/GID mapping with 0660 dedicated group and SO_PEERCRED; Worker scoped RPC succeeds, Backend/stranger uid denied, JSON consumer spoof rejected.

### Нормативные state machines

**Ownership** (единственный граф): `DISCOVERED → PENDING_ADOPTION → PUBLICATION_ONLY | FULLY_MANAGED → DETACHED → DELETED`; обратный `FULLY_MANAGED → PUBLICATION_ONLY` возможен только через новый Change Plan. На `(resource,aspect)` ровно один authority; QUARANTINED — независимый запрет записи, не альтернативное право владения.

**Plan:** `DRAFT → PREFLIGHTED → AWAITING_APPROVAL → APPROVED → EXECUTION_CLAIMED → CLOSED`; stale baseline/expiry требует новую DRAFT revision, не повторное approval старой ревизии.

**Job:** `QUEUED → INTENT_PREPARED → DISPATCHING → EXECUTING → VERIFYING → SUCCEEDED | FAILED | UNKNOWN_OUTCOME | CANCELLED_SAFE`. `UNKNOWN_OUTCOME` **терминален для попытки**; никакой переход из terminal back to EXECUTING.

**Incident:** `OPEN → RECONCILING → RECONCILED_SUCCEEDED | RECONCILED_FAILED | QUARANTINED`; incident может оставаться OPEN при QUARANTINED зависимости до независимого closed evidence. Перевод в QUARANTINED не гарантирует завершения daemon effects и запрещает пересекающую запись.

**Host Admission Gate:** `NORMAL → QUIESCING → MAINTENANCE → RESUMING → NORMAL` с аварийным `RECOVERY_HOLD`. `MAINTENANCE` исключает remote mutating permits, `NORMAL` исключает updater maintenance permit; root-owned journal переживает замену Backend/Worker и schema migration. На failure gate fail-closed.

**Backup Coordinator:** `REQUESTED → CLOSING_ADMISSION → SHORT_BARRIER → BARRIER_RELEASED → SEALED → SIGNED → UPLOADING → PUBLISHED | FAILED`; `ABORTED` допустим из pre-snapshot phases. Только `PUBLISHED` даёт завершённую off-host копию; barrier заканчивается на BARRIER_RELEASED, upload его не удерживает.

### Единственные Stage Gates

**Stage0:** прототипы `AC-A01..A05`, `AC-A20`, `AC-B01/B02/B03/B04/B06/B07/B08/B09/B10`; прошедший Stage0 не делает продукт готовым к эксплуатации.

**Stage1:** Foundation Host/Auth/Database/Broker/Worker/Updater-host-supervisor с отрицательными тестами; здесь не требуется готовый UI `AC-28`.

**Stage2:** единый сквозной сценарий `AC-28` плюс `AC-B05` и все зависимые service/backups/Audit controls.

**Stage3:** все MVP требования и связанные AC подтверждены свидетельствами, P0/профиль DR и подписанные выпуски; `NOT_RUN` или `FAIL` обязательного AC блокируют релиз.

**Stage4/5:** только соответствующие строки post-MVP / optional adapters; базовые P0/P1 инварианты не ослабляются.

**Проверки целостности registry:** отсутствие обязательного поля, неразрешённый AC, owner/stage, неправильный release, недостижимая зависимость, отсутствие assertion, test без требования или попытка считать Stage0 успешным без нужных негативных тестов — ошибка валидации. Статус каждого теста в этой редакции `NOT_RUN`.


## 41. Управление baseline, доказательствами и безопасным порядком разработки

**Редакция 2.3 — документарный baseline, а не сертификат безопасности.** B01–B10 устранены как неоднозначности требований, не как доказанные свойства runtime; все 84 AC ожидают выполнения. High B01–B04/B09 подлежат узким Stage0 прототипам до закрепления реализации соответствующих привилегированных путей. Остальные B05–B08/B10 имеют отдельные отрицательные тесты с точными границами.

**Минимальный Stage0 протокол при отдельном разрешении владельца:**

1. `T0-1` Docker delegated effect: задержать запрос внутри dockerd, убить helper/SSH, показать `UNKNOWN_OUTCOME` и отсутствие нового конфликтующего permit (B01/B04).
2. `T0-2` Snapshot/concurrency: concurrent Job/DEK rotation, unavailable SFTP, ENOSPC/kill на каждой фазе, release bounded barrier и независимое восстановление (B02 + A02/A03).
3. `T0-3` Bundle authenticity: другой DB/DEK при правильном recipient/challenge/source hash отклоняется без независимого Owner exact digest (B03).
4. `T0-4` Conflict/update: shared Compose volume/network, открытый UNKNOWN, race remote restart/application update/self-update, падение до/после QUIESCING ACK (B04/B09).
5. `T0-5` Profiles/registry: чистая Ubuntu/Compose с /bin/sh+forced command/authorized_keys root, Broker AF_UNIX peer ACL, тест реестра на пропущенные assertion/stage и Session/CSRF/role revoke (B06/B07/B08/B10). Restore вчерашнего source-архива на пустую цель и отказ на непустой (B05) принимается на Stage2.

**Ранее обязательные A01–A05 прототипы сохраняются**; B-тесты не заменяют их и не отменяют проверку независимого восстановления без OS key, delayed daemon effects, Backend/Worker TCB, единственного authority и Rescue CLI. Обязательная матрица свидетельств: `test_id`, сборки и manifest/SBOM, исходное состояние, сценарий, fault injection, фактическое наблюдение, непустой evidence digest, время и рецензент. `PASS` присваивается только по evidence, `NOT_RUN` и пустой отчет блокируют Stage3.

**Исправление проекта разрешено:** провал или контрпример → ADR_CHANGE_REQUEST с оценкой FR/NFR/AC, threat model, migrations, remote effect bounds и recovery. Если безопасный контракт не проходит тест, соответствующий privilege capability остаётся отключённым на Backend/Worker/Broker, а не только скрытым в UI.

**Границы:** не используется API провайдера или скрытая авторотация DNS, не объявляется exactly-once SSH, невозможность произвольного snapshot clone, защита от root/Backend RCE, секретно-безопасный произвольный сторонний stdout, универсальный disk snapshot VPS, авто-failover, авто-rollback несовместимой SQLite схемы или гарантированный RPO/RTO. Публичный бренд HostOrbit требует отдельной проверки товарных знаков и доменной доступности.

**Не менялись:** исходный код, репозитории, VPS, Docker, DNS и инфраструктура. После отдельного разрешения владельца разрешён только ограниченный Этап 0 с лабораторными прототипами; production deploy ещё не разрешён.
