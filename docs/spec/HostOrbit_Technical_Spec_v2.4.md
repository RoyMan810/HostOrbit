# Техническое задание HostOrbit v2.4

Редакция от 17 ноября 2026 года. v2.4 сужает объём первой версии и уточняет правила её приёмки.

[Реестр v2.4](HostOrbit_Requirements_Registry_v2.4.json) задаёт релизный объём, этапы, связи требований с критериями и пути свидетельств. [ТЗ v2.3](archive/HostOrbit_Technical_Spec_v2.3.md) содержит исходные технические контракты. Для областей, перечисленных ниже, действует формулировка v2.4. Для остальных областей действуют технические контракты v2.3. Нормативные машины состояний Plan, Job и Incident из §40 сохраняются.

[Статус реализации](../../README.md) и [инструкции](../README.md) описывают текущий код. Наличие требования в ТЗ означает, что его нужно реализовать и проверить. Результаты приёмки фиксируются отдельно.

## Сквозная приёмка Stage2

AC-28 выполняется на чистом Controller и отдельной Ubuntu VPS, без VPN и Remnawave.

1. Установить подписанную сборку, создать Owner локально, подключить VPS с подтверждением SSH fingerprint.
2. Обнаружить Docker Compose, явно импортировать один тестовый контейнер по фиксированным ID, проекту и сервису.
3. Сохранить версионированный Change Plan. Выполнить Preflight, показать Diff и риск, принять решение Backup Gate, получить approval точной ревизии.
4. Повторить проверки непосредственно перед эффектом. Перезапустить ровно один контейнер через типизированную операцию, проверить эффект, сохранить Timeline и Audit/Outbox.
5. Отдельно подтвердить создание и проверку зашифрованного ControllerBackup с защищённой off-host публикацией.
6. Проверить отказ на неподходящей цели, при устаревшем baseline, изменившейся ревизии, отсутствии approval или admission permit. При неопределённом исходе после отправки команды сохранить UNKNOWN и конфликтующие блокировки. Повторять эффект автоматически запрещено.

AC-B05 проверяет восстановление пригодного архива в новый пустой тестовый Docker volume и отказ для занятой цели. Наличие решения владельца по лабораторному прогону указывается в истории. Формальный результат требует свидетельства в реестре.

## Backup Gate для Docker restart

Допускается класс `RESTART_STATELESS_TEST_CONTAINER`. Для него отдельный предоперационный ResourceBackup не требуется только при выполнении всех условий:

- Владелец явно импортировал контейнер как тестовый и подтвердил, что приложение не хранит эксплуатационные данные в writable layer и не зависит от сохранения состояния процесса. Перезапуск не должен затрагивать эксплуатационные внешние сервисы.
- Закреплён полный ID, Compose project/service, fingerprint хоста и ревизия политики. Свежий preflight подтверждает состояние и отсутствие примонтированных томов, bind mount и других mount. Известна область зависимостей. Неизвестная, общая или изменившаяся область с возможным внешним эффектом блокирует допуск.
- План разрешает только restart этого контейнера в пределах оценённого простоя. Исключены создание, пересоздание, удаление, pull, обновление образа, изменение конфигурации и операции с volume.
- Сервер фиксирует решение Backup Gate и его основания для конкретной ревизии. Действуют отдельный approval, повторная проверка baseline, действующий одноразовый permit и проверка результата. Наличие резервной копии не заменяет соответствие классу.

Контейнер с данными, неподтверждённая цель и недостоверные сведения блокируют применимость класса. Для прочих операций продолжают действовать ограничения §33.3 v2.3. Резервное копирование для миграции БД, обновления Controller и независимого DR требуется по соответствующим правилам.

Рабочий Change Plan и связанное задание используют одну Controller DB. Миграция схемы предварительно проверяется на отдельной копии. Проверка миграции и допуск рабочей операции имеют разные результаты.

## Нагрузочный профиль

Для NFR-08, AC-45 и AC-A22 используется один профиль. Controller имеет **1 vCPU / 2 GiB RAM / 40 GiB SSD** и отдельное зашифрованное backup-хранилище. Нагрузка охватывает до 25 VPS, 200 сервисных объектов, максимум четыре параллельных read-only SSH-соединения и одну изменяющую операцию глобально. Цель p95 чтения API без ожидания внешнего SSH — ≤500 мс. Методика §26 и §37 v2.3 сохраняет 30-дневный набор данных, 30 минут прогрева, восьмичасовой soak, проверку WAL и учёт ошибок. Результат development-установки на этом железе сам по себе не подтверждает нагрузочную приёмку.

## Этапы и критерии

| Этап | Условие |
|---|---|
| Stage0 | Принятые прототипы и их действующие регрессии. Список обязательных тестов сохранён. |
| Stage1 | Foundation с отрицательными проверками и отчётами, привязанными к исходникам. |
| Stage2 | AC-28 и AC-B05 с наблюдаемыми результатами. |
| Stage3 | Все AC из требований MVP, MVP/BLOCKED и MVP/PAUSED. Независимый DR, приёмка нагрузки, подписи выпуска и требования P0 обязательны. |
| Stage4/5 | Только соответствующие строки post-MVP. Гарантии запускаемых привилегированных операций проверяются при их включении. |
