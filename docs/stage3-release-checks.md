# Проверки перед выпуском MVP

## Подпись кандидата издателем

Изолированный компьютер издателя формирует пакет из подготовленного архива updater и трёх OCI-дайджестов. Команда принимает закрытый 32-байтный seed Ed25519 в файле с правами `0600` или `0400`.

```sh
python -m deploy.build_update_release \
  --output release-1.2.0 --updater hostorbit-updater-linux-amd64-1.2.0.tar.zst \
  --signing-key /secure/hostorbit-release.seed \
  --version 1.2.0 --installed 1.1.0 --min-bootstrap 1.0.0 --min-release 1.1.0 \
  --schema-from 3 --schema-to 3 --vault-format 1 \
  --web-digest "$WEB_DIGEST" --api-digest "$API_DIGEST" --worker-digest "$WORKER_DIGEST"
```

Версии и форматы в примере иллюстрируют параметры. Задайте реальные значения выпуска. В выходной каталог попадают только архив, манифест и подпись. Скрипт проверяет их штатным верификатором перед публикацией каталога. Передайте ключ проверки владельцу отдельно от кандидата. Для запуска через Supervisor подготовьте статически связанный Linux amd64-бинарник `hostorbit-updater` с командой `--self-test`: код 0 означает успех, проверка укладывается в 10 секунд. Архив USTAR/Zstandard должен содержать только этот файл с правом исполнения.

```sh
tar --format=ustar --zstd -cf hostorbit-updater-linux-amd64-1.2.0.tar.zst hostorbit-updater
```

## Проверка кандидата на контроллере

`python deploy/update_release.py` сверяет канонический JSON и подпись Ed25519 с отдельно установленным ключом издателя. В каталоге кандидата ожидаются `release.json`, его двоичная подпись `release.sig` и файл `hostorbit-updater-linux-amd64-<version>.tar.zst`. Подписанное описание версии включает минимальные версии bootstrap и выпуска, пару схем SQLite, формат Vault, идентификатор ключа, OCI-дайджесты WebUI, API и Worker, размер и SHA-256 архива.

Передайте текущую версию, версию bootstrap, локальный нижний порог версии, текущую схему и формат Vault через параметры `--installed`, `--bootstrap`, `--minimum-release`, `--schema` и `--vault-format`. Укажите путь к независимо полученному открытому ключу в `--trust-key`. Формат ключа совпадает с открытым ключом подписанного установщика. Значения должны относиться к проверяемому экземпляру.

`CANDIDATE_VERIFIED` подтверждает проверку кандидата в момент чтения. Установленный контроллер, A/B-слоты и рабочая SQLite остаются без изменений. Перед выпуском ещё нужны привязка к допуску host supervisor, атомарное переключение с аварийным восстановлением и проверенная миграция рабочей БД. [Репетиция миграции](stage1-migrations.md)

## Репетиция переключения A/B

Запустите из checkout в окружении HostOrbit:

```sh
python -m deploy.rehearse_update ./release-1.2.0 \
  --trust-key /secure/hostorbit-release.pub \
  --installed 1.1.0 --bootstrap 1.0.0 --minimum-release 1.1.0 \
  --schema 2 --vault-format 1 --migration-review ./migration-review
```

Укажите ключ, принадлежащий пользователю, запускающему репетицию. При изменении схемы требуется каталог завершённой [репетиции миграции](stage1-migrations.md) для той же пары схем. При неизменной схеме опустите `--migration-review`.

Команда копирует пакет в приватный временный слот B, повторно проверяет подпись и содержимое, атомарно переключает указатель A → B и проверяет возможность возврата на A. Сбой проверки после переключения возвращает `UPDATE_REHEARSAL_ROLLED_BACK` и код 1. Репетиция проверяет файлы пакета и SQLite-копии. Службы Controller и исполняемый updater запускаются только в отдельной приёмке с допуском host supervisor.

## Выбор пакета updater через Supervisor

С root-консоли в доверенном checkout можно выбрать проверенный пакет с неизменной схемой БД. Подготовьте локальный файл явного допуска с правами `0600` и полями `plan_id`, `revision`, `approval_id` и `release_sha256`. Идентификаторы имеют формат ULID. SHA-256 должен совпадать с результатом независимой проверки выбранного манифеста.

```sh
sudo /opt/hostorbit/venv/bin/python -m deploy.supervised_update ./release-1.2.0 \
  --trust-key /etc/hostorbit/release.pub --approval /root/update-approval.json \
  --installed 1.1.0 --bootstrap 1.0.0 --minimum-release 1.1.0 \
  --schema 3 --vault-format 1
```

Команда запрашивает у Supervisor допуск для точной ревизии и подписанного манифеста. Пакет копируется в приватный каталог, а указатель `active` меняется атомарно только в `MAINTENANCE`. После проверки активного пакета команда запускает `--self-test` в отдельном временном корне systemd с непривилегированным UID и без доступа к сети. Supervisor получает подтверждение для возобновления после успешного завершения проверки. Выбранная версия, прежний слот и незавершённая операция хранятся в `/var/lib/hostorbit/update-slots`.

Если перепроверка пакета, запуск `--self-test` или подтверждение Supervisor не проходят, указатель возвращается на предыдущий слот. При ошибке после запроса обслуживания остаётся `pending.json`. Новый запуск заблокирован до сверки журнала Supervisor, текущего слота и точного дайджеста. Самостоятельное снятие блокировки по тайм-ауту запрещено. При принудительной остановке процесса текущий указатель сверяют по этому журналу перед любыми повторными действиями.

`UPDATER_PACKAGE_SELECTED` с `self_test: PASSED` означает, что пакет выбран и бинарник прошёл изолированную проверку запуска. Замена рабочих служб и миграция рабочей БД выполняются в отдельном процессе обновления, который ещё предстоит реализовать.

## Синтетическая нагрузка на API и SQLite

Из корня репозитория в Python-окружении с `requirements-dev.txt`:

```sh
python -m tools.capacity_soak --warmup 0 --seconds 10
```

Без параметров выполняются 30 минут прогрева и 8 часов измерения. Тест создаёт отдельную временную SQLite с 25 VPS, 200 контейнерами и 30 днями синтетических наблюдений. Четыре параллельных запроса читают инвентарь, карточку, аудит и сессию. Один последовательный писатель проводит тестовое SSH-наблюдение через переходы очереди. Тестовые SSH-результаты формируются локально.

Отчёт содержит число запросов, p95/p99 по маршрутам, неожиданные HTTP-ответы, проверку отсутствия тестовых секретов в ответах, максимальный размер WAL и проверку целостности базы и аудита. CI выполняет короткий smoke. Полная приёмка AC-45 и AC-A22 требует отдельного Ubuntu-стенда с установленным Controller, реальными SSH-наблюдениями, проверкой квот и полным профилем из ТЗ.
