# Проверки перед выпуском MVP

## Решение о приёмке Stage3

**21 ноября 2026 года владелец принял Stage3 целиком.** На момент решения зафиксированы результаты 20 из 72 обязательных критериев. Ещё 52 критерия имеют статус `NOT_RUN` в реестре. Валидатор по-прежнему учитывает результаты отдельных проверок.

## Результаты проверок

Из 72 обязательных критериев **20 имеют PASS**, **52 остаются NOT_RUN**. По результатам CI закрыты AC-01 (локальный bootstrap на чистой установке), AC-03 (подмена SSH-отпечатка) и AC-26 (клавиатурные сценарии и текст предупреждений на RU/EN). [Реестр Stage3](spec/HostOrbit_Requirements_Registry_v2.4.json)

Владелец принял локальный прогон восстановления при полном отказе VM Controller. **RPO 2:06**, **RTO 4:59** до входа Owner по HTTPS и проверки Audit и Outbox. Восстановленный Controller остался в `READ_ONLY_RECOVERY`, одна цель осталась в `QUARANTINED`. VM использовали общий физический хост. Ручная активация, правила хранения и два офлайн-носителя recovery identity требуют отдельных проверок. [Протокол и сверка результатов](../evidence/verification/stage3-acceptance-review.json)

## Подпись кандидата издателем

Изолированный компьютер издателя формирует пакет из подготовленного архива updater и трёх OCI-дайджестов. Команда принимает закрытый 32-байтный seed Ed25519 в файле с правами `0600` или `0400`.

```sh
python -m deploy.build_update_release \
  --output release-1.2.0 --updater hostorbit-updater-linux-amd64-1.2.0.tar.zst \
  --signing-key /secure/hostorbit-release.seed \
  --version 1.2.0 --installed 1.1.0 --min-bootstrap 1.0.0 --min-release 1.1.0 \
  --schema-from 3 --schema-to 3 --vault-format 1 \
  --web-digest "$WEB_DIGEST" --api-digest "$API_DIGEST" --worker-digest "$WORKER_DIGEST"
```

Версии и форматы в примере иллюстрируют параметры. Задайте реальные значения выпуска. В выходной каталог попадают только архив, манифест и подпись. Скрипт проверяет их штатным верификатором перед публикацией каталога. Передайте ключ проверки владельцу отдельно от кандидата. Для запуска через Supervisor подготовьте статически связанный Linux amd64-бинарник `hostorbit-updater` с командой `--self-test`: код 0 означает успех, проверка укладывается в 10 секунд. Архив USTAR/Zstandard должен содержать только этот файл с правом исполнения.

```sh
tar --format=ustar --zstd -cf hostorbit-updater-linux-amd64-1.2.0.tar.zst hostorbit-updater
```

## Проверка кандидата на контроллере

`python deploy/update_release.py` сверяет канонический JSON и подпись Ed25519 с отдельно установленным ключом издателя. В каталоге кандидата ожидаются `release.json`, его двоичная подпись `release.sig` и файл `hostorbit-updater-linux-amd64-<version>.tar.zst`. Подписанное описание версии включает минимальные версии bootstrap и выпуска, пару схем SQLite, формат Vault, идентификатор ключа, OCI-дайджесты WebUI, API и Worker, размер и SHA-256 архива.

Передайте текущую версию, версию bootstrap, локальный нижний порог версии, текущую схему и формат Vault через параметры `--installed`, `--bootstrap`, `--minimum-release`, `--schema` и `--vault-format`. Укажите путь к независимо полученному открытому ключу в `--trust-key`. Формат ключа совпадает с открытым ключом подписанного установщика. Значения должны относиться к проверяемому экземпляру.

`CANDIDATE_VERIFIED` подтверждает проверку кандидата в момент чтения. Затем применяется отдельная команда выбора пакета через Supervisor. Обновление API и Worker с рабочей миграцией выполняется отдельной командой. Прогон обновления и восстановления после аварии с systemd и Docker Compose требуется для выпуска. [Миграция Controller](stage1-migrations.md)

## Репетиция переключения A/B

Запустите из checkout в окружении HostOrbit:

```sh
python -m deploy.rehearse_update ./release-1.2.0 \
  --trust-key /secure/hostorbit-release.pub \
  --installed 1.1.0 --bootstrap 1.0.0 --minimum-release 1.1.0 \
  --schema 2 --vault-format 1 --migration-review ./migration-review
```

Укажите ключ, принадлежащий пользователю, запускающему репетицию. При изменении схемы требуется каталог завершённой [репетиции миграции](stage1-migrations.md) для той же пары схем. При неизменной схеме опустите `--migration-review`.

Команда копирует пакет в приватный временный слот B, повторно проверяет подпись и содержимое, атомарно переключает указатель A → B и проверяет возможность возврата на A. Сбой проверки после переключения возвращает `UPDATE_REHEARSAL_ROLLED_BACK` и код 1. Репетиция проверяет файлы пакета и SQLite-копии. Службы Controller и исполняемый updater запускаются только в отдельной приёмке с допуском host supervisor.

## Выбор пакета updater через Supervisor

С root-консоли в доверенном checkout можно выбрать проверенный пакет с неизменной схемой БД. Для команды нужен Python 3.15 с модулем `compression.zstd`. Установщик из репозитория проверяет его при сборке Python. Подготовьте локальный файл явного допуска с правами `0600` и полями `plan_id`, `revision`, `approval_id` и `release_sha256`. Идентификаторы имеют формат ULID. SHA-256 должен совпадать с результатом независимой проверки выбранного манифеста.

```sh
sudo /opt/hostorbit/venv/bin/python -m deploy.supervised_update ./release-1.2.0 \
  --trust-key /etc/hostorbit/release.pub --approval /root/update-approval.json \
  --installed 1.1.0 --bootstrap 1.0.0 --minimum-release 1.1.0 \
  --schema 3 --vault-format 1
```

Команда запрашивает у Supervisor допуск для точной ревизии и подписанного манифеста. Пакет копируется в приватный каталог, а указатель `active` меняется атомарно только в `MAINTENANCE`. После проверки активного пакета команда запускает `--self-test` в отдельном временном корне systemd с непривилегированным UID и без доступа к сети. Supervisor получает подтверждение для возобновления после успешного завершения проверки. Выбранная версия, прежний слот и незавершённая операция хранятся в `/var/lib/hostorbit/update-slots`.

Если перепроверка пакета, запуск `--self-test` или подтверждение Supervisor не проходят, указатель возвращается на предыдущий слот. При ошибке после запроса обслуживания остаётся `pending.json`. Новый запуск заблокирован до сверки журнала Supervisor, текущего слота и точного дайджеста. Самостоятельное снятие блокировки по тайм-ауту запрещено. При принудительной остановке процесса текущий указатель сверяют по этому журналу перед любыми повторными действиями.

`UPDATER_PACKAGE_SELECTED` с `self_test: PASSED` означает, что пакет выбран и бинарник прошёл изолированную проверку запуска. Рабочие службы API и Worker обновляет `deploy.application_update`. Для выпуска требуется прогон с реальными systemd и Docker Compose и проверкой отказов до и после фиксации SQLite. [Применение обновления](stage1-migrations.md)

## Синтетическая нагрузка на API и SQLite

Из корня репозитория в Python-окружении с `requirements-dev.txt`:

```sh
python -m tools.capacity_soak --warmup 0 --seconds 10
```

Без параметров выполняются 30 минут прогрева и 8 часов измерения. Тест создаёт отдельную временную SQLite с 25 VPS, 200 контейнерами и 30 днями синтетических наблюдений. Четыре параллельных запроса читают инвентарь, карточку, аудит и сессию. Один последовательный писатель проводит тестовое SSH-наблюдение через переходы очереди. Тестовые SSH-результаты формируются локально.

Отчёт содержит число запросов, p95/p99 по маршрутам, неожиданные HTTP-ответы, проверку отсутствия тестовых секретов в ответах, максимальный размер WAL и проверку целостности базы и аудита. CI выполняет короткий smoke. Для полного профиля используйте [прогон на локальной Ubuntu VM](#восьмичасовой-прогон-на-локальной-ubuntu-vm).

## Локальные проверки безопасности и WebUI

Используйте Python и Node из CI, установите версии из `requirements-dev.txt` и `web/package-lock.json`. Запускайте из корня checkout. Для фикстуры WebUI нужен OpenSSL. По умолчанию Playwright использует свой Chromium. Для установленного Chromium задайте `HOSTORBIT_CHROMIUM` абсолютным путём к бинарнику.

```sh
python -m pip install -r requirements-dev.txt
python -m tools.stage3_security > stage3-security.json
npm --prefix web ci
npm --prefix web run build
(cd web && npx playwright install chromium)
npm --prefix web test -- accessibility.spec.ts
```

Проверки безопасности охватывают локальный bootstrap Owner, область RBAC, жизненный цикл сессий, CSRF, обработку ошибок и использование ссылки на секрет в Worker/Broker. WebUI открывается через loopback HTTPS. В RU и EN тест проходит вход, переход к содержимому, выбор VPS, журнал, настройки и выход с клавиатуры. Ошибка входа объявляется как предупреждение, а устаревшее наблюдение объясняется текстом.

[Наблюдения по локальным проверкам](../evidence/verification/stage3-local.json) связаны с AC через `verification_path` в [реестре](spec/HostOrbit_Requirements_Registry_v2.4.json). Для приёмки применяются штатные `status` и `evidence_path`.

## Восьмичасовой прогон на локальной Ubuntu VM

Создайте одноразовую Ubuntu Server 24.04 VM с 1 vCPU, 2 ГиБ ОЗУ, SSD 40 ГиБ и отдельным зашифрованным backup-хранилищем. Зафиксируйте версию образа, конфигурацию VM и дайджест сборки. Внутри VM подготовьте раздельный каталог для результатов и каталог SQLite на SSD.

Для проверки SQLite и API с заранее созданной 30-дневной историей запустите синтетический профиль с точным лимитом API-пользователя. Первый прогон можно сократить параметрами `--warmup 0 --seconds 4`.

```sh
python -m tools.capacity_soak --work-dir /path/on/controller-ssd \
  --warmup 1800 --seconds 28800 --check-quota > stage3-sqlite-soak.json
```

Для нагрузочного прогона установленного Controller подготовьте HTTPS reverse proxy с loopback-адресом и доверенным сертификатом для IP. [Установка Controller и подготовка целей](stage1-installation.md) Подключите 25 изолированных целей со штатным restricted SSH helper. Подготовьте суммарно 200 тестовых контейнеров, проверьте их первым наблюдением и запишите 25 ID целей в файл `fixture-targets.txt`, по одному в строке. Для реального профиля требуется 30-дневная связанная история Audit, Jobs и метрик в установленной БД. Синтетический профиль генерирует свою историю в отдельной временной БД.

Выделите отдельную учётную запись фикстуры с доступом к инвентарю, аудиту и наблюдениям. Запустите в интерактивном терминале VM. Пароль считывается без эха.

```sh
python -m tools.capacity_controller --disposable-fixture \
  --origin https://127.0.0.1:9443 --ca ./fixture-ca.pem \
  --targets ./fixture-targets.txt --username fixture-owner \
  --warmup 1800 --seconds 28800 --check-quota > stage3-controller-soak.json
```

Прогон проверяет согласованность списка целей и число наблюдаемых контейнеров, затем чередует четыре чтения Web API и запрос или проверку результата одного штатного SSH-наблюдения. p95/p99 считаются отдельно по каждому API-маршруту и включают только чтение. После измерения отдельный всплеск запускает 100 чтений одновременно и сверяет документированный лимит 120 запросов в минуту. Запишите все ожидаемые отказы штатных защит отдельно от неожиданных ответов, сетевых ошибок и тайм-аутов.

В SQLite-отчёте время `begin` включает открытие соединения и ожидание блокировки, а `commit` включает фиксацию и закрытие соединения. Отчёт содержит численность выборки и p95/p99 транзакций SQLite, максимальный размер WAL, результат checkpoint и проверки целостности. Для приёмочного стенда отдельно соберите реальные показатели ожидания writer lock, длительности транзакций, `SQLITE_BUSY`, fsync, роста WAL, checkpoint и планы запросов. Сохраните только метрики и очищенные журналы.

Полная приёмка AC-45 и AC-A22 дополнительно требует подтверждённого предела четырёх одновременных SSH-сеансов, двух конкурирующих утверждённых запросов на изменение с максимум одним исполняемым и десяти циклов остановки и запуска Worker. Сверьте их с аудитом и состояниями Jobs, зафиксируйте классификацию ошибок, состав стенда, профиль и заключение рецензента. Установленный профиль этого скрипта проверяет SSH-наблюдения, чтение и квоту. Сценарии с утверждёнными изменениями, сбоями Worker и метриками хранилища требуют отдельного протокола. [Требования к профилю](spec/HostOrbit_Technical_Spec_v2.4.md#нагрузочный-профиль)
