# Первая рабочая версия VPN-Orbit

Цель — дать одному владельцу возможность управлять своими VPS из браузера. Первый профиль хоста: Ubuntu Server 24.04 LTS amd64, OpenSSH по IPv4, systemd и Docker Compose v2. Для HTTPS используется Nginx; DNS настраивается вручную. Текущие статусы и критерии завершения ведутся в [README](../README.md#прогресс-первой-версии).

## Границы текущего onboarding

Сейчас веб-интерфейс подключает **заранее одобренную и подготовленную** VPS: владелец сверяет SSH fingerprint, проходит SSH-аутентификацию, после чего Controller регистрирует цель и запускает SSH-наблюдение. Это не означает, что браузер подготавливает чистый сервер.

Создание ограниченной сервисной учётной записи и установка VPN-Orbit SSH helper доступны отдельной локальной командой `tools/prepare_vps.py`. Она работает с Ubuntu 24.04 amd64 через уже доступную SSH-учётную запись администратора с `sudo`, проверяет fingerprint до изменений и сохраняет локальный журнал подготовки и ключи в закрытом каталоге. Скрипт настраивает ограниченный SSH-доступ и проверяет результат; он **не устанавливает Docker, Docker Compose и остальные зависимости приложений**. Их наличие и установка пока остаются отдельной операцией. Полный процесс — от чистой VPS до установки зависимостей и подключения — из браузера не выполняется.

Подключение в WebUI опирается на root-owned target policy Controller. Политика заранее закрепляет IP, порт, SSH host key, разрешённые CIDR, revision, зависимости, capabilities и ссылки на секреты. Регистрация через Web API не добавляет произвольную цель и не изменяет эту политику. Без явно установленной политики установка Controller не предоставляет целей для подключения.

## Контракт подготовки VPS и target policy

Целевой контракт подготовки: проверять SSH host key, ОС/архитектуру и возможность безопасно изменить SSH-конфигурацию до внесения изменений; ограничивать повторный запуск тем же адресом, портом и fingerprint; продолжать незавершённые фазы и проверять postconditions. Очистка должна удалять только артефакты, созданные VPN-Orbit, не присваивая себе и не удаляя заранее существующие системные ресурсы. Это критерии завершения подготовки, а не утверждение, что весь контракт уже доступен из браузера.

Для наблюдения используется отдельная системная учётная запись `vpn-orbit-svc`: только ключевая SSH-аутентификация, фиксированный `ForceCommand`, без shell, PTY, forwarding и пользовательских SSH hooks. Её ключи и root-owned helper устанавливаются с ограниченными правами; проверка выполняется через типизированный probe. Если для эксперимента включается firewall-подготовка, она использует отдельную учётную запись и отдельный ключ. Такая подготовка не означает, что управление firewall готово в пользовательском интерфейсе.

Target policy — защищённый root-owned файл установки Controller, а не пользовательский ввод Web API. Каждая цель должна явно задавать уникальный ID, numeric IP, порт, CIDR, закреплённый Ed25519 host key, `policy_revision`, список зависимостей, разрешённые capabilities и соответствующие им Secret References. Для `docker.restart` и `firewall.apply` требуются отдельные ссылки на ключи; секреты разных назначений не переиспользуются. Policy digest и revision связывают цель, ключи и разрешения; изменение любого из них требует контролируемого изменения root-политики и повторной проверки привязки. Установка без `--targets` создаёт пустую политику.

## Состояния операций и неопределённый результат

Операция проходит состояния `QUEUED` → `INTENT_PREPARED` → `DISPATCHING` → `EXECUTING` → `VERIFYING`, после чего завершается `SUCCEEDED`, `FAILED`, `UNKNOWN_OUTCOME` или `CANCELLED_SAFE`. Не каждый переход обязан быть виден клиенту, но журнал сохраняет подтверждённую последовательность.

- До возможной отправки удалённой команды операцию можно завершить как `CANCELLED_SAFE`.
- После начала dispatch потеря SSH-соединения, ответа или подтверждения эффекта не доказывает, что изменение не произошло. Такой исход фиксируется как `UNKNOWN_OUTCOME`, а не как обычный отказ.
- Терминальный `UNKNOWN_OUTCOME` не повторяется автоматически. Сначала требуется отдельная сверка сохранённых подтверждений; пока исход не разрешён, затронутые изменения блокируются.
- `SUCCEEDED` требует проверенного эффекта, а не только успешного SSH-ответа. Явный отказ до эффекта может завершиться как `FAILED`.

## Контракт firewall

В runtime и на VPS имеются типизированные компоненты firewall, но законченный браузерный процесс, включая приёмку интерфейса и end-to-end проверку, пока не готов. Наличие этих компонентов не означает готовность функции для обычного управления VPS.

Разрешённый план должен содержать только ограниченный набор правил: действие `allow`/`deny`, направление `in`/`out`, протокол TCP/UDP, порт и канонический CIDR; максимум 32 правила без дубликатов. План обязан сохранять входящий TCP-доступ на фактический SSH-порт. Свободный nftables-код и произвольная замена системных firewall-правил не допускаются. Исполнитель изменяет только таблицу VPN-Orbit, сохраняет предыдущую версию и использует root-owned журнал.

После применения удалённая сторона ставит независимый от Controller таймер отката (в текущем профиле — 60 секунд). Для подтверждения требуется новое SSH-соединение; затем выполняется явное подтверждение. Если проверка доступа или подтверждение не удаются, правила откатываются. Неподтверждённый откат или потеря ответа дают `UNKNOWN_OUTCOME`, блокирующий повтор до сверки. Перед готовностью функции нужны сквозные проверки сохранения SSH-доступа, таймера, отката после обрыва связи и поведения при перезапуске исполнителя.

## Контракт Compose-профилей и будущих сервисов

Поддерживаемые профили Compose должны быть явным allowlist VPN-Orbit, а не произвольным YAML или удалённой командой. Профиль фиксирует допустимые сервисы, образы по digest, конфигурационные параметры, необходимые Secret References, тома, сети, зависимости и ожидаемый жизненный цикл. Перед изменением Controller показывает владельцу типизированный diff и затронутую dependency closure; непосредственно перед dispatch повторно сверяет исходное состояние и отклоняет устаревший план.

Изменение ограничивается ресурсами, которыми профиль явно управляет. Удаление останавливает и удаляет только принадлежащие VPN-Orbit компоненты; данные, внешние тома, общие сети и другие общие ресурсы сохраняются. Неизвестный дрейф, неполная инвентаризация зависимостей и неоднозначный результат блокируют разрушительное действие. Для удаления данных требуется отдельная явная процедура и подтверждение, а не побочный эффект `compose down`.

Remnawave Panel/Node, Bedolaga Bot и Cabinet остаются будущими сервисами. Для каждого сервиса приёмка включает:

1. версионированный allowlisted профиль с закреплёнными образами и проверенными параметрами;
2. проверку предусловий, доступности портов, секретов, томов, сетей и dependency closure без изменения хоста;
3. повторную проверку drift перед применением, явное подтверждение владельца и аудит плана/результата;
4. идемпотентные установку, обновление и удаление с сохранением данных и ресурсов вне владения профиля;
5. проверяемый health/postcondition, понятную диагностику и безопасное поведение при потере связи или `UNKNOWN_OUTCOME`;
6. регрессионные тесты и сквозной прогон на отдельном стенде, включая сбои до/после dispatch и проверку сохранности общих ресурсов.

Первичная регистрация Remnawave Node остаётся в Remnawave Panel. Наличие этих критериев не означает, что любой из перечисленных сервисов уже реализован или принят.

## Флаг удалённых изменений

`remote_mutation_enabled: false` — значение release manifest и метаданных установки: сборка заявляет, что общий режим произвольных удалённых изменений не включён. Это не runtime-переключатель для каждой операции и не обещание, что в коде нет ни одного изменяющего действия: имеется узкое исключение для явно разрешённого тестового `docker.restart`. Фактический допуск всё равно определяется отдельной capability и root-owned policy цели.

Такой перезапуск возможен только для цели с явной capability в root-owned policy, отдельным ключом и Secret Reference, изолированным тестовым контейнером без mounts и зависимостей, свежим baseline, проверками Change Plan и явным подтверждением владельца. Это не разрешение на перезапуск произвольных контейнеров, произвольные команды или готовность развёртывания Compose-профилей. Firewall и будущие сервисы не считаются готовыми к общему удалённому управлению из-за наличия отдельных runtime-компонентов.

## Проверка выпуска и отложенные задачи

Поведение проверяется локальными тестами и сквозными сценариями на отдельном стенде; реальные пользовательские VPS не используются как тестовая среда. До выпуска должны быть приняты соответствующие критерии выше и текущие статусы README. Резервное копирование и восстановление, перенос старой базы VPN-Orbit и расширенный интерфейс аудита остаются отдельными задачами, если не будут включены в явный scope выпуска.
