# Поэтапный план улучшений

База, статусы и доказательства ID — [AUDIT_REPORT](AUDIT_REPORT.md). Никакой пункт этого плана не отменяет историческую приёмку и не включает remote mutation до выполнения gates.

## 1. Восстановить проверяемость main — P1

**AUD-01.** Зафиксировать код и точные входы, повторить необходимые app/runtime и реальные boundary jobs для пяти затронутых capabilities, выпустить новые revision-specific evidence и добиться прохождения Stage0/Stage1 gates. Исторические отчёты не перезаписывать как будто они проверяли новый SHA.

**Готово:** обязательный CI зелёный на том же SHA, hashes и тесты в evidence воспроизводимы; открытые Stage2/3 остаются честно NOT_RUN. Зависимостей на новые runtime-функции нет.

## 2. Сделать backup и восстановление согласованными — P1

**AUD-02.** Зафиксировать общий размерный контракт для plaintext tar и ciphertext, включая framing/encryption. До дорогостоящего capture выявлять заведомо невозможные объёмы, а итог проверять до предоставления пригодного результата. Указать ограничение и ресурсные требования оператору.

**Готово:** действительный end-to-end signed backup → offline Rescue → новый Controller на границах размеров; превышение корректно отклоняется без ложной restore-пригодности, авторитетный старый backup не повреждается. До расширения предела — отдельно доказать отсутствие plaintext на диске, пиковую RAM и работу при ENOSPC.

## 3. Согласовать журнал после восстановления — P2

**AUD-04.** Спроектировать terminal event для каждого quarantined Job, включая queued и dispatched, и миграционную обработку уже восстановленных состояний. Не менять исходную попытку на вымышленный успех.

**Готово:** Job/status/timeline и hash chain консистентны после полного import/install/restart; неопределённый исход сохраняется и не запускается повторно.

## 4. Защитить release inputs — P1

**AUD-03.** Собрать wheel из чистого экспорта фиксированного commit; проверить заранее доверенные wheel hashes перед сборкой подписи; отделить signing от доверия к network index. Сохранить offline installation и проверяемую историю SBOM.

**Готово:** untracked/ignored Python-файл в исходном рабочем дереве не попадает в bundle; подмена колеса до подписи отклоняется; manifest точно связывает источники и подписанные артефакты. Проверить на Python 3.13 и поддерживаемой архитектуре.

## 5. Измерить и устранить реальные пределы — P2

**AUD-05/AUD-06.** Сначала throttled SFTP и capacity dataset по ТЗ §37. Затем подобрать bounded timeout с обнаружением отсутствия прогресса; для истории — минимальный индекс с миграцией только по результатам плана запроса и p95. Установить byte budgets/retention, не удаляя последнюю проверенную копию, открытые incidents или необходимый Audit.

**Готово:** публикация и retry проходят при документированной минимальной полосе; soak на 25 VPS/200 объектов укладывается в критерии, измерены SQLITE_BUSY, p95, рост WAL и восстановление после прерывания. Миграция проходит restore старых схем.

## 6. Усилить тесты и CI

Исполнить матрицу из [TEST_COVERAGE_REVIEW](TEST_COVERAGE_REVIEW.md): независимый DR, UID/socket, реальные SFTP и SSH отказы, accessibility и supply-chain negative tests. Проверять, что job на main не только запущен, но относится к правильному SHA; обеспечить обязательный статус проверок для merge после проверки настроек защиты ветки (в этом аудите они не подтверждены).

## 7. Продолжить Stage2, затем Stage3

Реализовать один ограниченный вертикальный сценарий AC-28: зарегистрированная VPS → наблюдение → versioned plan/preflight → risk-based backup gate → approval → typed Docker action через authority/broker → подтверждение delegated effects → Audit и reconciliation. Только после end-to-end fault injection и AC-B05 выходить к расширению adapters. Stage3 требует всех обязательных AC, независимого DR, release/update и capacity evidence.

**Не делать заранее:** переходить на микросервисы, PostgreSQL, внешний брокер, общий plugin framework или расширять SSH команды без доказанной потребности и нового threat model.
