# K-VPN Monitor Kit: панель, Telegram, несколько нод

Мониторинг — отдельный компонент, который можно установить **без переустановки Remnawave Node**. Он проверяет **TCP-доступность**, а не всю VLESS/REALITY/gRPC/XHTTP-цепочку. Рабочие VPN-профили, UFW и Docker установщик мониторинга не перенастраивает.

## Архитектура

- **Monitoring panel** (например Host-Panel): принимает отчёты по **SSH** от пользователей `kvpn-probe`, оценивает статусы и отправляет уведомления в **Telegram-группу/тему**. Это не интерфейс Remnawave Panel.
- **RU probe (`monitor ru`)**: на RU-сервере проверяет TCP-подключение к заданному Foreign `IP:port` и отправляет `OK`/`FAIL` на панель.
- **Foreign probe (`monitor foreign`)**: на Foreign-сервере проверяет локальный `127.0.0.1:port` и также отправляет статус на панель.

Каждая проверка имеет собственный **Probe ID**, SSH-ключ и systemd-таймер. Несколько проверок могут работать на одном сервере. `ru1-nl1`, `ru1-nl2`, `nl1-local` — **примеры имён**, не фиксированные значения.

## Шаг 1 — Telegram-бот и тема

Создайте отдельного бота через **@BotFather**. Добавьте бота в нужную Telegram-группу с темами и дайте ему возможность отправлять сообщения. Подготовьте:

- **Bot token** — секрет, вводится в скрытом поле TUI (не присылайте его никому).
- **`chat_id` группы** — для супергруппы часто отрицательный ID, например вида `-100…`.
- **`message_thread_id` темы** — *числовой* ID конкретного топика. Это **не** ссылка на чат и не имя темы. Его можно найти в `message_thread_id` соответствующего сообщения в Bot API `getUpdates`, если бот получает такие обновления (параметры приватности/доступа влияют на возможность получения); либо получить через ваш проверенный администраторский инструмент.

Хранить токен в URL, shell history, логах или примерах не нужно. Если токен раскрыт — отзовите его через BotFather.

## Шаг 2 — установить центральный приёмник

На **сервере мониторинга**, где ещё нет K-VPN Monitor Kit:

```bash
sudo bash kvpn-install.sh monitor panel
```

Или TUI → `Мониторинг` → `Установить приёмник и Telegram-бота`. Укажите `chat_id`, `message_thread_id` и токен. Результат — `kvpn-monitor-kit.timer` и системный пользователь `kvpn-probe` с ограниченными правами. Параметры и токен хранятся в `/etc/kvpn-monitor` (права root-only), отчёты — в `/var/lib/kvpn-monitor`.

На **этом же сервере**, через **доверенную консоль** узнайте SSH host fingerprint:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Значение вида `SHA256:…` потребуется агентам. Сравнивайте с отпечатком **из консоли панели**, а не с непроверенным выводом `ssh-keyscan` из сети: это защита от подмены SSH-сервера.

Проверьте отправку в тему:

```bash
sudo bash kvpn-install.sh monitor test-telegram
```

Убедитесь, что тестовое сообщение действительно видно в нужной теме. Если бот не может отправлять сообщения — проверьте chat_id, thread_id, права бота и исходящий HTTPS-доступ к Telegram.

## Шаг 3 — создать проверку на RU или Foreign

На **RU-ноде** для проверки удалённого Foreign:

```bash
sudo bash kvpn-install.sh monitor ru
```

Введите:

- **Probe ID**: уникальный идентификатор, например `ru1-nl1`.
- **Monitoring panel IP/hostname** и SSH port (обычно `22`). Этот адрес — **панель мониторинга**, не обязательно Remnawave Panel.
- **Foreign host**: IP/домен зарубежной ноды для проверки, например `198.51.100.10`.
- **TCP port**: реальный порт Xray на Foreign (пример `8443`).
- **SSH SHA256 fingerprint** панели, независимо проверенный на шаге 2.

На **Foreign-ноде** для локальной проверки порта (например, `8443`):

```bash
sudo bash kvpn-install.sh monitor foreign
```

Нужно указать Probe ID (например, `nl1-local`), панель мониторинга, порт SSH, локальный TCP-порт и проверенный отпечаток. `127.0.0.1` выбирается автоматически; вводить IP Foreign в поле цели не нужно.

**Безопасность:** агент получает SSH host key через `ssh-keyscan`, сверяет его **с введённым отпечатком** и при несовпадении прекращает настройку. Появившееся `Could not fetch…` означает сетевую проблему/таймаут, а **не** повод отключать проверку SSH-ключа.

После успешной установки агент покажет **публичный** ключ, начинающийся с `ssh-ed25519 AAAA…`. Таймер пока **не запускается**. Публичный ключ можно в любой момент снова увидеть:

```bash
sudo bash kvpn-install.sh monitor public-keys
```

В TUI: `Мониторинг` → `Показать публичные SSH-ключи агентов`. Не передавайте приватные файлы `*.key`, используйте **только** `*.key.pub`.

## Шаг 4 — зарегистрировать агента на панели

Вернитесь на **сервер мониторинга**:

```bash
sudo bash kvpn-install.sh monitor register
```

Поля вводятся **в таком порядке**:

1. **Probe ID** — точно такой же, как на агенте.
2. **Readable name** — понятная подпись в Telegram, например `Node-RU → Foreign TCP 8443`.
3. **Node PUBLIC ssh-ed25519 key** — **вся строка** из `.key.pub`, **не IP-адрес**.
4. **Source IP** — публичный **исходящий IP**, с которого агент делает SSH-подключение к панели (при NAT может отличаться от адреса VPS). Это **не** порт, не fingerprint и не ключ.
5. **Stale threshold [720]** — сколько секунд не получать отчётов до `UNKNOWN`.
6. **Consecutive failures [2]** — число последовательных `FAIL` для тревоги.
7. **Successes to recover [1]** — число `OK`, необходимое для уведомления о восстановлении.

Пример (все адреса заменяйте своими): `Probe ID=ru1-nl1`, `Source IP=192.0.2.11`. Публичный SSH-ключ **не** начинается с `SHA256:` (это отпечаток ключа панели, совершенно другое поле).

Панель привязывает ключ к одному Probe ID и Source IP. Повторная регистрация того же ключа и параметров безопасна; заменить ключ/адрес существующей регистрации автоматически нельзя.

Проверьте, что **Node → monitoring panel TCP/22 (или ваш SSH-порт)** доступен, а UFW панели разрешает SSH с **именно этих** источников. Установщик не меняет sshd и UFW панели; если нужно открывать SSH, делайте это вручную и адресно, не для всего Интернета.

## Шаг 5 — запустить таймер именно на агенте

Возвратитесь на **ту RU/Foreign-ноду**, где создавали проверку:

```bash
sudo systemctl enable --now 'kvpn-monitor-kit-probe@ru1-nl1.timer'
sudo systemctl start 'kvpn-monitor-kit-probe@ru1-nl1.service'
sudo journalctl -u 'kvpn-monitor-kit-probe@ru1-nl1.service' -n 20 --no-pager
```

Замените `ru1-nl1` на **свой Probe ID**. `Probe ru1-nl1: OK` означает доступность TCP; `STATUS_ACCEPTED` — приём отчёта по SSH. Если видите `Permission denied`, проверьте регистрацию ключа и Source IP на панели.

## Шаг 6 — проверить приём и Telegram-оценку на панели

На **сервере мониторинга**:

```bash
sudo bash kvpn-install.sh monitor status
sudo systemctl start kvpn-monitor-kit.service
sudo journalctl -u kvpn-monitor-kit.service -n 30 --no-pager -o cat
```

В статусе панели ожидается `ru1-nl1: OK` (или ваш ID); физический отчёт находится в `/var/lib/kvpn-monitor/reports/<ID>.status`, а состояния — `/var/lib/kvpn-monitor/state.json`. Первая оценка может показывать `INIT` до первого отчёта. В штатной работе Telegram **не присылает «OK» каждую минуту**: отправляются тревоги `FAIL`/`UNKNOWN` и сообщения `RECOVERED`.

**Интервалы:** агент — примерно каждые **5 минут** после окончания предыдущей проверки; панель анализирует состояние примерно каждую минуту. По умолчанию `FAIL` после **2** отдельных ошибок, `UNKNOWN` при отсутствии свежих отчётов **более 720 секунд**, восстановление после **1** удачного результата. Фактическое время может различаться из-за systemd timers и сети.

## Масштабирование и обслуживание

Чтобы добавить `ru1-nl2`, снова выполните `monitor ru` на той же RU-ноде **с новым ID**, зарегистрируйте новый ключ на панели и запустите **новый** таймер. Аналогично можно добавлять Foreign local probes. Не запускайте `monitor panel` второй раз: повторная установка панели **блокируется**. Изменение существующей конфигурации/обновление поверх неё автоматически **не поддерживается**.

## Что мониторинг НЕ проверяет

TCP connect не проверяет Xray-протокол, ключи, балансировку, DNS клиента, аутентификацию, подписки, NAT/маршруты или фактический выход в Интернет. Для полноценной доступности VPN нужны дополнительные независимые end-to-end тесты, которых этот комплект не содержит.
