# Stage2: инвентарь зарегистрированных VPS

Первый компонент Stage2 по FR-006/FR-018 из [ТЗ v2.4](spec/HostOrbit_Technical_Spec_v2.4.md): список и карточка уже локально зарегистрированных ресурсов. Существующие Auth, SQLite schema 2 и очередь наблюдений остаются источниками истины. Реализация использует FastAPI и стандартную библиотеку без новых зависимостей.

Выбран read model поверх существующей очереди: новый постоянный snapshot потребовал бы миграции и второго источника состояния. Регистрация через Web и обнаружение Docker/Nginx требуют отдельных контрактов и сюда не входят. Stage2/AC-28 этим компонентом не принимаются.

## Контракт

- `GET /api/v1/resources?after=<ULID>&limit=50`: только доступные по `vps:read` ресурсы, сортировка по ID, максимум 100 записей и `next_after`. Disabled-ресурсы остаются видимы.
- `GET /api/v1/resources/{id}`: 404 для отсутствующего или недоступного ресурса. Обе операции требуют действительную HTTPS-сессию и возвращают ETag/no-store.
- Метаданные: ID, revision, enabled, policy revision, даты регистрации/обновления. Policy digest, IP, ключи, Secret References, permits и actor IDs не публикуются.
- Наблюдение: `NOT_CHECKED` до завершённой попытки; `REACHABLE` только после успешного host.probe с текущими scope/policy и временем не старше 300 секунд, не позже текущего времени. Это SSH helper reachability, не здоровье приложений.
- Ошибка/UNKNOWN, смена scope, отключение ресурса, просроченная выборка и откат часов дают `UNKNOWN` с причиной. Последняя успешная выборка сохраняется отдельно как историческая, вместе с timestamp. Новая ожидающая попытка не стирает последнюю завершённую.
- Результат проецируется на фиксированные поля helper observation; произвольные данные job/credentials не сериализуются. Чтение не ставит задания, не выполняет SSH и не изменяет схему.
- После добавления маршрутов повторно проверяются Auth/RBAC и два затронутых capability reports; историческая приёмка сохраняется. Новая проверка явно автоматическая.

## Проверка границ

Недоступные ресурсы исключаются до pagination; завершённые попытки упорядочиваются по sequence события `job.finished`, даже при одинаковых timestamps; stale scope не оживляет старый успех; clock rollback не создаёт свежую выборку; лишние JSON поля не попадают в API. Каждый случай закреплён application-тестом.

Сначала выбирается ограниченная страница ресурсов, затем последняя попытка и последний успех определяются одним проходом связанной Audit-истории без изменения схемы. В локальном in-memory сравнении на синтетических 100 000 событиях и 25 ресурсах запрос занимал около 48 мс против 95–97 мс прежнего; это не нормативное capacity-испытание. Работа по истории остаётся неограниченной, индекс с проверенной миграцией и восьмичасовой soak по ТЗ остаются задачами до capacity-приёмки.

## Обнаружение Docker и Nginx

Обновлённые `ssh-gateway` и `typed-helper` поддерживают фиксированный запрос `hostorbit.v2.probe`. После проверки SSH host key helper читает метаданные двух путей на Ubuntu, `/usr/bin/docker` и `/usr/sbin/nginx`. В `observation.last_success.software` возвращаются только значения `PRESENT`, `NOT_DETECTED` или `UNKNOWN` для `docker` и `nginx`. Они описывают наличие инструментов в этих путях. Состояние служб, контейнеров и проектов Compose требует отдельного наблюдения.

При тихом отказе старого gateway с кодом 65 Broker повторяет фиксированный запрос v1 в том же SSH-соединении. В таком результате поле `software` отсутствует. При установке v2 замените оба root-owned файла через действующую процедуру установки helper. Старый Controller может использовать v1 с обновлённой парой.

## Контейнеры импортированных Docker-проектов

Для probe v3 владелец вручную добавляет до восьми контейнеров импортированного тестового Compose-проекта в `/etc/hostorbit/docker-discovery.json` на VPS. Каталог принадлежит root и закрыт от записи группы и остальных пользователей. Файл принадлежит root, имеет режим `0600` и одну жёсткую ссылку.

```json
{
  "v": 1,
  "containers": [
    {
      "id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "project": "fixture",
      "service": "web"
    }
  ]
}
```

Замените пример на полный ID контейнера и значения Compose project/service из проверенного импорта. При пересоздании контейнера укажите новый ID после проверки импорта. Helper использует один ограниченный GET к локальному `/run/docker.sock` с фильтром по утверждённым ID и сверяет метки проекта и сервиса. В ответе v3 Controller получает только ID, проект, сервис и типизированное состояние. Карточка показывает время последнего успешного наблюдения. Состояние `RUNNING` описывает процесс контейнера, а доступность приложения проверяется отдельно.

Сводка Docker различает пустую область, некорректный защищённый файл и недоступность daemon. При gateway без поддержки v3 Broker выбирает v2 или v1 в том же закреплённом SSH-соединении после тихого отказа версии. Для v3 установите проверенные `ssh-gateway` и `typed-helper` по существующей [процедуре](stage1-runtime.md).

### Опубликованные порты Docker

Probe v4 использует тот же ограниченный GET и проверку Compose-меток. Для каждого контейнера в `observation.last_success.docker.containers` возвращается `published_ports` с адресом привязки IPv4/IPv6, портом хоста, портом контейнера и протоколом `tcp`, `udp` или `sctp`. Записи `EXPOSE` и прямой маршрутизации без порта хоста исключаются. Пустой массив означает, что Docker не сообщил опубликованных привязок. `null` означает, что данные для контейнера недоступны, неполны или превышают лимит в восемь привязок. Сводка описывает данные Docker на момент наблюдения. Проверка доступности порта и поиск конфликтов с другими слушателями остаются отдельными задачами.

При обновлении установите оба root-owned файла, `ssh-gateway` и `typed-helper`. Controller согласовывает версию с gateway и helper, включая v6/v5/v4/v3/v2/v1. В старых наблюдениях и ответах v3 поле `published_ports` отсутствует. Форма цели restart preview и Change Plan сохраняется.

### Подключённые тома и mounts

Probe v5 сохраняет сводку и порты. Для каждой работающей цели с совпавшими полным ID и Compose-метками helper дополнительно делает ограниченный read-only Docker inspect. В Controller поступает только `mount_status`: `NONE` при подтверждённом отсутствии настроенных mounts, `PRESENT` при наличии mount, `UNKNOWN` при неполных данных, несовпадении цели или недоступности приемлемого результата. Имена томов, пути, конфигурация и переменные окружения в ответ не входят.

Старые ответы v1–v4 не содержат подтверждения mounts. Для Backup Gate они эквивалентны неизвестному состоянию.

### Сетевая изоляция

Probe v6 переиспользует Docker inspect той же подтверждённой цели. `network_status` имеет значение `ISOLATED` при режиме Docker `none` и подтверждённом подключении только к сети `none`. `OTHER` означает другой режим либо дополнительное сетевое подключение. Неполные сведения, несовпадение цели и ответы старых версий дают неизвестное состояние. Имена сетей, IP и идентификаторы сетевых подключений Controller не получает.

### Зависимости тестового контейнера

Probe v7 проверяет узкий профиль выделенного Docker-стенда. Для работающей цели без mounts в сети `none` требуются частные PID, IPC, UTS и cgroup namespaces, read-only rootfs, сброс всех capabilities, отсутствие дополнительных capabilities, устройств, device rules, links и privileged mode. Допускаются runtime `runc` и только локальные драйверы логирования `local`, `json-file` или `none`. Затем read-only запрос с `all=1&limit=2` требует ровно один контейнер на демоне с полным ID и состоянием выбранной цели. Второй контейнер блокирует допуск, даже если он остановлен. Controller получает только `dependency_status`. Идентификаторы, конфигурация и сведения о других контейнерах не передаются.

`ISOLATED` подтверждает этот профиль на момент наблюдения, `OTHER` обозначает конфигурацию за его пределами, `UNKNOWN` — неполные данные. Helper v1–v6 не может подтвердить профиль. Owner отдельно подтверждает отсутствие воздействия на эксплуатационные сервисы.

## Локальные TCP-слушатели

На Linux-хосте с установленным HostOrbit можно проверить один TCP-порт в сетевом пространстве имён вызывающего процесса:

```bash
/opt/hostorbit/venv/bin/python -m hostorbit.runtime.listener_diagnostics --port 443
```

Команда читает локальную таблицу сокетов ядра и возвращает JSON с отдельными результатами для IPv4 и IPv6. `LISTENING` означает, что порт прослушивается по перечисленным адресам. `NOT_LISTENING` означает, что в таблице этого семейства слушателей для порта нет. При недоступной или некорректной таблице результат для семейства — `UNKNOWN`, код выхода — 1. Команда показывает адреса привязки на момент проверки, включая `0.0.0.0` и `::` без предположений о режиме dual-stack.

В локальном режиме отчёт содержит `external_reachability: NOT_TESTED`. Наблюдения опубликованных портов Docker в карточке VPS описывают настройки Docker. Локальный CLI проверяет сокеты в своём пространстве имён.

### Конфликт с локальными TCP-слушателями

```bash
python -m hostorbit.runtime.listener_diagnostics --port 443 --check-bind 0.0.0.0
```

Укажите планируемый IPv4 или IPv6 адрес привязки. `POSSIBLE_CONFLICT` перечисляет пересекающиеся TCP-слушатели. IPv6 wildcard учитывается консервативно, поскольку таблица сокетов не показывает режим dual-stack каждого сокета. Недоступная таблица нужного семейства даёт `UNKNOWN`, если конфликт пока не найден. В обоих случаях код выхода 1.

`NO_CONFLICT_OBSERVED` означает, что на момент чтения таблиц пересечения со слушателями не обнаружены. Команда не резервирует порт и не обнаруживает конфликты с сокетами вне состояния LISTEN или с другими сетевыми пространствами имён.

### TCP-доступность с другой машины

На машине в сети, из которой должен быть доступен сервис, запустите тот же модуль из установленного пакета HostOrbit. Укажите IP назначения и порт. Замените пример на адрес проверяемого хоста:

```bash
python -m hostorbit.runtime.listener_diagnostics --connect 203.0.113.20 --port 443
```

Режим `--connect` без дополнительных опций устанавливает одно TCP-соединение с тайм-аутом 3 секунды и сразу закрывает его. Он принимает числовой IPv4 или IPv6. IPv6-адреса, требующие выбора интерфейса, отклоняются. Результат `CONNECTED` подтверждает TCP-доступность из сети проверяющей машины в момент запуска. Он не подтверждает работу приложения, TLS или доступность из других сетей.

В случае отказа отчёт различает `REFUSED`, `TIMED_OUT`, `UNREACHABLE` и `ERROR`. Код выхода 0 означает успешное подключение, 1 — неуспешную попытку, 2 — неверные аргументы.

### TLS-сертификат на заданном IP

Чтобы проверить конкретный сервер до переключения DNS, передайте имя сайта через `--tls-name`. Замените тестовые IP и имя на значения для вашего сервера:

```bash
python -m hostorbit.runtime.listener_diagnostics --connect 203.0.113.20 --port 443 --tls-name site.example
```

Команда подключается к заданному IP и передаёт имя сайта в SNI. Она проверяет цепочку сертификатов по доверенным CA проверяющей машины, срок действия и имя в SAN. Для интернациональных имён укажите Punycode. На TCP и TLS выделяется до 3 секунд каждому.

В JSON TCP-результат и TLS-результат разделены. `tls.state: VERIFIED` подтверждает TLS-проверку, а `expires_at` содержит время окончания действия сертификата в секундах Unix. `CERTIFICATE_INVALID` означает отказ проверки сертификата, `TIMED_OUT` — тайм-аут, `ERROR` — другую ошибку TLS, `NOT_TESTED` — TCP-подключение не состоялось. В режиме `--tls-name` код 0 возвращается только при успешной TLS-проверке.

#### HTTPS-ответ на заданном IP

Добавьте `--https-path`, чтобы после проверки сертификата выполнить один HTTP/1.1 HEAD на том же соединении:

```bash
python -m hostorbit.runtime.listener_diagnostics --connect 203.0.113.20 --port 443 --tls-name site.example --https-path /healthz
```

Отчёт содержит HTTP-статус в `https.status`. Код выхода 0 соответствует ответу 2xx. Команда выводит 3xx и другие ответы без перехода по перенаправлениям и без чтения тела. Для пути требуется начальный слэш; не-ASCII символы кодируются как URL. При отказе TLS запрос не отправляется.

### Адреса домена после обновления DNS

После ручного обновления DNS проверьте, какие IPv4 и IPv6 адреса видит системный резолвер машины запуска:

```bash
python -m hostorbit.runtime.listener_diagnostics --resolve site.example --expect-ip 203.0.113.20 --expect-ip 2001:db8::20
```

Повторите `--expect-ip` для каждого ожидаемого адреса. Совпадение полного набора возвращает `MATCH`. При `MISMATCH` отчёт перечисляет отсутствующие и лишние адреса. Без ожидаемого списка команда показывает адреса со статусом `RESOLVED`. `NO_ADDRESSES` и `LOOKUP_FAILED` различают отсутствие адресов и ошибку резолвера.

Результат относится к настройкам, локальным записям и кэшу этой машины. Для проверки после изменения DNS выполните команду в нужной сети.

## История SSH-задания

`GET /api/v1/jobs/{job_id}/timeline` требует действительную сессию и `vps:read` на VPS задания. Недоступное и отсутствующее задание возвращают 404. Ответ содержит только последовательность, время, статус и нормализованную причину событий принятия, перехода и завершения. История читается из зафиксированного аудита в одном snapshot с проверкой доступа, не выполняет SSH и не проверяет целостность цепочки. Сервер сверяет допустимость переходов, последовательность ревизий и итоговое состояние с записью задания. Несогласованные данные или более 100 подходящих событий дают 503, а не частичную историю. Ответ не содержит actor, деталей аудита, scope или permit.

Индекс по correlation ID отсутствует: ограничение ответа не ограничивает объём поиска в истории одного VPS. Индекс с проверенной миграцией требуется до capacity-приёмки. Это история отдельного probe, а не полная Timeline Stage2.

## Предпросмотр перезапуска контейнера

`GET /api/v1/resources/{resource_id}/docker/containers/{container_id}/restart-preview` требует HTTPS-сессию и права `vps:read` и `vps:restart` на одну VPS. Запрос принимает полный ID. Controller проверяет текущее наблюдение и возвращает `PREVIEW_ONLY` для контейнера в состоянии `RUNNING`. При устаревшем, неуспешном или несовместимом наблюдении возвращается 409. Неизвестная цель возвращает 404.

Ответ фиксирует проект и сервис, состояние, время наблюдения, boot ID, ревизии ресурса и политики и риск кратковременной недоступности сервиса. `preview_digest` — SHA-256 канонического JSON ответа без самого digest. Он описывает полученный снимок и не даёт права на исполнение. Запрос не создаёт сохранённый Change Plan, approval или job и не обращается к SSH/Docker. Для исполнения по ТЗ ещё нужны повторный preflight, проверка backup, подтверждение и проверка результата операции.

## Репетиция Change Plan для Docker restart

Компонент [change_drafts](../hostorbit/change_drafts.py) сохраняет черновики на приватной копии Controller DB после [репетиции миграции 2 → 3](stage1-migrations.md). Вызов выполняется в одной SQLite-транзакции с проверкой сессии, CSRF и прав `vps:read` и `vps:restart` на одну VPS. Черновик фиксирует точный ID последнего завершённого наблюдения, контейнер, boot ID и ревизии ресурса и политики. Сервер добавляет семантический diff и риск, вычисляет хеш и записывает ревизию вместе с Audit/Outbox.

Обновление черновика сохраняет предыдущую ревизию и принимает только точный strong ETag текущей. Без `If-Match` возвращается 428, с устаревшим или слабым ETag — 412. Для обновления нужно свежее успешное наблюдение той же цели.

`check_draft_baseline` повторно проверяет права, хеш плана, точный ETag и наблюдение в одном снимке SQLite. Новое наблюдение, даже с тем же временем, или изменение привязки цели даёт `STALE_BASELINE` (409), если цель по-прежнему доступна. Если наблюдение просрочено или цель недоступна, проверка возвращает причину отказа. Успешный результат `MATCHED` привязан к ревизии плана и моменту проверки. Проверка не пишет в базу и не выдаёт разрешение на выполнение.

`check_draft_probe` сверяет черновик с результатом `host.probe`, поставленного через `request_draft_probe` после сохранения черновика. Для однозначного порядка время создания задания должно быть позже времени сохранения черновика по часам Controller с точностью до секунды. Передайте ID задания, ETag и исходный ключ запроса. Проверка использует отдельную read-only транзакцию исходной БД и сопоставляет запись аудита исходного наблюдения в обеих БД. Она проверяет права в обеих БД и принимает только последний успешный и свежий результат с тем же контейнером, boot ID, областью доступа и ревизиями ресурса и политики. Несовпадение пользователя, ревизии, ключа или ID задания, а также истечение срока записи в журнале очереди дают `PREFLIGHT_PROBE_NOT_BOUND` (409).

`request_draft_probe` ставит `host.probe` в существующую очередь исходного Controller. Перед постановкой он проверяет ETag, общую запись аудита, права и привязку ресурса. Очередь повторно проверяет сессию, CSRF и `vps:probe` в транзакции записи. Повтор с тем же ключом на той же ревизии возвращает прежнее задание в пределах срока хранения ключа очереди. Для новой попытки укажите новый ключ. Сервер выводит ключ очереди через HMAC с закрытым случайным значением ревизии. По публичному хешу плана его вычислить нельзя. Черновики прежнего формата доступны для чтения и локальной сверки, а перед постановкой нового probe их требуется обновить с текущим ETag. Полученный ID передаётся в `check_draft_probe` после выполнения задания. Если область или политика изменились после постановки, результат сверки отклоняется.

В репетиции только Owner может сохранить черновик с `confirm_stateless_test=True`. Это подтверждение, что выбранный импортированный контейнер тестовый, не хранит эксплуатационные данные в writable layer, не зависит от сохранения состояния процесса и не затрагивает эксплуатационные внешние сервисы при restart. Подтверждение включается в хеш конкретной ревизии и записывается с актором в Audit/Outbox. Для следующей ревизии требуется новое явное подтверждение.

После успешного `check_draft_probe` совпадение baseline и решение Backup Gate выводятся отдельно. Без подтверждения возвращается `RESTART_OWNER_CONFIRMATION_REQUIRED`. При неполных данных о mounts возвращается `RESTART_MOUNT_OBSERVATION_REQUIRED`, для цели с mounts — `RESTART_MOUNTS_PRESENT`. При подтверждённом отсутствии mounts preflight различает `RESTART_NETWORK_OBSERVATION_REQUIRED` для неизвестной сети и `RESTART_NETWORK_NOT_ISOLATED` для неизолированной цели. Цель в изолированной сети получает `RESTART_DEPENDENCY_SCOPE_REQUIRED` при неполных сведениях о зависимостях и `RESTART_DEPENDENCY_SCOPE_UNSUPPORTED` вне проверяемого профиля. Подтверждённый профиль с явным подтверждением Owner даёт `BACKUP_NOT_REQUIRED` для класса `RESTART_STATELESS_TEST_CONTAINER` в репетиции. Во всех случаях исполнение остаётся `BLOCKED`. Approval точного плана и допуск к исполнению остаются отдельными условиями [ТЗ v2.4](spec/HostOrbit_Technical_Spec_v2.4.md#backup-gate-для-docker-restart).

Для фиксации результата `record_draft_backup_decision` повторяет проверку в транзакции `BEGIN IMMEDIATE` на копии БД, с CSRF и действующими правами. Событие `change_plan.backup_evaluated` содержит актор, цель, ID плана, ревизию, хеш плана, ID проверенного наблюдения и причину решения. Audit и Outbox записываются вместе. Повтор того же запроса возвращает прежнюю запись, пока ревизия и наблюдение остаются применимыми. Событие помечено `rehearsal: true`. Approval и разрешение на исполнение выдаются отдельным контуром.

Компонент доступен в репетиции. Live-миграция, HTTP-маршруты, допуск через backup gate, approval и исполнение требуют отдельной реализации. Обе проверки оставляют `execution=BLOCKED`.
