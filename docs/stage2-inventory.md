# Stage2: инвентарь зарегистрированных VPS

Первый компонент Stage2 по FR-006/FR-018 и §3.1 ТЗ v2.3: список и карточка уже локально зарегистрированных ресурсов. Существующие Auth, SQLite schema 2 и очередь наблюдений остаются источниками истины. Реализация использует FastAPI и стандартную библиотеку без новых зависимостей.

Выбран read model поверх существующей очереди: новый постоянный snapshot потребовал бы миграции и второго источника состояния. Регистрация через Web и обнаружение Docker/Nginx требуют отдельных контрактов и сюда не входят. Stage2/AC-28 этим компонентом не принимаются.

## Контракт

- `GET /api/v1/resources?after=<ULID>&limit=50`: только доступные по `vps:read` ресурсы, сортировка по ID, максимум 100 записей и `next_after`. Disabled-ресурсы остаются видимы.
- `GET /api/v1/resources/{id}`: 404 для отсутствующего или недоступного ресурса. Обе операции требуют действительную HTTPS-сессию и возвращают ETag/no-store.
- Метаданные: ID, revision, enabled, policy revision, даты регистрации/обновления. Policy digest, IP, ключи, Secret References, permits и actor IDs не публикуются.
- Наблюдение: `NOT_CHECKED` до завершённой попытки; `REACHABLE` только после успешного host.probe с текущими scope/policy и временем не старше 300 секунд, не позже текущего времени. Это SSH helper reachability, не здоровье приложений.
- Ошибка/UNKNOWN, смена scope, отключение ресурса, просроченная выборка и откат часов дают `UNKNOWN` с причиной. Последняя успешная выборка сохраняется отдельно как историческая, вместе с timestamp. Новая ожидающая попытка не стирает последнюю завершённую.
- Результат проецируется на фиксированные поля helper observation; произвольные данные job/credentials не сериализуются. Чтение не ставит задания, не выполняет SSH и не изменяет схему.
- После добавления маршрутов повторно проверяются Auth/RBAC и два затронутых capability reports; историческая приёмка сохраняется. Новая проверка явно автоматическая.

## Проверка границ

Недоступные ресурсы исключаются до pagination; завершённые попытки упорядочиваются по sequence события `job.finished`, даже при одинаковых timestamps; stale scope не оживляет старый успех; clock rollback не создаёт свежую выборку; лишние JSON поля не попадают в API. Каждый случай закреплён application-тестом.

Сначала выбирается ограниченная страница ресурсов, затем последняя попытка и последний успех определяются одним проходом связанной Audit-истории без изменения схемы. В локальном in-memory сравнении на синтетических 100 000 событиях и 25 ресурсах запрос занимал около 48 мс против 95–97 мс прежнего; это не нормативное capacity-испытание. Работа по истории остаётся неограниченной, индекс с проверенной миграцией и восьмичасовой soak по ТЗ остаются задачами до capacity-приёмки.

## Обнаружение Docker и Nginx

Обновлённые `ssh-gateway` и `typed-helper` поддерживают фиксированный запрос `hostorbit.v2.probe`. После проверки SSH host key helper читает метаданные двух путей на Ubuntu, `/usr/bin/docker` и `/usr/sbin/nginx`. В `observation.last_success.software` возвращаются только значения `PRESENT`, `NOT_DETECTED` или `UNKNOWN` для `docker` и `nginx`. Они описывают наличие инструментов в этих путях. Состояние служб, контейнеров и проектов Compose требует отдельного наблюдения.

При тихом отказе старого gateway с кодом 65 Broker повторяет фиксированный запрос v1 в том же SSH-соединении. В таком результате поле `software` отсутствует. При установке v2 замените оба root-owned файла через действующую процедуру установки helper. Старый Controller может использовать v1 с обновлённой парой.

## Контейнеры импортированных Docker-проектов

Для probe v3 владелец вручную добавляет до восьми контейнеров импортированного тестового Compose-проекта в `/etc/hostorbit/docker-discovery.json` на VPS. Каталог принадлежит root и закрыт от записи группы и остальных пользователей. Файл принадлежит root, имеет режим `0600` и одну жёсткую ссылку.

```json
{
  "v": 1,
  "containers": [
    {
      "id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "project": "fixture",
      "service": "web"
    }
  ]
}
```

Замените пример на полный ID контейнера и значения Compose project/service из проверенного импорта. При пересоздании контейнера укажите новый ID после проверки импорта. Helper использует один ограниченный GET к локальному `/run/docker.sock` с фильтром по утверждённым ID и сверяет метки проекта и сервиса. В Controller поступают только ID, проект, сервис и типизированное состояние. Карточка показывает время последнего успешного наблюдения. Состояние `RUNNING` описывает процесс контейнера, а доступность приложения проверяется отдельно.

Сводка Docker различает пустую область, некорректный защищённый файл и недоступность daemon. При старом gateway Broker выбирает v2 или v1 в том же закреплённом SSH-соединении после тихого отказа версии. Для v3 установите проверенные `ssh-gateway` и `typed-helper` по существующей [процедуре](stage1-runtime.md).

## История SSH-задания

`GET /api/v1/jobs/{job_id}/timeline` требует действительную сессию и `vps:read` на VPS задания. Недоступное и отсутствующее задание возвращают 404. Ответ содержит только последовательность, время, статус и нормализованную причину событий принятия, перехода и завершения. История читается из зафиксированного аудита в одном snapshot с проверкой доступа, не выполняет SSH и не проверяет целостность цепочки. Сервер сверяет допустимость переходов, последовательность ревизий и итоговое состояние с записью задания. Несогласованные данные или более 100 подходящих событий дают 503, а не частичную историю. Ответ не содержит actor, деталей аудита, scope или permit.

Индекс по correlation ID отсутствует: ограничение ответа не ограничивает объём поиска в истории одного VPS. Индекс с проверенной миграцией требуется до capacity-приёмки. Это история отдельного probe, а не полная Timeline Stage2.

## Предпросмотр перезапуска контейнера

`GET /api/v1/resources/{resource_id}/docker/containers/{container_id}/restart-preview` требует HTTPS-сессию и права `vps:read` и `vps:restart` на одну VPS. Запрос принимает полный ID. Controller проверяет текущее наблюдение и возвращает `PREVIEW_ONLY` для контейнера в состоянии `RUNNING`. При устаревшем, неуспешном или несовместимом наблюдении возвращается 409. Неизвестная цель возвращает 404.

Ответ фиксирует проект и сервис, состояние, время наблюдения, boot ID, ревизии ресурса и политики и риск кратковременной недоступности сервиса. `preview_digest` — SHA-256 канонического JSON ответа без самого digest. Он описывает полученный снимок и не даёт права на исполнение. Запрос не создаёт сохранённый Change Plan, approval или job и не обращается к SSH/Docker. Для исполнения по ТЗ ещё нужны повторный preflight, проверка backup, подтверждение и проверка результата операции.
